# 事故记录 2026-10-29 20:48 —— unbind 在 GPU 被占用时挂死

## 一句话

`push.sh` 的 `echo $DEV > .../unbind` 在 **GPU 被用户态程序占用**时不会失败、也不会返回，
而是**卡死在内核 `nv_pci_remove` 里**，且进程落成不可杀状态（D/R），最终只能重启。

**这不是重构引入的** —— 重构只调整了结构，`unbind` 那一行逻辑完全没变。
是环境变了：上午跑 push 时 GPU 空闲，晚上跑时 Firefox 等程序正占着 `/dev/nvidia*`。

---

## 现场

### 触发前的 GPU 占用（`fuser -v /dev/nvidia*`）

```
/dev/nvidia0:   union 1754 F.... piliplus
                union 2207 F.... RDD Process          ← Firefox 的渲染进程
/dev/nvidiactl: union 1754 F.... piliplus
                union 2207 F.... RDD Process
                union 62302 F.... stretchly
/dev/nvidia-uvm: union 1754 F.... piliplus
```

### 卡死位置（`/proc/<pid>/stack`，需 root）

```
[<0>] device_release_driver_internal+0x3b/0x200
[<0>] unbind_store+0xa1/0xb0
[<0>] kernfs_fop_write_iter+0x14f/0x200
[<0>] vfs_write+0x28c/0x440
[<0>] ksys_write+0x6d/0xf0
[<0>] do_syscall_64+0x87/0x1b0
[<0>] entry_SYSCALL_64_after_hwframe+0x76/0x7e
```

⇒ 停在 `device_release_driver_internal`，即**在等 `device_lock` / 等 `remove()` 完成**。

### 进程状态演进

| PID | 阶段 | state | 说明 |
|---|---|---|---|
| 85413 | 第一次 push（20:48） | R | utime=1 但 `kill -9` 无效 —— 卡在内核不可中断路径 |
| 85526 | 第二次 push（20:51） | D | `kill -9` 无效 |
| 85698 | bash -x 跟踪（20:53） | D | `kill -9` 无效 |

三个都杀不掉。后续 `bind` 尝试同样阻塞（15s 超时后仍挂着）。

### 最终状态

```
lspci -Dn | grep 10de        → 0000:01:00.0 0302: 10de:1b87 (rev a1)   ← 设备在
/sys/bus/pci/devices/.../driver → （无符号链接，未绑定任何驱动）
setpci -s 01:00.0 0.l        → 1b8710de                              ← 配置空间可读，设备没死
nvidia-smi                   → No devices were found                  ← 拿不到设备
lsmod                        → nvidia/nvidia_uvm/nvidia_drm/nvidia_modeset 都还在
load average                 → 4.48（被空转进程拉高）
```

⇒ **设备没坏，是内核锁被占死。** `cfg != 0xffffffff` 说明不是 ZOMBIE。

---

## 结论

**`unbind` 在 GPU 有活跃用户时会挂死。** 这解释了：
- 为什么上午 11:56 / 12:26 两次 push 都成功（GPU 空闲）
- 为什么晚上同样命令会挂（Firefox 占着 GPU）

### 必须给脚本加的保护

在 `unbind` 之前检查 GPU 占用，有占用就**拒绝执行并提示**，而不是盲写：

```bash
# 检查是否有进程持有 /dev/nvidia*
if fuser /dev/nvidia* >/dev/null 2>&1; then
    err "有进程正占用 GPU，unbind 会挂死内核"
    fuser -v /dev/nvidia*
    echo "  先关掉这些程序（浏览器/Electron 应用最常见），或改用 20-install.sh 重载模块"
    exit 1
fi
```

### 恢复办法

已确认**软件层救不回来**（kill -9 / rebind / 等 GPU 释放 都试过）⇒ **整机重启**。

## 与既有纪律的关系

`docs/安全纪律.md` 里原本记的是「用户态 mmap 写 BAR0 会打死设备」。
这条新事故补充了另一类风险：

| 风险 | 触发条件 | 后果 | 可逆性 |
|---|---|---|---|
| 用户态 mmap 写 BAR0（已有记录） | 链路降级瞬间 | ZOMBIE | 重启 |
| **`unbind` 时有 GPU 占用（本次）** | GPU 被程序持有 | 内核锁死 | **重启** |
| 写 `0x8C040` 带 COMMIT | 缺前置步骤 | 掉总线 | 重启 |

共同点：**都在内核层，都只能重启。** 所以「动手前先清场（关掉所有 GPU 程序）」应该写成硬性前置步骤。
