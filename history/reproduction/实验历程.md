# 实验历程（只记关键转折与否定结论）

原始研究记录共 200+ 篇，未随仓库发布（只在作者本地）。本文件只记
"为什么走这条路、为什么不走那条"。

---

## 第一阶段：确认问题存在（reports 176-183）

**起点**：P104-100 的 PCIe 带宽只有 0.78 GB/s，明显是 Gen1 x4 水平。

- 确认 `lspci` 报 `Speed 2.5GT/s`、`LnkCap.MaxSpeed=1`
- 确认 P106 有类似现象（用户类推）
- 摸清 BAR0 的声明位（`0x8841C`）与速率字段（`0x8C040.SPEED`）
- 参考 cmpunlocker 项目的做法（写 XP3G + `0x8841C` + `0x8C040` + Retrain）

**踩到的第一个坑**：`nvidia-smi` 的 PCIe 字段全是驱动缓存。
寄存器已经是 Gen2 了，它照样报 `gen.current = 1`。

---

## 第二阶段：手动推 Gen2 成功，但带宽不变（reports 182-186）

链路确实能推到 5GT/s（`LNKSTA=2`、`lspci` 显示 `Speed 5GT/s`），
但**跑 DMA 带宽还是 0.78**。

**这阶段最重要的收获**：搞清了三态判活
（D3COLD 可救 / GONE 要重启 / ZOMBIE 只能重启），
以及三条确定性致命操作（写 COMMIT、碰端点 Retrain、训练未完成时写 SPEED）。

**当时以为的结论**：带宽不变是因为"RM 已按 Gen1 初始化"。
这个判断是对的，但没有意识到**根因是驱动每次 cuInit 都主动降级**。

---

## 第三阶段：kretprobe 方案（reports 184）

找到了正确时机：`nv_pci_probe` 返回的瞬间。

- `gen2kr.ko` 用 kretprobe 挂 `nv_pci_probe`
- 在 probe 返回时解锁声明 + 写 SPEED=1 + 训练 + 根端口 Retrain
- 结果：Gen2 x4，**pinned H2D 1.56 / D2H 1.71 GB/s**，Xid 0

**这是第一次拿到翻倍带宽。** 但代价是必须带一个常驻守卫 ——
因为驱动会降，守卫要在 3.8 秒内拉回来。

---

## 第四阶段：找"锁定环"（reports 187-194）

想从根上解决，于是开始逆向"谁在写 SPEED"。

- 定位 `_nv017281rm`，以为那是锁定环
- 打了补丁（`or $0x80000` → `or $0x40000`），确证执行、确证生效
- **但单独用无效**：RM 已按 Gen1 初始化，链路推上去带宽仍是 Gen1

这一阶段还纠正了两个方法论错误：
- 「零引用 ≠ 死代码」在 NVIDIA RM 上不成立（67.5% 函数零入边，靠对象槽间接调用）
- `perf script` 必须 `-F comm,iregs`，否则寄存器永远读不到

---

## 第五阶段：守卫工程化（reports 196-197）

把守卫从 9.59s 优化到 3.84s：

- `retrain_min_ms` 本意是"两次完整尝试的间隔"，却被误用来卡 stage0→stage1 ⇒ 白等 2 秒
- 新增 `stage_gap_ms=150` 专管 stage 间隔
- `debounce_cnt` 10→3，`speed_settle_ms` 3000→800（扫描得出）

**两次打挂设备**：用户态 mmap 写 `0x8C040`，链路动态时 2/2 掉卡。
由此得到重要结论：**改链路控制寄存器必须走内核路径**。

---

## 第六阶段：机制终局（reports 198）

用 perf 抓到 `_nv017105rm` 的完整调用栈，终于看清：

```
rm_init_adapter → ... → _nv017755rm → _nv017105rm(mode=1)
```

**驱动不是"照抄当前速率"，是每次 cuInit 都主动要求 Gen1。**

同时查明：
- `0x8872C`（XVE_OVR）驱动**零引用** —— 我们一直在写一个驱动不碰的寄存器
- COMMIT 不是毒药，驱动自己会写（`_nv017105rm+0x1ff`）
- registry `RMPcieLinkSpeed` / `RMPcieStickyGenSpeed` 都**无效**
- 反复 reload 会让设备进入锁死态，**只能整机重启**

---

## 第七阶段：正解（reports 199）

用户提出：**"别让它降，而不是降了再救。"**

先纠正一个错误结论：之前说"SPEED=2 是端点内部回写、CPU 拦不了"是**错的**
（那次 perf 断点没生效）。四点断点实证 SPEED 完全由软件写。

然后找到最省的补丁：**平移 mode 白名单的边界**

```asm
- lea  -0x1(%rdx),%eax   /  cmp $0x2,%eax     → (mode-1) > 2 → bail
+ lea  -0x2(%rdx),%eax   /  cmp $0x1,%eax     → (mode-2) > 1 → bail
```

只改 2 个字节。mode=1 下溢成 `0xFFFFFFFF` → bail，2/3 照旧，≥4 照旧。
bail 返回 `%r12d` = 0 = CUDA_SUCCESS。

**验证（关键：必须摘掉守卫才测得出来）**：
- 无守卫 3 轮 cuInit + 等 10s → 链路一次没掉
- 20 分钟 353 轮 → 全成功，平均 0.70s，Xid 0
- 带宽 pinned 1.563 / 1.705 GB/s，**测后链路仍 5GT/s**
- 守卫回归：补丁+守卫同载 → guard 日志 **0 条**

## 走过的三条死路（详细记录，省得重走）

### 死路 1：手动推 Gen2 后跑 DMA
链路是 Gen2，`LNKSTA=2`，`lspci` 也对，但带宽永远 0.78。
因为 RM 已在 Gen1 下完成内部数据面初始化（SKP OS、credits、MPSS）。

### 死路 2：只 patch `_nv017281rm`
确证执行、确证生效（写入值从 `0x20085800` 变成 `0x20545800`），
但 `_nv017105rm(mode=1)` 随后会覆盖它。

### 死路 3：改 registry 参数
```bash
modprobe nvidia "NVreg_RegistryDwords=RMPcieLinkSpeed=2"
modprobe nvidia "NVreg_RegistryDwords=RMPcieStickyGenSpeed=1"
```
两个都挡不住降级。静态分析确认 `_nv017157rm` 确实读这些 key
（`RMPcieLinkSpeed` 写进 `obj[0xa38]` 策略位域），但它们不是"要不要 Gen2"的开关。

**副作用**：这轮实验反复 reload 驱动，把设备搞进了锁死态，只能整机重启。

---

## 还没闭环的两点

1. **`obj[0x954]` 的运行时取值** —— 这是 `set_link_speed(2)` 的门禁。
   需要冷启动后**首次** modprobe 的窗口，reload 之后就错过了。
2. **`rm_init_adapter` 里 `mode=1` 的源头** —— 20 层调用栈已记录，
   但常量在哪一层产生还没逐层看。若最终是硬编码或来自 VBIOS，
   则"让驱动原生要 Gen2"这条路彻底封死，确认补丁是唯一解。
