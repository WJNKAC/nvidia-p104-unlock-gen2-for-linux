### 1.1 分类结果（`tools/find_8c040_writes.py`）

| 类型 | 数量 | 说明 |
|---|---|---|
| **直接写**（`mov [reg+0x8C040], ...`） | **0** | ★ 一处都没有 |

```asm

```

## 3. 动态验证：前两个都不携带 0x8C040

用 perf 硬件断点（不受 `notrace` 限制）+ `--intr-regs` 直接读参数寄存器：

```bash
perf record -e mem:0x<ADDR>:x -a --intr-regs=cx,r8,si,dx -o d -- <cmd>
perf script -i d -F comm,ip,iregs     # → CX:0x...  R8:0x...
```

### 3.1 `_nv053912rm`（12 处调用它）

```
CX 分布：0x180×4283  0x160×4283  0x164×1738  0x70000×738  0x100cec×102 ...
含 0x8c040 的样本：0
```

**全在 0x160 ~ 0x10a4cc 区间，一次都没有 0x8C040。**
即使反复新建 CUDA 上下文（6 轮新进程）仍为 0。

### 3.2 `_nv049698rm`（2 处调用它）

```
在 _nv049698rm 上设执行断点，跑 5 轮新 CUDA 上下文
结果：samples = 0（一次都没被调用）
```

**⇒ 这个封装在这些场景下根本不执行。**

### 3.3 三个封装的汇总

| 封装 | 静态调用数 | 动态是否见 0x8C040 |
|---|---|---|
| `_nv053907rm` | 18 | ❌（未单独测，但其为读封装） |
| `_nv053912rm` | 12 | ❌ CX 里 0 次 |
| `_nv049698rm` | 2 | ❌ 根本没被调用 |

## 4. 因此得到一个重要的反证

> **在正常运行（含反复新建 CUDA 上下文）期间，
> 驱动并不写 `0x8C040` 的 SPEED 字段。**

这与此前的 SSE 观测**矛盾**，需要重新解释：

之前观察到（reports/188）：
```
[ 3.08s] SPEED=2 LNKSTA=0x1041 sp=1   ← CUDA 启动瞬间
```
当时判定为"驱动写 SPEED=2"。但**采样间隔是 20 ms，只能说明"值变了"，不能说明"谁写的"**。

可能的其他解释（都还没排除）：
1. **硬件自己变了** —— 链路重训失败后，LTSSM 把 SPEED 字段回滚到实际可用速率
2. 由某条**未走这三个封装**的路径写入（如 GSP 固件直接写）
3. primus/Xorg `:8` 的另一个 nvidia 驱动实例在写（该实例有自己的 MMIO 映射）

**⇒ 下一步必须用"物理地址写断点"直接抓写者，而不是靠采样推断。**
（本次尝试时设备已进入 C. ZOMBIE，未能完成。）

## 6. 修复的两个工具 bug（本轮踩到的）

1. **`setpci` 取 BAR0 会拿到 `0xffffffff`**（无 sudo 或设备异常时）
   ⇒ 改用 `/sys/bus/pci/devices/.../resource` 第一行，更可靠
2. **`$((0x$VAR))` 写法错误**：当 `$VAR` 已含 `0x` 前缀时会变成 `0x0x...`
   ⇒ 应为 `R=$(awk ...); printf '%x' $((R))`

## 7. 现在确定的事 vs 待验证的事

### 已确定（静态 + 动态双证）

- `.text` 里 `0x8C040` 出现 33 次，**全部是"偏移当参数"**
- 这些调用只去 3 个封装：`_nv053907rm`(18) / `_nv053912rm`(12) / `_nv049698rm`(2)
- `_nv053912rm` 收到的 CX 里 `0x8C040` 出现 **0 次**
- `_nv049698rm` 在新 CUDA 上下文场景下**未被调用**

### 待验证（需设备恢复）

- **物理地址写断点**：`perf record -e mem:<BAR0+0x8C040>:w -a` 
  → 直接抓写者的 IP，不需要猜是哪个封装
- 若物理地址断点也抓不到 ⇒ 说明写入来自 **GSP 固件**（CPU 视角不可见），
  那"patch 软件写点"这条路彻底关闭，只能回到 kretprobe + 守卫
