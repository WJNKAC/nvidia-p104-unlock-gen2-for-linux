## 0. 本轮最重要的三条

1. **驱动的 `set_link_speed(1)` 在每次 `cuInit` 都被调用** —— 不是"照抄当前速率"的锁定环，
   而是**主动要求 Gen1**。调用点在 `rm_init_adapter` 里，perf 实测 4/4 次 `DX=0x1`。
2. **`0x8872C`（XVE_OVR）驱动从来不用** —— `.text` 里零引用。我们一直在盲写一个
   驱动自己都不碰的寄存器（来自参考项目），这解释了它时序行为的不可预测。
3. **驱动自己会写 COMMIT（bit0）** —— `_nv017105rm+0x1ff` 明确 `or $0x1,%r15d` 后写回。
   ⇒ reports/186 的「写 COMMIT 必死」是**误归因**，致命的是"缺前置步骤就写"。

## 1. 静态：`_nv017105rm` / `_nv017102rm` 是驱动的 `set_link_speed(mode)`

### 分派结构（`_nv017105rm`，`.text+0x127d60`，0x49e 字节）
```asm
127d66: lea -0x1(%rdx),%eax
127d81: cmp $0x2,%eax
127d84: ja  1280c8              ; edx ∉ {1,2,3} → bail
127d8a: cmp $0x2,%edx ; je 1280d9   ; mode 2 → 检查能力位
127d97: je  128169                  ; mode 3 → 检查能力位
                                     ; mode 1 → 顺序落入
```

### 三条分支各写什么（Pascal 编码）
| mode | 指令 | SPEED[19:18] | 速率 |
|---|---|---|---|
| 1 | `or $0x80000,%eax`（127e65） | 2 | **2.5GT/s = Gen1** |
| 2 | `or $0x40000,%eax`（12819b） | 1 | **5.0GT/s = Gen2** |
| 3 | 清 SPEED（eax 已在 127e4e 清过）| 0 | **8.0GT/s = Gen3** |

⇒ **`mode` 直接就是 PCIe 代数。**

### 能力门禁
```asm
1280d9: cmpb $0x0,0x954(%rsi)   ; mode 2 需要 obj[0x954] != 0
1280e0: jne  127d9d             ; 有 → 继续
1280e6: jmp  1280c8             ; 无 → 直接 bail，什么都不写

12816d: cmpb $0x0,0x955(%rax)   ; mode 3 需要 obj[0x955] != 0
```
`_nv017102rm`（`.text+0x130110`）是兄弟版本，额外支持 mode 4（门禁 `obj[0x956]`）。

### 顺序里还有一段「等待回读匹配」
```asm
127edd: 读 0x8C040 → 127f00 再读 → call <查询，edx=0x549>（超时参数）
127f19: cmp %r8d,0x24(%rbp)     ; 回读 == 期望？
127f21: jne 127ed8              ; 不等就重来，直到 eax == 0x65
```

## 2. 动态：`set_link_speed` 每次 `cuInit` 都被以 **mode=1** 调用

perf 硬件执行断点（`_nv017105rm` 是 notrace，只能 perf）：

```
DX:0x1   ← 4/4 次
样本来源：minictx ×3、bwtest2 ×1
```

### 完整调用栈（`perf -g`，一次 `minictx`）
```
_nv017105rm              ← set_link_speed(mode=1)
_nv017755rm+0x98         ← 直接调用者
_nv021133rm+0x20e / _nv021141rm+0x1c0 / _nv021137rm+0x3e
_nv050280rm / _nv014838rm / _nv014904rm / _nv050526rm / _nv015094rm
_nv050988rm / _nv031219rm / _nv031217rm / _nv031218rm / _nv031502rm
_nv000790rm+0x1123
rm_init_adapter+0xcd     ← ★ RM 适配器初始化
nv_open_device+0x4b7
nvidia_open+0x1d3
cuInit → minictx
```

### 调用者 `_nv017755rm` 的判断逻辑（`.text+0x127b40`）
```c
u32 _nv017755rm(dev, obj, u32 mode)      // r13d = mode
{
    r14d = LNKSTA & 0xf;                 // 当前链路速率
    if ((mode - 1) > 2) bail;
    eax = obj[0x9a8];                    // 缓存的最大支持速率
    if (eax < r14d && eax != 0) goto err;
    if (mode == r14d) return;            // ★ 目标==当前 → 什么都不做
    call obj[0x470](dev, obj, mode);     // → _nv017105rm
}
```

⇒ **现在链路是 Gen2（r14d=2）而 mode=1，两者不等，于是每次都主动降回 Gen1。**
这就是"每新建上下文就掉速"的完整机制 —— 与"锁定环"无关，是**显式的策略调用**。

## 3. 能力位从哪来：`_nv017279rm` 五路求交 → `_nv017812rm` 落盘

### `_nv017812rm(dev, obj, flags)`（`.text+0x11a230`，0x73 字节，纯 setter）
```asm
11a23c: test $0x4,%dl  ; je skip
11a241: movb $0x1,0x954(%rsi)   ; flags & 0x04 → cap Gen2
11a24d: movb $0x1,0x955(%rsi)   ; flags & 0x08 → cap Gen3
11a259: movb $0x1,0x956(%rsi)   ; flags & 0x10 → cap mode4
11a265: movb $0x1,0x957(%rsi)   ; flags & 0x20 → cap mode5
```
无 MMIO、无副作用，纯内存写。

### `_nv017279rm`（`.text+0x13c320`）= 求交后 tail-call
```asm
13c337: call <直接调用>          → ebx = cap0
13c34c: call *(obj+0x1a8)        → r15d = cap1
13c362: call *(obj+0x1b0)        → r14d = cap2
13c373: call *(obj+0x1b8)        → 存 0xc(rbp) = cap3
13c391: call *(obj+0x1c0)        → eax = cap4
13c39c: edx = ebx & r15d & r14d & cap3 & eax
13c3b3: jmp _nv017812rm
```
⇒ **五路按位与**，任何一路缺 `0x04`，Gen2 能力位就被清掉。

**动态未能捕获 `_nv017812rm`**（unbind/bind 窗口内 0 命中），
推测它只在更早的初始化路径里跑一次。这一环仍待补。

## 4. `0x8872C` 是我们的发明，驱动零引用

```
'0x8872C 作为 mov-imm' 在 .text 命中：0 处
```

`gen2kr` 一直写 `0x8872C = 6`（来自参考项目 cmpunlocker 的做法），
但**驱动从不访问这个寄存器**。这解释了为什么它的时序行为一直不可预测：
没有任何来自驱动侧的行为可以对照。

⚠ 不代表不能用（实测两次"触发训练 + 根端口 Retrain"确实有效），
但它是一个**无文档、无参照的私有开关**，应保持敬畏。

## 5. ★ 驱动自己会写 COMMIT —— reports/186 的结论需要修正

`_nv017105rm` 在"链路宽度字段 == 2"的分支里：
```asm
127f33: movl $0xb,0x18(%rbp)     ; 重试计数 = 11
127f40: and  $0xfffffff0,%r15d    ; 清 bits[3:0]
127f47: mov  $0x8c040,%ecx
127f4e: or   $0x1,%r15d           ; ★ 置 bit0 = COMMIT
127f5a: call <写 0x8C040>
```

**这是一个真实存在的、驱动自己的 COMMIT 写入路径。**

`commit_audit.py` 扫全部 33 个写点，其中 6 个在调用前对值寄存器动过 bits[3:0]；
经人工核对，`_nv017105rm+0x1ff` 是确定无疑的 COMMIT（中间没有再写别的）。

### 结论修正
- reports/186：「写 `0x8C040.bit0`(COMMIT) → **任何状态都必死**」
- **现在**：COMMIT 是驱动正常流程里的「提交/生效」步骤。
  我们自己写时之所以死，是因为**缺前置步骤**（SPEED 未写、训练未完成、来源值含垃圾位），
  不是 COMMIT 本身有毒。

⚠ **但这不构成"可以写 COMMIT"的许可**。外部写入仍然没有驱动那套前置序列，
  仍然不要写。

## 7. ★★ 状态污染：多次 reload 后无法自愈，只能重启

### 现象
在做了多轮 registry 实验 + 驱动 reload 之后，设备进入一种**锁死状态**：

```
LnkCap  = 0x00453c41  MaxSpeed=1
LnkCap2 = 0x00000002  vector=0x02（仅 Gen1）
LnkCtl2 = 0x0001      TLS=1
0x8841C = 0xc0b4ad00  ← 声明位写对了！
0x8872C = 0x00000006  ← 训练触发了！
0x8C040 SPEED=1       ← 也对
但 LNKSTA 永远是 1
```

### 试过的所有挽救手段（全部失败）
| 手段 | 次数 | 结果 |
|---|---|---|
| `unbind/bind` 触发 push | 6 | 全部 `未升速，LNKSTA=1041` |
| 守卫按回 SPEED + 触发训练 + 根端口 Retrain | 13 | 全部失败 |
| 守卫重写端点 TLS=2 | 连续 ~20 次 | 写 2 后下一轮读回 1（被钳住） |
| 守卫重新解锁声明 + 触发训练 | 9 | `CAP2` 始终 0x0002 |

### 重启后
一次重启，`insmod gen2kr` + `unbind/bind`，**一次 push 成功**：
```
LnkCap MaxSpeed=2 / LnkCap2=0x06 / LNKSTA=2 / TLS=2 / SPEED=1
```

⇒ **结论：驱动被反复 reload 会把「TLS=1 + 声明 Gen1」固化到某种驱动侧状态里，
   用户态与守卫都抢不过；只有整机重启能清。**

### 操作纪律
- 试验时**尽量减少驱动 reload 次数**，需要改参数时集中一次做完
- 一旦出现"CAP2 恒 0x0002 + TLS 恒 1 + 多次 push 全失败"，**不要再试，直接重启**
- 不要把"连续失败"当成"方法不对"，它可能只是状态脏了

## 10. 我犯的一个错（用户当场纠正）

我曾拿 `nvidia-smi` 的 `Device Max: 1` 当作"驱动认为端点能力是 Gen1"的证据。
**这是错的** —— `nvidia-smi` 的 PCIe 字段读驱动缓存，
这条铁律 reports/176-178 就写过，我却又踩了一次。

同一时刻寄存器实际是：`LnkCap=0x00454c42 → MaxSpeed=2`（Gen2）、`LnkCap2=0x06`、
`LnkSta=0x1042`、`LnkCtl2=0x0002` —— **四处全是 Gen2**。

⇒ 重新确认：**PCIe 状态判据只能是寄存器（LNKSTA/LnkCap/LnkCtl2），
   `nvidia-smi` 的任何 PCIe 字段都不能当判据。**
