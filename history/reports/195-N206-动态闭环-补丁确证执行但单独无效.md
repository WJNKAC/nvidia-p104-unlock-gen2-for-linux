# 195 / N206 — 动态闭环：补丁点确证执行、补丁精确生效、但单独补丁无效

日期：2026-10-29 08:00–09:00
设备：P104-100（10de:1b87），Debian 13 / kernel 6.12.113+deb13-amd64 / NVRM 580.178.04
状态：设备存活，链路当前 Gen1（downgraded），补丁已应用

---

## 0. 一句话结论

**补丁是真的（点被执行、字节生效），但单独用没有价值。**
`_nv017281rm` 里那条 `or $0x80000` 确证**每次新建 CUDA 上下文都执行**，
补丁把写入值从 `0x20085800`(SPEED=2) 改成 `0x20545800`(SPEED=1)，实测生效。
但把链路手动推到 Gen2 后跑真实 DMA，带宽仍是 **0.776/0.852 GB/s（Gen1 水平）**，
链路在传输开始前就降回 Gen1 —— 因为 **RM 内部已按 Gen1 完成初始化**。
⇒ 仍然只能在 `nv_pci_probe` 时机推 Gen2（gen2kr 路线），补丁替代不了它。

## 1. ★★★ 推翻 reports/191 的一个假结论（工具误用）

reports/191 曾断言：「`_nv053912rm` 的 CX 里 `0x8C040` 出现 **0 次**」，并据此推翻
"它是 BAR0 写函数"。

**这是工具误用。** `perf script` **默认输出不含寄存器**，必须显式加 `-F comm,iregs`：

```
$ perf script -i d                      # 默认：只有 comm/pid/cpu/time/event
  bwtest2  3275 [005] 197.093053: 1 mem:0xffffffffc1981000:x: ffffffffc1981000 ...

$ perf script -i d -F comm,iregs        # ★ 寄存器在这里
  bwtest2  ABI:2  CX:0x8c040  DX:0x1  SP:0xffffd4018295b8d8  IP:0xffffffffc1981000  R8:0x20085800
```

重测（跑 1 次 `bwtest2 32 1`，80,375 次 `_nv053912rm` 调用）：
**`CX==0x8c040` 命中 1 次，R8=`0x20085800`** —— 1 个上下文写 1 次，完全对得上。

⇒ **reports/191 的"0 次"作废**。`_nv053912rm` 确实是 BAR0 写封装：
```asm
5ff6d0: mov %ecx,%r13d      ; ECX = 第 4 个参数 = 寄存器偏移
5ff6e0: mov %esi,0xc(%rbp)
5ff747: test %ebx,%ebx ; jne 5ff730   ; 重试循环
5ff773: lea 0x4120(%rdx),%rdi         ; BAR 映射基址在对象 +0x4120
```

**新增铁律**：用 perf 硬件断点读寄存器时，`perf script` 必须带 `-F comm,iregs`；
不加就等于没抓寄存器，会把"没看到"误判成"没发生"。

## 2. ★★★★★ 补丁点确证执行（这是 reports/193 遗留的最大不确定点）

`_nv017281rm`（`.text+0x1269f0`，运行时 `0xffffffffc19809f0`）**是 notrace**：
`available_filter_functions` 里没有它，kprobe/bpftrace 全被拒。
只有 perf 硬件执行断点可用。

### 2.1 空闲不执行，新建上下文才执行
| 场景 | 命中次数 |
|---|---|
| 空闲 20s | **0** |
| `bwtest2` 跑一次（1 个 ctx） | **1** |
| 循环 5 次（5 个 ctx） | **5** |
| `minictx` 1 轮 | **1** |

**N 个上下文 ⇒ N 次执行**，每次都在 `bwtest2`/`minictx` 进程上下文里。
⇒ 它是 **CUDA 上下文初始化的必经路径**，不是"链路异常恢复分支"。

### 2.2 分支端点也确证（不只是函数入口）
对 `0x127000`（`or $0x80000`，即写 SPEED=2 那条）打点，**5 次 ctx 命中 5 次**。
同时抓到 **`DX:0x1`** —— 正是 `cmp $0x1,%edx` 里的 sp=1，分支条件吻合。

### 2.3 写入值确证（完整因果链）
```
CUDA ctx 创建
 → _nv017281rm                        (5/5, 1/1)
 → 读 0x8C040 + 读 0x88088 取 LNKSTA   (DX=0x1 → sp=1)
 → 0x127000: or eax,0x80000            (5/5 命中)
 → call _nv053912rm(CX=0x8c040, R8=0x20085800)   (1/1 命中)
 → bits[19:18]=2 → 2.5GT/s → 锁死 Gen1
```
**这条链第一次在动态上被完整坐实。**

## 3. ★ 补丁精确生效

`patch_speed_lock.py apply` → `0x127043: 0x08 → 0x04`，反汇编确认：
```
127000: 0d 00 00 04 00   or $0x40000,%eax     ← 原 0x80000
```

重载驱动后重测同一写入点：

| | 写入 0x8C040 的值 | bits[19:18] | 速率 |
|---|---|---|---|
| 补丁前 | `0x20085800` | 2 | 2.5GT/s |
| 补丁后 | `0x20545800` | **1** | **5.0GT/s** |

**只改 SPEED 字段，其他位一字未动。**

### 顺手修掉 `patch_speed_lock.py` 的一个 bug
原脚本在 `check` 时用 `SIG_OR`（含 0x08）校验目标字节，
**打过补丁后字节变 0x04，校验必然失败**，报"该处字节与预期不符，拒绝打补丁"——
会让人误以为补丁没打上。已加 `SIG_OR_NEW`，同时接受两种形态并区分显示。

## 4. ★★★★★ 为什么单独补丁没有用（本轮最重要的否定结论）

### 4.1 补丁后链路确实能自己升上去
`0x8C040` 保持 `0x20545800`（SPEED=1），配合：
① 解锁声明（`LCAP2 0x0002 → 0x0006`）② `0x8872C=6` ③ 根端口 Retrain（1–2 轮）
→ `LNKSTA[3:0]=2`，`lspci: Speed 5GT/s, Width x4`（无 downgraded 标记）。

### 4.2 但一跑 DMA 就降级，带宽毫无改善
```
起点: LnkSta: Speed 5GT/s, Width x4
bwtest2 128 3:
  pageable   H2D 0.776   D2H 0.852 GB/s
  pinned     H2D 0.778   D2H 0.855 GB/s     ← Gen1 水平（Gen2 应为 1.55）
终点: LnkSta: Speed 2.5GT/s (downgraded), Width x4
Xid: 无（因为链路在 DMA 前已降级，没形成"Gen2 链路 + Gen1 内部状态"错配）
```

### 4.3 机制：RM 内部时间线错配（再次印证 reports/184）
手动推 Gen2 只是改了**链路和寄存器**，但 RM 已经在 Gen1 下完成了内部数据面初始化
（SKP OS 顺序集、credits、MPSS 全部按 Gen1 配）。
新建上下文时 RM 走自己的链路配置流程 → 协商不上 → 降级 → 并把 SPEED 回写为 2。

**⇒ 唯一有效的时机仍然是 `nv_pci_probe` 返回的那一瞬（gen2kr 方案）。**
补丁能保证"它不再主动锁 Gen1"，但救不回"RM 已按 Gen1 初始化"。

### 4.4 顺带否掉一个猜想：不是"第二个写入者"
从 Gen2 起点采样 320 万次/12s，抓到同一瞬间（**0.090s**）：
```
0x8C040  0x20545800(SPEED=1) → 0x20585800(SPEED=2)
0x88088  0x1042(sp=2)        → 0x1041(sp=1)
```
起初判断为"另有函数改写 SPEED"。但逐层排查后：

| 检查 | 结果 |
|---|---|
| `_nv017105rm`（执行断点） | 命中 1 次，是同批 4 个候选里唯一执行的 |
| 它内部两处 `or $0x80000`（0x127e65 / 0x12803b） | **各 0 次**，没走 |
| 单轮 `minictx`，`_nv053912rm` 全部 `CX=0x8c040` | **只有 1 次，值恒为 `0x20545800`(SPEED=1)** |
| 单轮后寄存器终值 | `0x20545800`，**SPEED 保持 1** |

⇒ **补丁后没有第二个软件写入者**。SPEED 变 2 是链路降级过程中
由端点内部（硬件/GSP 侧）回写的，CPU 不可见，软件侧无从拦截。

**这条结论很重要**：它把"再 patch 一个函数"这条路直接关掉了。

## 4.5 ★★★★★ 补丁已回滚；gen2kr 在 6.12.113 上仍然有效，但需长测试

### 重编 gen2kr 并验证
`gen2kr.ko` 原为 6.1.0-50 编译，在 6.12.113 上不能 insmod。重编：
```bash
cd /data/labs/nvidia/pcie-gen2/kmod && make          # gcc 14.2 直接编，无需 CC=gcc-12
```
编译干净通过（只有 gen2hw.c 两个 unused 警告）。

### 两组对照（同一晚、同一设备）

| | 打补丁时 | 回滚补丁后 |
|---|---|---|
| `insmod gen2kr` + `unbind/bind` | push 后 `未升速，LNKSTA=1041` | **`★ SUCCESS Gen2 LNKSTA=1042（第 1 次）`** |
| push 写入的 lnkcfg0 | `20545800` (SPEED=1) | `20545800` (SPEED=1) |
| 短测 `128MB×3` | 0.776 / 0.852 | 0.778 / 0.855 |
| 长测 `512MB×15` | 未测 | **pinned H2D 1.554 / D2H 1.709** |

**注意**：两次 `lnkcfg0` 都是 `20545800`(SPEED=1) ——
因为 **gen2kr 的 push 自己就会写 SPEED=1**（`writel((lk & ~0xC0000) | (1<<18))`）。
所以补丁在这一层是**冗余**的，不是它带来了 SPEED=1。

### 长测复现（关键，别被短测误导）
```
buffer=512 MB  iter=15
  pageable  H2D med 0.776  max 1.552   D2H med 1.704  max 1.706
  pinned    H2D med 1.554  max 1.555   D2H med 1.709  max 1.710  GB/s
```
与 reports/184 的 `1.560 / 1.699` 吻合。

**为什么短测只有 0.778**：`bwtest2` 一新建上下文，端点内部即降级；
gen2kr 的守卫要花 **约 20 秒**（日志：779s 按回 → 782/784/786/788/790… 连续失败）才把链路拉回。
`128MB×3` 全程落在恢复窗口内，测到的必然是 Gen1 数值。
⇒ **评价这个方案必须用 `512MB×15` 以上，或在链路就绪后立刻起测。**

### 补丁的最终判定
- 单独用：**无效**（RM 已按 Gen1 初始化，见 §4）
- 与 gen2kr 合用：**冗余**（gen2kr 自己写 SPEED=1）
- 是否**有害**：本晚数据（打补丁时 push 失败、回滚后 push 成功）**提示可能有害**，
  但每组只有 1 次，**证据不足，不能定论**。

⇒ **已回滚补丁**，驱动恢复原始 md5 `7f6805ed15f1ae8122aa78e65a5d48a0`。
若将来要重评"补丁是否有害"，必须做 ≥5 次对照的 `unbind/bind` 成功率统计。

| 工具 | 用途 |
|---|---|
| `probe-lock.sh` | 算运行时地址 + 校验可插桩性（notrace 会在这里暴露）+ 打印 perf 命令模板 |
| `probe-run.sh` | 单场景执行断点计数（`idle`/自定义） |

| `probe-writer.sh` | 抓写封装实参（**必须 `-F iregs`**） |
| `probe-one-ctx.sh` | 单轮上下文 + 列出全部 0x8C0xx 写入 |
| `probe-multi.sh` | 多候选函数同时打点（x86 最多 4 个） |
| `probe-patch2.sh` | 定位 `_nv017105rm` 内两条 `or $0x80000` 哪条执行 |
| `probe-who-writes.sh` | 写封装 + 调用栈 |
| `trace-downgrade.sh` | 从 Gen2 起点采样，抓降级瞬间 |
| `unlock-decl.py` | **只做**解锁声明 + 触发训练（不写 SPEED，避开必死路径） |
| `minictx.c` / `minictx` | 只建/销毁上下文，**零 DMA**（观察链路不被 DMA 干扰） |

### 踩过的坑（都写进脚本注释了）
- `dash` 的 `$(( ))` 对 `0xffffffffc185a000` 报 `Illegal number`（>2^63）→ 用 python 算地址
- SSH + 单引号 + `sh -c "..."` + `python -c "..."` 嵌套会吃掉引号 → **一律写成脚本文件传过去**
- `/dev/mem` 必须 `O_RDWR` 打开，`O_RDONLY` + `PROT_WRITE` 会 `PermissionError`
- `grep 'Speed 5GT/s'` 会误匹配 `Speed 2.5GT/s`（子串）→ 判据用寄存器 `LNKSTA[3:0]==2`
- 掉速后 `0x8C040.SPEED` 已被写成 2，此时重训目标仍是 2.5GT，**永远推不上 Gen2**；
  必须先让 SPEED 回到 1 再重训

## 6. 补丁的残留价值（别全盘否定）

虽然单独用无效，但它有明确的正向作用：
1. **链路掉速后不再被主动锁死**：`_nv017281rm` 会请求 5GT/s，而不是 2.5GT/s
2. 配合 gen2kr 时，**上下文创建不再把 SPEED 打成 2**，
   可能减少守卫的"按回"次数（待测）
3. 是"RM 完全理解 Gen2"的辅助证据

**回滚随时可用**：
```bash
sudo python3 /data/labs/nvidia/pcie-gen2/tools/patch_speed_lock.py revert
# 备份：/lib/modules/6.12.113+deb13-amd64/updates/dkms/nvidia.ko.orig_speedlock
```
