## 1. 静态分析：驱动是怎么决定 SPEED 字段的

### 1.1 先纠正一个方法论错误

第一版扫描脚本（`find_lnkcfg0.py`）假设访问形式是 `mov [0x8c040+reg], ...`，
结果 **0 处命中**，并且报 `PT_LOAD 段 0 个`。

原因：`.ko` 是 **ET_REL 可重定位目标文件，没有 program header**，必须用 **section header**；
而且实际访问形式完全不是 displacement。

### 1.2 真正的形式：偏移当函数参数

`.text` 里 33 处 `0x8C040` 全部是：

```
b9 40 c0 08 00     mov $0x8c040, %ecx
```

即驱动通过**函数封装**访问 BAR0，偏移作为参数传入（形如 `os_reg_read(pGpu, offset)`）。

### 1.3 核心例程（`.text+0x126c4e`，已完整反汇编）

```asm
; ---- 读 0x8C040 ----
126c51: mov  ecx, 0x8c040
126c56: xor  edx, edx
126c58: xor  esi, esi
126c5a: mov  rdi, r13            ; r13 = pGpu
126c5d: call <reg_read>          ; → eax = LINK_CONFIG_0
; ---- 读 0x88088 取当前速率 ----
126c67: mov  ecx, 0x88088        ; LINK_CTRL_STATUS
126c71: mov  ebx, eax            ; 保存 LINK_CONFIG_0
126c73: call <reg_read>
126c78: shr  eax, 0x10           ; 高 16 位 = LNKSTA
126c7f: and  edx, 0xf            ; edx = 当前速率 sp
; ---- 清 SPEED[19:18] ----
126c82: and  eax, 0xfff3ffff     ; ~0x000C0000
; ---- 按当前速率决定写什么 ----
126c87: cmp  edx, 0x1
126c8a: je   0x127000            ; sp==1 → 走下面那个分支
126c93: or   r8d, 0x40000        ; SPEED=1
126c9a: cmp  edx, 0x2
126c9d: cmovne r8d, eax          ; sp!=2 → SPEED=0
126cb0: call <reg_write>         ; 写回 0x8C040

; ---- sp==1 分支 ----
127000: or   eax, 0x80000        ; SPEED=2      ← 补丁目标
127005: mov  r8d, eax
127008: jmp  0x126ca1            ; 回去写
```

### 1.4 映射成速率表（Pascal 编码：0=8GT / 1=5GT / 2=2.5GT）

| 当前 LNKSTA | 驱动写入 SPEED | 硬件解码 | 结果 |
|---|---|---|---|
| sp=1 (2.5GT) | `2` | 2.5 GT/s | **锁死 Gen1** |
| sp=2 (5GT) | `1` | 5.0 GT/s | 保持 Gen2 |
| sp=3 (8GT) | `0` | 8 GT/s | 保持 Gen3 |

**结论：这不是"主动钳制"，而是"照抄当前值"。**

因为冷启动时 `LCAP2` 只声明 2.5GT → 链路训练得 Gen1 → 这个例程写 SPEED=2
→ 于是永远停在 Gen1。**这是一个自我强化的锁定环。**

这也解释了为什么 reports/184 的「probe 时机」有效：只要在它运行前让链路先到 Gen2，
它自己就会写 SPEED=1 并维持。

## 2. 1 字节二进制补丁：打了，但无效

### 2.1 补丁内容

把 `sp==1` 分支的 `or eax, 0x80000`（SPEED=2）改成 `or eax, 0x40000`（SPEED=1）。

```
文件偏移 0x127043：0x08 → 0x04
原始: 0d 00 00 08 00 41 89 c0 e9 94 fc ff ff
补后: 0d 00 00 04 00 41 89 c0 e9 94 fc ff ff
```

工具：`tools/patch_nvko.py`（check / apply / revert，签名唯一性校验 + 自动 `.orig` 备份）
- 签名 `0d000008004189c0e994fcffff` 命中 **1 处**，文件偏移 `0x127040`
- md5 `7f6805ed15f1ae8122aa78e65a5d48a0` → `945915e78f5224367590e5d22cd978cf`
- Secure Boot 为 disabled、lockdown 为 none，补丁模块可正常加载

### 2.2 直接效果：确实能少一次报错，但链路维持不住

打补丁 + `guard_rounds=1`（几乎无守卫）后观察 60 秒：

```
[512.83] [guard] 补 Retrain（LNKSTA=1041）
[512.83] 守卫结束，共按回 SPEED 0 次       ← 守卫退出
[10s] ep=1042  [15s] 1042  ...  [60s] 1042  ← 60 秒全程 Gen2
```

看起来有效。但一跑带宽就暴露：

```
测前: 1042
pinned H2D med 0.778  D2H 0.855     ← Gen1 水平
测后: 1041   +5s: 1041   +10s: 1041 ← 再没回来
```

**补丁让驱动写 SPEED=1，但没有人触发重训**，链路掉了就回不来。

### 2.3 A/B 对照：补丁对回压次数毫无影响

固定场景：空闲 20 秒 + `nvidia-smi -q` ×3，统计守卫的「SPEED 被改回」次数。

| 组 | 空闲 20s 回压 | nvidia-smi ×3 后回压 | 补 Retrain |
|---|---|---|---|
| **B（打了补丁）** | 0 | **3**（每次 1 次） | 6 |
| **A（原始驱动）** | 0 | **3** | 6 |

**完全相同。补丁没有效果。**

### 2.4 为什么无效：`.text` 里有 38 处同类写入

`tools/scan_speed_writes.py` 统计：

```
or  eax, 0x80000  → SPEED=2(Gen1) :  总计 44，.text 内 38
or  r8d, 0x80000  → SPEED=2       :  总计  4，.text 内  4
or  eax, 0x40000  → SPEED=1(Gen2) :  总计 45，.text 内 45
or  r8d, 0x40000  → SPEED=1       :  总计  9，.text 内  9
```

**38 处写 SPEED=2**，说明这个"按当前速率回写"的逻辑被大量内联复制（不同调用点/不同架构分支）。
改一处等于没改。

⇒ **二进制补丁路线不可行。**
批量改 38+ 处风险也高：`or reg, 0x80000` 在其他寄存器上下文里完全可能合法
（bit19 不是只有 LINK_CONFIG_0 用）。

**⇒ 结论：kretprobe + 守卫循环仍是正确方案。已回滚补丁，驱动恢复原始 md5。**

## 4. 空闲期行为（重要，说明守卫开销很小）

```
纯空闲 20 秒（不碰 GPU）：
  [5s] 1042  [10s] 1042  [15s] 1042  [20s] 1042
  空闲期按回 SPEED: 0
  空闲期补 Retrain: 0
```

**空闲时守卫一次都不用动手。** 它只在有配置空间访问/GPU 活动时被触发。

而每次 `nvidia-smi`（会读配置空间）都会触发 1 次 SPEED 回压 + 2 次补 Retrain。
说明 **配置空间访问会引发一次链路速率重估**。

## 5. ★★ 修正：「主机宕机」是误判 —— 实际是 S3 自动睡眠

### 5.0 我当时怎么判断的（错的）

```
ssh: connect to host 〈实验机IP〉 port 22: No route to host
ping: Destination Host Unreachable（100% loss），持续 2 分钟以上
```

我据此写成"整机失联，需物理重启"，并推测是守卫在 DMA 中反复重训打挂了 PCIe 树。

### 5.1 实际情况（2026-10-29 06:30 复查，证据确凿）

```
系统引导 2026-10-29 01:05
boot 0: 01:05:22 ~ 06:30:58        ← 同一 boot，5.5 小时，从未重启

01:20:29  systemd-logind[1018]: The system will suspend now!
01:20:29  systemd-sleep[5936]: Performing sleep operation 'suspend'...
06:21:24  systemd-sleep[5936]: System returned from sleep operation 'suspend'.
```

**机器在 01:20:29 就进入了 S3 深睡眠**，而我从 01:32 开始探测、一路报 "No route to host"。
S3 睡眠会让网卡断电、网络完全消失，**现象与宕机一模一样，但机器完好无损。**

唤醒后设备状态完全正常：

```
power_state = D0
配置空间 0x00 = 1b8710de     ← 正常应答
LNKSTA = 1041, LCAP2 = 0x0002 ← 回到冷态
nvidia-smi 正常
```

### 5.2 结论修正

| 项 | 原结论 | 修正后 |
|---|---|---|
| 机器是否挂 | 整机锁死，需物理重启 | **没有挂，S3 睡眠了 5 小时** |
| 是否守卫打挂 PCIe 树 | 最可能原因 | **无证据，撤回** |
| 设备是否受损 | 不明 | **完好，唤醒后即正常** |
| 谁触发的 | 我推测是守卫 | **`systemd-logind` 的 idle 自动休眠** |

**⇒ 「不要在 DMA 中重训」这条建议仍然保留（保守是对的），但它不再是"有事故支撑的结论"，
只是基于机理的谨慎。** 后续若再遇到真实故障，需要重新取证。

### 5.3 新增强制纪律：实验前必须禁用自动睡眠

```
systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
# 恢复：systemctl unmask ...
```

否则长跑实验会被 idle 休眠打断，而且**表现为"机器失联"，极易误判为实验打挂了硬件**。
本次已对 union 执行 mask。

### 5.4 方法论教训（比事故本身更重要）

> **"网络不可达" 不能直接推断为 "机器宕机"。**

区分手段（按可靠性）：
1. `uptime` / `who -b` —— 若 uptime 远超"失联时长"，说明没重启
2. `journalctl --list-boots` —— 看是否新增 boot（重启会新增）
3. `journalctl -b | grep "PM: suspend"` —— 直接看有没有睡眠记录

**这三条 30 秒就能查清，我却在「宕机」这个错误前提上做了 5 小时的分析。**

### 5.5 附带发现：S3 会把设备打回冷态

S3 睡眠前设备处于某个状态，唤醒后 `LCAP2=0x0002`（未解锁）、`LNKSTA=1041`（Gen1）。
⇒ **S3/唤醒等价于一次"软冷启动"，我们推上去的 Gen2 会丢失，需要重新执行配方。**
这对工程部署有影响：笔记本/会休眠的机器上，需要唤醒后钩子。
