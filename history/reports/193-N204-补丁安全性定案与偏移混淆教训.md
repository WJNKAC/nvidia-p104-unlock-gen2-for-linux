# N204 — 补丁安全性定案 + 三种偏移的混淆教训

**日期**：2026-10-29 08:25
**目的**：验证 `or eax,0x80000` 那处补丁的**安全性边界**（会不会误伤别的寄存器）
**结论**：**安全。该分支只有 1 个入口、1 个出口，落点只写 `0x8C040`。**
但过程中我两次混淆了"文件偏移 / .text 内偏移"，必须固化下来。

---

## 0. 定案：补丁影响范围

```
.text+0x126c87  cmp  edx,0x1          ; edx = 当前 LNKSTA.sp
.text+0x126c8a  je   0x127000         ; ★ 唯一入口（已扫描确认，只有这 1 处跳向它）
.text+0x127000  or   eax,0x80000      ; ★ SPEED=2 → Pascal 2.5GT/s
.text+0x127005  mov  r8d,eax
.text+0x127008  jmp  0x126ca1         ; ★ 唯一出口（已扫描确认，只有这 1 处跳向它）
.text+0x126ca1  mov  rdi,r13
.text+0x126ca4  xor  r9d,r9d
.text+0x126ca7  mov  ecx,0x8c040      ; ★ 只写这一个寄存器
.text+0x126cac  xor  edx,edx
.text+0x126cae  xor  esi,esi
.text+0x126cb0  call <write>
.text+0x126cb5  pop  rbx              ; 直接返回
```

**两个"唯一"是安全性依据**（都用相对跳转全量扫描验证过）：

| 检查 | 结果 |
|---|---|
| 跳向 `0x127000` 的指令 | **1 处**（`0x126c8a` 的 `je`） |
| 跳向 `0x126ca1` 的指令 | **1 处**（`0x127008` 的 `jmp`） |

⇒ 改 `0x127000+3` 那个字节，**只影响"当前 sp==1 时写 SPEED 请求"这一条路径**，
不涉及任何其它寄存器（落点处 `ecx` 被硬编码为 `0x8C040`）。

## 1. ★ 我两次犯的偏移混淆（必须记住）

### 1.1 三种偏移，差 0x40

| 名称 | 定义 | 用途 |
|---|---|---|
| **文件偏移** | 从文件开头算 | `patch_*.py` 直接读写文件时用 |
| **`.text` 内偏移** | 从 `.text` 起点算 | `objdump --start-address` 用 |
| **运行时地址** | `.text` 基址 + `.text` 内偏移 | kprobe / perf / 断点用 |

`.text` 的 `sh_offset = 0x40`，所以：

```
文件偏移 = .text 内偏移 + 0x40
```

### 1.2 我的两次错误

**错误 1**：拿 `nv-kernel.o_binary` 的 `.text` 内偏移（`0x105d42`）去查
`nvidia.ko` 的 `.text`（`/tmp/nvtext.bin`）→ 反汇编出一堆 `endbr64; mov eax,0x56; ret` 桩。

原因：**两个文件 `.text` 布局完全不同**：

| 文件 | 大小 | `.text` 大小 |
|---|---|---|
| `nvidia.ko` | 157,271,160 | **15,333,236** |
| `nv-kernel.o_binary` | 112,677,456 | **15,198,308** |

**错误 2**：拿文件偏移 `0x127040` 去查 `.text` 提取（`/tmp/nvtext.bin`），
看到的是 `mov esi,0xb10000`（日志代码）——因为实际 `.text` 内偏移应为 `0x127000`。

**当时我差点据此得出"`0x127040` 不是 SPEED 写入点"的错误结论。**

### 1.3 固化：`tools/resolve_speedlock.py`

一次输出三种偏移 + 交叉校验 + 用**正确偏移**反汇编验证：

```
签名 anchor      file=0x126cc7   .text+0x126c87
★ 目标指令       file=0x127040   .text+0x127000
运行时地址       0xffffffffc1cb1000   （基址 0xffffffffc1b8a000 + 0x127000）

该处字节（file 0x127040）: 0d 00 00 08 00 41 89 c0 e9 94 fc ff ff
  ✓ = or eax,0x80000 ; mov r8d,eax ; jmp rel32

反汇编验证（--start-address 用 .text 内偏移 0x127000）:
 ★127000:  0d 00 00 08 00     or   eax,0x80000
   127005:  41 89 c0          mov  r8d,eax
   127008:  e9 94 fc ff ff    jmp  0x126ca1
```

## 2. 补丁的实际效果（预期）

### 2.1 修改内容

```
file 0x127043:  0x08 → 0x04
指令:  or eax,0x80000  →  or eax,0x40000
Pascal 编码: SPEED=2 (2.5GT/s)  →  SPEED=1 (5.0GT/s)
```

### 2.2 行为变化

| 场景 | 打补丁前 | 打补丁后 |
|---|---|---|
| 链路当前是 Gen1（sp==1） | 速率请求写成 **2（继续 Gen1）** | 速率请求写成 **1（请求 Gen2）** |
| 结果 | **永久锁死 Gen1** | 配合 `LCAP2=0x06` 解锁，链路有机会自己爬到 Gen2 |

**这是"解除自我强化锁定环"的最小改动**，不需要 kprobe、不需要常驻守卫。

### 2.3 前提条件（缺一不可）

1. **声明必须已解锁**（`LCAP2=0x06`）。否则速率请求 5GT 也会被硬件拒绝。
   ⇒ 仍需用 `safe-gen2.py` 的 ① 解锁声明部分，或用 `gen2kr` 的 push 逻辑。
2. 驱动重载后补丁才生效（`.ko` 是加载时映射的）。

## 3. 仍需验证的事（设备 C. ZOMBIE，需重启）

### 3.1 这个分支真的会被执行吗？

**这是最大的不确定点。** 该函数是"链路异常恢复"，正常时不跑。
而且两个入口都只有单一来源，说明它由某个上层判断驱动。

验证方法（重启后）：

```bash
ADDR=$(sudo grep -w _nv017281rm /proc/kallsyms | cut -d' ' -f1 | head -1)
sudo perf record -e mem:0x$ADDR:x -a --intr-regs=cx,r8,dx -o /tmp/f.data \
  -- sh -c 'for i in 1 2 3; do bwtest2 64 3; sleep 1; done'
sudo perf script -i /tmp/f.data -F comm,ip,iregs | head -20
```

- **有命中** ⇒ 分支会跑，patch 有意义
- **无命中** ⇒ 需要先人为制造一次"Gen2 → Gen1 掉速"再测

### 3.2 patch 后能否自愈

```bash
sudo python3 tools/resolve_speedlock.py      # 先看三种偏移对不对
sudo python3 tools/patch_speed_lock.py apply # 打补丁
modprobe -r nvidia_drm nvidia_modeset nvidia_uvm nvidia; modprobe nvidia
sudo python3 safe-gen2.py                    # 解锁声明 + 推 Gen2
bwtest2 128 7                                 # 测带宽
```

**判据**：跑 CUDA 掉速后，链路能否**自己回到 Gen2**（不再需要 `gen2kr` 守卫）。
若成立，就可以把 `gen2kr` 从"常驻守卫"降级为"只在开机时推一次"。
