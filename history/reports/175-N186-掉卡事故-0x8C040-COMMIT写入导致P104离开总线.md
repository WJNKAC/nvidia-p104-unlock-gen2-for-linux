# N186 — 掉卡事故：`0x8C040` COMMIT 写入导致 P104 离开 PCIe 总线

**日期**：2026-10-28 23:54
**对象**：P104-100（10de:1b87），root port `00:01.0`，驱动 580.178.04，内核 6.1.0-50-amd64
**脚本**：`/data/labs/nvidia/pcie-gen2/gen2-recipe.py`
**日志**：`/data/labs/nvidia/pcie-gen2/log-recipe-20261028-235445.log`
**结论一句话**：第 1 步最后那条 `0x8C040` 的 COMMIT 写，是本次掉卡的**直接原因**；
掉卡后**次级总线复位也救不回来，必须断电重启**。

## 1. 关键读数解读

### 1.1 起点状态

| 寄存器 | 值 | 含义 |
|---|---|---|
| `0x8841C` `CONFIG` | `0xc0b40500` | bit15=0 → 复位前置位没置，声明不会被锁存 |
| `0x8C040` `LINK_CONFIG_0` | `0x20085800` | `SPEED[19:18]=2` → 2.5 GT/s（Pascal 反直觉编码） |
| `0x880A4` `LINK_CAP2` | `0x0002` | 只声明 2.5 GT/s，**不声明 5.0 GT/s** ← 受限点 |
| `0x88088` `LNKSTA` | `0x1041` | Gen1 x4 |
| 根端口 `LNKCTL2` | `0x0043` | TLS=3（10 GT/s 目标），根端口本身没被限制 |
| 根端口 `LNKSTA` | `0x5041` | Gen1 x4，DLL Active |

**注意根端口 TLS=3**：根端口目标是 Gen3，它一直在等端点来提高速率；
端点是 Gen1-only 声明，所以双方稳定在 Gen1。这说明**瓶颈完全在端点侧声明**。

### 1.2 `0x8C040` 读回 `0xffffffff` 是什么意思

写之前能正常读到 `0x20085800`；写完 COMMIT 立刻读回 `0xffffffff`。

- `0xffffffff` 是 PCIe 目标设备不应答时的标准返回值（UR/CA 后主控填全 1）
- **这说明 COMMIT 写下去的瞬间，BAR0 MMIO 就不再应答了**
- 也就是说：**设备在"第 1 步"就已经受伤了**，只是配置空间还活着，
  所以 `step1()` 末尾的 `alive()`（走 `lspci`）仍然返回 True，骗过了流程检查
- 紧接着 `remove` + `rescan` 就是压死骆驼的最后一根稻草

**教训**：`alive()` 用 `lspci` 判断"活着"是不够的 —— 配置空间能读 ≠ MMIO 能应答。
以后必须补一条 **BAR0 自杀探针**：写完高危寄存器后立刻回读一个已知无害的常量寄存器
（比如 `0x8841C` 或 `0x880A4`），读回 `0xffffffff` 就立即中止，绝不进入第 2 步。

## 2. 参考项目自己就撞过这堵墙

`ref/p104-gen2-unlock/docs/03-走过的弯路.md:126`：

> 对含 COMMIT / 使能 / 复位语义的寄存器做**逐位写走查** | 本卡实测：对 `0x8C040` 逐位走查 → **显卡掉下 PCIe 总线**，只能重启 | 本项目自身事故

`ref/p104-gen2-unlock/docs/04-硬件事实表.md:302` 重复了同一条。

⇒ **这不是我们姿势不对，是这张卡对 `0x8C040` 的写操作本身就有掉卡风险。**
参考项目（Windows）能稳定跑通，说明 Windows 上有一条我们没复刻到的"兜底"：

`研究过程记录.md` 里提到的 **`Gen2PnpFallback`（v3.1.1+，默认开）**：

> 失败保底：**不依赖 Stage2** —— Stage1 重训失败即自动
> **禁用→启用 40HX（DEV_1F0B）** 完整重载 nvlddmkm
> （驱动重读 `RMPcieLinkSpeed` 等策略 + **整卡复位**）再解锁一轮

以及 README 里的原话：

> **"破解第一次失败，再破解一次就可以了"**

⇒ **Windows 上第一次写 COMMIT 之后掉链路是"预期内"的**，靠 PnP 禁用→启用把卡完整复位拉回来。
Linux 的 `remove`/`rescan` 是**纯软件重新枚举**，没有"给卡断电再上电"这一步，
所以拉不回来。

**这就是我们和参考项目最本质的分歧点**：不是寄存器配方不同，而是
**「掉链路之后的恢复手段」在 Linux 上缺一层。**

## 3. 复现条件对比：这次和上次成功差在哪

| 环节 | 上次成功 | 本次 |
|---|---|---|
| 第 1 步 `0x8C040` COMMIT | 同样写了 | 同样写了 |
| `0x8C040` 回读 | 未记录 | `0xffffffff` |
| 第 2 步 remove 前 | **驱动还绑着** | **先 unbind 再 remove**（为绕 D3cold） |
| remove 后 rescan | 设备回来，`LCAP2=0x06` | 设备再也没回来 |

唯一差异是 **remove 前多了一次 unbind**。

但要注意：unbind 是在第 1 步**之后**才做的，而 `0x8C040` 的 `0xffffffff` 回读发生在
unbind **之前**。所以 **unbind 不是掉卡原因**，它最多只是让恢复更难
（驱动 `remove()` 回调里可能本来有把设备拉回 D0 / 清 LTSSM 的动作，被我们提前用掉了）。

**待验证假设 H1**：`unbind` 触发的驱动 `remove()` 回调把设备放进了 D3hot，
之后再 `remove` + `rescan`，端点从 D3hot 冷启动失败 → 不应答配置读。

**待验证假设 H2**：COMMIT 让端点进入 Recovery，此时被拔掉，LTSSM 卡死在 Recovery/Configuration。

## 4. 下一步（重启后的 V2 方案）

### 4.1 先补安全网（无副作用，先做）

1. `alive()` 升级为 **`mmio_alive()`**：回读 `0x880A4`（LINK_CAP2，稳定常量 `0x0002`），
   读回 `0xffffffff` 立即 `sys.exit(1)`，禁止继续第 2 步。
2. 第 1 步拆成 **1a / 1b** 两段，`0x8C040` COMMIT 单独作为 1b，可开关：
   `python3 gen2-recipe.py --no-commit` 跳过。
3. 每条危险写之前把当前状态 dump 到 `/data/labs/nvidia/pcie-gen2/state-<ts>.json`，
   掉卡后还能事后复盘。

### 4.2 实验矩阵（按风险从低到高，逐格做）

| 组 | 第 1 步 | 第 2 步 | 目的 |
|---|---|---|---|
| **A** | **完全跳过 `0x8C040`**，其余照写 | unbind → remove → rescan | 验证「声明锁存只靠重新枚举」，根本不需要 COMMIT |
| B | 跳过 `0x8C040` | 直接 remove（不 unbind）→ rescan | 与上次成功路径对齐，验证 unbind 是否有害 |
| C | 全写，但 `0x8C040` **只写 SPEED 不写 COMMIT** | unbind → remove → rescan | 分离"改 SPEED 字段"与"发 COMMIT 触发重训" |
| D | 全写 | 先 remove/rescan 拿到 `LCAP2=0x06`，**再**写 COMMIT | 声明已解锁后再请求 5.0 GT/s，此时根端口 TLS=3 能接纳，理论上最安全 |

**A 组优先**：如果 A 就能把 `LCAP2` 从 `0x02` 推到 `0x06`，
那 COMMIT 这一步可以从配方里彻底删掉，掉卡风险归零，整个方案难度大降。

### 4.3 恢复手段先备好

掉卡后首选：**断电重启**（`echo b > /proc/sysrq-trigger` 不行，要真断电重训链路）。
软件层抢救顺序（都试过，本次全失败，但保留作为标准流程）：
1. `rescan`
2. 根端口 `BRIDGE_CONTROL` 次级总线复位
3. 根端口 `LINKCTL` bit5 Retrain
4. 保留 `00:01.0` 的 `remove` + 上层的 `rescan`
5. 断电重启

## 6. 结论

1. **`0x8C040` 的 COMMIT 写会掉卡**，这是本卡已知事故（参考项目也记录过）。
2. 掉卡判据：`0x8C040` 回读 `0xffffffff` → 端点 MMIO 已死；此后 `lspci` 仍能看到设备，
   **不能作为"活着"的证据**。
3. 掉卡后**软件手段全部无效**，只能断电重启。
4. **下一次必须从 A 组开始**：先证明"不需要 COMMIT"，再谈提速。
