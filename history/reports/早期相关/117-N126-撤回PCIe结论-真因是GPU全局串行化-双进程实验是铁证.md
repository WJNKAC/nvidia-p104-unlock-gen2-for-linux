## 1. 决定性实验：双进程并发

**如果 121 µs 是"每个 context 自己的开销"，两个进程应该各跑各的（总吞吐翻倍）。
如果它是"GPU 上的全局串行资源"，两个进程会互相排队（总吞吐不变）。**

### 1.1 结果

| 模式 | 单进程 | 双进程（每个） | **双进程总吞吐** | 变化 |
|---|---|---|---|---|
| **M3 交替（有同步）** | **24.93 fps** | 12.89 fps | **25.78 fps** | **1.03 ×** |
| **M1 只 draw（无同步）** | 194.98 fps | 195.13 fps | **390.26 fps** | **2.00 ×** |

### 1.2 判读

**M1：两个进程各自跑 195 fps，总吞吐正好翻倍 ⇒ 完全并行，互不影响。**
**M3：两个进程各掉到 12.89 fps，总吞吐 25.78 ≈ 单进程 24.93 ⇒ 完全串行。**

**⇒ GPU 上有一个全局资源，每 121 µs 只能被一个 context 用一次。**
**⇒ 这个成本与"有几个 context"无关 —— 加到第二个 context，两个都变慢一半。**

### 1.3 ★ 并发数扫描 1/2/4：总吞吐恒定

```
1 进程: 每个 36.25 fps  总吞吐 36.25 fps  总速率 7,250 对/秒
2 进程: 每个 17.91 fps  总吞吐 35.82 fps  总速率 7,164 对/秒
4 进程: 每个  9.66 fps  总吞吐 38.64 fps  总速率 7,728 对/秒
```

**每个进程的 fps 精确按 1/N 分配**（36.25 → 17.91 ≈ /2 → 9.66 ≈ /4），
**总吞吐恒定在 7,164 ~ 7,728 对/秒（波动 ±4%）。**

**⇒ 这是"单一全局资源"的教科书级签名。**
**⇒ 若是每 context 独立开销，加进程应线性加速；若是带宽/算力，总吞吐会随负载变化。**
**⇒ 实际是"完全按时间片均分"⇒ GPU 上同一时刻只能有一个 context 处于那个动作里。**

### 1.4 三种算法交叉验证

```
单进程 M3:  24.93 fps × 300 对/帧 = 7,479 对/秒
双进程 M3:  12.89 × 2 × 300      = 7,734 对/秒
1 / 121 µs                        = 8,264 对/秒
```

**三者落在 7.5k~8.3k 对/秒的同一区间。**

**⇒ GPU 的"状态变更 + draw"处理速率被钉在约 8 k 对/秒，无论多少进程。**

## 2. 这解释了 515 和 vGPU

| 环境 | 每对 | 双进程会怎样（预测） | 机制 |
|---|---|---|---|
| **525 物理机** | **121 µs** | 总额不变（已实测） | 每对触发一次 **GPU 全局串行化动作** |
| **515 物理机** | **0.03 µs** | 应该翻倍（未测） | **不做这个动作** |
| **525 vGPU** | ~0.2 µs（相当于 130+ fps 档） | 应该翻倍（未测） | **动作被虚拟化，不需要碰物理 GPU 的全局状态** |

### 2.1 为什么 515 不受影响

**这个动作是 525 引入的软件行为，不是硬件必然。** 515 的 glcore 发完命令就走，从不要求 GPU 做全局同步。

**⇒ PCIe 慢不慢与它无关** —— 515 即使 PCIe 再慢 10 倍，也不会有 121 µs，因为它压根不做那 125 次访问。

### 2.2 为什么 vGPU 不受影响（回答用户第二个质疑）

**关键：宿主确实要驱动物理 GPU、确实要过 PCIe，但宿主不需要"为 guest 的每一次状态变更做一次物理 GPU 的全局上下文切换"。**

```
物理机 525：
  app 每对 → 驱动要求 GPU 做全局同步 → 物理 GPU 真的串行化 → 121 µs

vGPU 525：
  guest 每对 → 请求"全局同步"（发给虚拟设备）
              → 宿主收到后，可以在自己的队列里合并/延后，
                不需要为此打断物理 GPU 当前的工作
              → guest 立刻拿到"完成"（因为它等的是宿主内存里那个标志，不是物理 ctxsw）
```

**⇒ vGPU 的"全局同步"是**虚拟的**：guest 以为自己独占 GPU 并完成了同步，
而物理 GPU 那边由宿主统一调度（多个 guest 的提交可以交错/合并）。**

**这正好和"宿主没有造假完成"不矛盾**：中断是真的（报告 115 的 MSI-X 直通），
但**"状态变更后必须做一次全局串行化"这个语义被宿主吸收了**。

## 3. 这个"全局串行化动作"是什么（推测，但约束很强）

**已知（硬）：**

| 观测 | 数据 |
|---|---|
| 每对成本 | 121 µs（≈ 231k 周期 @1911 MHz） |
| **与进程数无关** | 双进程总吞吐 1.03×（**全局资源**） |
| 与像素无关 | 506 倍像素只 +8% |
| 与 quad 面积几乎无关 | 200 倍面积只 +15% |
| 与状态类型无关 | program 123.4 / FBO 123.5 / texture 126.0 µs |
| 功耗 | 利用率 0→100%，但功耗只 +1.68 W |
| uniform 免费 | 4.5 µs（≈ 纯 draw） |
| 批量只收 1 次 | M9：1000 次切换 + 1000 draw = 1 次 |

**六条约束里，唯一能同时满足"全局 + 定长 + 低功耗 + 与内容无关"的是：**
**GPU 侧的 context switch / 全局状态同步（PGRAPH 的 ctxsw 或 channel 抢占）。**

- Pascal 的 context switch 典型耗时就是**几十万周期**量级（231k 完全在范围内）
- ctxsw 是**全局资源**（同一时刻 GPU 只能在一个 context 上跑）→ 解释双进程串行
- ctxsw 在保存/恢复寄存器，**不是算力活** → 解释 +1.68 W
- 与像素/几何无关 → 解释尺寸无关性
- uniform 不改变 context 内容 → 解释免费
- 批量变更只触发一次 → 解释 M9

**这是目前唯一能同时解释全部六条约束的候选。**

## 4. 为什么 525 会每对做一次 ctxsw（推测）

**最可能：525 引入了"保守的独占保护"** ——
物理直通时，驱动必须保证"只有我在用这张卡"，所以每次状态变更后主动做一次 context 隔离/同步，
避免与其他客户端（CUDA、其他 GL context、X server）的残留状态冲突。

**515 没有这个保守行为**（更快但理论上更容易被别的客户端干扰）。
**vGPU 不需要它**（Host RM 独占物理 GPU，guest 的状态是虚拟的，由 Host 保证隔离）。

**⇒ "515 快"和"vGPU 快"是同一件事的两面：都不做那个保守的全局同步。**
