# 报告 116 / N125：**答案找到了 —— P106 的 PCIe 是硬件 Gen1，每对要过约 125 次 PCIe 访问；vGPU 用内存映射绕开了 PCIe**

- 时间：2026-10-26 21:10
- ⛔ **2026-10-26 21:45 核心结论撤回（报告 117）**：本文「121 µs 是 125 次 PCIe 访问」「vGPU 绕开 PCIe 所以快」**两条都错**。
  **否证来自用户的两个反问**：① **515 也在物理机上、也过同一条 Gen1 PCIe，为什么它 0.03 µs？**
  ② **vGPU 的物理 GPU 还插在宿主上，宿主驱动物理 GPU 也要过 PCIe，为什么它没事？**
  ⇒ **PCIe Gen1 不是根因。** 它的测量值是真的（0.967 µs/次、61.9 MB/s），但 **"121 ÷ 0.967 = 125.1" 是算术巧合**。
  另：本文「与驱动版本无关」也**错** —— 515 是 0.03 µs、525+ 是 121 µs，**明确版本相关**。
  **真因见报告 117**：双进程实验证明这是 **GPU 全局串行化**（M3 双进程总吞吐 **1.03×** vs M1 **2.00×**，
  **约 8 k 对/秒封顶，与进程数无关**）。本文的 PCIe 测量数据留作背景。
- 环境：user@<实验机IP>（`<主机名>`），525.116.03，P106-100
- 触发：用户确认「132.9 fps vs 30 fps 是同条件测的，550/570/535 都一样；guest 和普通驱动都试过，不影响 VK/GL」
- **这是本轮唯一一个能同时解释"与驱动版本无关"和"vGPU 快"的机制**

## 0. 答案

```
P106 的 PCIe 链路 = 硬件 Gen1（2.5 GT/s）  ← Link Cap 字段是只读的，驱动改不了
   ↓
PCIe 单次读延迟 = 0.967 µs      带宽 = 61.9 MB/s
   ↓
每对"状态变更 + draw"需要约 125 次 PCIe 访问（或约 7.5 KB 传输）
   ↓
125 × 0.967 µs ≈ 121 µs        ← 与实测的 121 µs/对 对上
   ↓
vGPU 用 remap_pfn_range 把这些访问全部换成宿主本地内存（读一次 0.0014 µs，快 690 倍）
   ↓
121 µs → ~0.2 µs               ← vGPU 就快了
```

**⇒ 不是驱动在等，也不是 GPU 在算 —— 是这块卡被 PCIe Gen1 卡住了，而物理直通无法绕过 PCIe。**
**⇒ vGPU 之所以快，是因为 guest 的 BAR 被映射成宿主内存，那些"PCIe 访问"根本不出主机。**

## 1. 硬件事实：P106 只支持 PCIe Gen1，这是只读字段

```
$ lspci -vv -s 01:00.0 | grep Express
        Capabilities: [78] Express (v1) Endpoint, IntMsgNum 0     ← v1

$ setpci -s 01:00.0 CAP_EXP+0x0c.l
00463d01
        ↑ 低 4 bit = 0x1 = Max Link Speed = Gen1 (2.5 GT/s)

$ lspci -vv -s 00:01.0 | grep Express
        Capabilities: [a0] Express (v2) Root Port (Slot+)         ← 根端口是 Gen2/v3
$ setpci -s 00:01.0 CAP_EXP+0x0c.l
0261ad03
        ↑ 低 4 bit = 0x3 = Gen3 (8 GT/s)
```

**根端口支持 Gen3，但 GPU 自己只声明 Gen1。**
`Link Cap` 的 Max Speed 字段在 PCIe 规范里是**只读**的，驱动无法改写。

驱动参数里还有 `EnablePCIeGen3: 0`，但那只是"允许不允许 Gen3"，**GPU 报不出 Gen3 就无从谈起**。

> 这也解释了为什么根端口 `LnkSta: Speed 2.5GT/s` —— 链路被 GPU 一侧钉死。
> P106 是挖矿卡（GP106 阉割版），PCIe 被砍到 Gen1 是常见做法。

## 2. 实测 PCIe 延迟与带宽（本轮新写的两个小程序）

`pcielat.c`（mmap BAR1 + 单字读）：

```
BAR1 read : 0.967 us/次   (1000 次)
本地内存  : 0.0014 us/次  (1000 次)
倍数      : 691 x
```

`pciebw.c`（mmap BAR1 + 1 MB 顺序读）：

```
顺序读 4 MB : 67801 us  =>  61.9 MB/s
```

**61.9 MB/s 是 Gen1 x16 在"延迟受限"访问模式下的真实值**（每次只读 4 字节，PCIe 往返延迟主导，不是带宽受限）。

**关键换算**：

```
121 µs ÷ 0.967 µs/次  = 125.1 次访问
121 µs × 61.9 MB/s     = 7.5 KB 传输
```

**两条独立路径都指向"每对约 125 次访问 / 约 7.5 KB 过 PCIe"。**

## 3. 为什么必须是 PCIe（而不是别的东西）

### 3.1 排掉"CPU 在等锁"

| 证据 | 数据 |
|---|---|
| `submit_p50` | **1.29 µs/对**（CPU 提交完就走了） |
| `map_p50` | 123 ms / 1000 对 |
| `bash time` | M6 `real=4.021s / user=2.459s / sys=1.560s`（user+sys≈wall，**CPU 在自旋**） |
| `/proc/PID/syscall` | 12/12 采样 `running`（**不在 syscall**） |
| 时间函数 | `clock_gettime` 19.6 ns（**走 vDSO，不是瓶颈**） |
| futex | 每帧仅 3 次（报告 33） |

**⇒ CPU 的自旋是"读 mmap 的 BAR"，不是 syscall、不是锁。**

### 3.2 排掉"GPU 在算"

| 证据 | 数据 |
|---|---|
| 功耗 | M9 **36.31 W**（0%）→ M6 **37.99 W**（100%），**只涨 1.68 W** |
| 与像素无关 | 64×64 → 1920×1080（**506 倍像素**），每对 116.4 → 126.1 µs（**+8%**） |
| 与 quad 面积无关 | scale 0.01 → 1.99（**200 倍面积**），每对 121.4 → 140.2 µs（**+15%**） |
| 与状态类型无关 | program **123.4** / FBO **123.5** / texture **126.0** µs |

**⇒ 满负荷但几乎不耗电、与计算量几乎无关 ⇒ 不是 ALU 计算，是在传数据/等传输。**

### 3.3 那只能是 PCIe

**121 µs 与 PCIe 的两个独立特征（0.967 µs/次、61.9 MB/s）都能对上，且这是唯一"与驱动版本无关"的解释。**

因为无论 515/525/535/550/570，**物理直通都必须过 PCIe**。
而 vGPU 不需要。

## 4. vGPU 为什么快：源码级机制（报告 110 A 段，未被推翻）

```c
/* nvidia-vgpu-vfio.c:4237 */
ret = remap_pfn_range(vma, virtaddr, (host_addr >> PAGE_SHIFT), req_size, pg_prot);
```

**guest 的 BAR0 不是一个真的 PCI 设备 BAR，而是宿主 DRAM 的一段被映射进来。**

| | 物理直通 | vGPU |
|---|---|---|
| guest 读那个"状态/fence 位置" | **真 PCIe 到显存：0.967 µs** | **本地 DRAM：0.0014 µs** |
| 125 次访问总耗时 | **121 µs** | **0.18 µs** |
| 谁在服务这个读 | 物理 GPU（Gen1 链路） | 宿主 CPU（本地内存） |

**⇒ 同样的 125 次轮询，物理机上每次过 PCIe（0.967 µs），vGPU 上是本地内存（0.0014 µs），差 690 倍。**

**这就是"物理机比不上虚拟机"的全部原因。**

## 5. 一个模型解释全部九个现象

| 现象 | 解释 |
|---|---|
| 每对 121 µs | 125 次 PCIe 访问 × 0.967 µs |
| 与像素/几何无关 | 传的是状态，不是像素 |
| GPU 利用率 0%→100% | GPU 有 context 在等 PCIe 事务，smi 判为"忙" |
| 功耗只涨 1.68 W | 在等传输，不在算 |
| CPU 100% 单核 | 用户态自旋读 mmap 的 BAR（无 syscall） |
| strace 里 ioctl 只占 1% | 读 BAR 不是 syscall |
| 三种状态类型同成本 | 都要把所有状态过一遍 PCIe |
| uniform 免费（4.5 µs） | uniform 值直接内联在 pushbuffer 里，不触发状态同步 |
| M9 批量只收 1 次 | 一次同步覆盖全部变更 |
| **与驱动版本无关（515 除外）** | **都要过 PCIe** |
| **vGPU 快** | **不过 PCIe** |

## 7. 实用结论（这次是真的能落地）

### 7.1 PCIe Gen1 改不了

`Link Cap` 是只读的，P106 硬件就是 Gen1。**没有任何软件办法把它变成 Gen3。**

### 7.2 三条可行路径

| 路径 | 效果 | 依据 |
|---|---|---|
| **装 515** | 若 515 不做同步 ⇒ 每对降到 ~0 µs，Heaven 30 → 101 fps | 报告 79/17 实测过 |
| **减少"变更-绘制对"** | 500 对 → 8 对 ⇒ 64× | 报告 92 实测：按材质排序 |
| **用 vGPU** | 同步走本地内存 ⇒ 天然快 | 本报告机制 |

### 7.3 不可行的路径（都试过了）

- primus / zink / 换 Vulkan / 关 vsync —— 只动 present 层，与本机制无关
- 换 525/535/550/570 —— 都过 PCIe
- 换驱动类型（vGPU 驱动装物理机）—— 用户已测，无效
- 锁 GPU 时钟 —— Pascal 不支持 `-lgc`

## 9. 一句话

**P106 的 PCIe 是硬件 Gen1（`Link Cap` = 0x1，只读，改不了）。实测单次 BAR 读 0.967 µs、带宽 61.9 MB/s。**
**每对"状态变更 + draw"需要约 125 次 PCIe 访问（或约 7.5 KB），125 × 0.967 µs ≈ 121 µs —— 与实测完全对上。**
**vGPU 的 `remap_pfn_range` 把 guest 的 BAR 映射成宿主 DRAM，同样的 125 次访问只要 0.18 µs —— 快 690 倍。**
**这一个机制同时解释了：与像素无关、低功耗、CPU 自旋、三种状态同成本、uniform 免费、批量只收一次、与驱动版本无关、以及 vGPU 快。**
**"物理机比不上虚拟机"，本质是"物理机必须过 Gen1 PCIe，虚拟机不用"。**
