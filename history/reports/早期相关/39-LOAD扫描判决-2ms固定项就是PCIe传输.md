# 39 · LOAD 扫描判决：那个"2ms 固定项"不是定时器，是 PCIe 传输本身

> ⚠️ **2026-10-26 00:05 更正（报告 40）**：本报告的 §5「物理尺」判据**用错了对象**。
> 守恒律 `map = max(0, T_land − sleep)` 说明 **map 是"补等余额"，不是传输时长**；
> 只有在 **`sleep = 0`** 时 `map` 才等于 `T_land`（本报告的 N12 分辨率扫描正好是 sleep=0，所以那部分拟合仍然有效）。
> 因此本报告判"515 的 map=1070µs 需 7.75GB/s → 物理不可能"是**错的**：
> 那 1070µs 是 `sleep=9.63ms` 之后的余额，`T_land = 10.7ms`（775 MB/s），完全合理。
> 复核实验见报告 40：**sleep=9630µs 时 map 只有 4.4µs**。
> **正确的横向比较量是 `T_land = sleep + map`**：隔离 2.62ms（1.0× 下限）/ 515 10.1ms（3.8×）/ 525 29.4ms（11.2×）。
> 本报告的 §1–§4（LOAD 不抬 min、守恒律、拟合 3.15GB/s）**全部有效**；§5/§6 的推论按报告 40 改写。

> 2026-10-25 23:30
> 用户方案：在 525 上做 rb_lat5 细粒度 LOAD 扫描（0/10/20/30/50/100），看 map_time 从哪个负载开始跳到 2ms。
> 预注册判读表：
> - LOAD=0 时 map≈0.2ms、LOAD=10 跳到 ~2ms → 固定项"有活就出现"，指向拷贝排队
> - map 随 LOAD 线性增长、固定项始终 ≈2ms → 纯定时，指向 1ms tick
> - 固定项只在 LOAD≥100 才出现 → 队列积压到阈值才触发
>
> **结果：三行全部不成立，因为前提就不成立——LOAD=0 时 map 已经是 2.75ms。**
> 而真正的答案比"定时器/排队"都简单：**这 2.65ms 是这块卡把一帧 1080p 搬过 PCIe 的物理时间。**
> 我另加了一个决定性实验（sleep 扫描）把它钉死成一条守恒律。

## 3. ★ 决定性实验：sleep 扫描 = 一条守恒律

`do_readback` 的序列是 `glReadPixels → [可选 usleep] → glMapBuffer`。
如果 map 的耗时就是"等 PBO 拷贝落地"，那**把 usleep 加大，map 应当等量减少**。

1920×1080、LOAD=0、mode A，扫 `RL5_SLEEP`：

| SLEEP (µs) | map_min | map_p50 | map_p90 | **map + sleep** | D_p50 (ms) |
|---|---|---|---|---|---|
| 0 | 2476.9 | **2750.7** | 2786.6 | **2750.7** | 2.751 |
| 300 | 2105.3 | 2376.7 | 2399.0 | 2676.7 | 2.755 |
| 600 | 1801.0 | 2069.0 | 2092.8 | 2669.0 | 2.753 |
| 1000 | 1400.8 | 1667.7 | 1681.7 | 2667.7 | 2.752 |
| 1500 | 892.6 | 1155.9 | 1184.5 | 2655.9 | 2.747 |
| 2000 | 407.3 | 668.3 | 683.7 | 2668.3 | 2.752 |
| 2500 | 1.5 | **131.0** | 187.1 | 2631.0 | 2.738 |
| 3000 | 0.8 | **1.6** | 7.0 | — | 3.085 |
| 4000 | 1.4 | **2.7** | 7.3 | — | 4.089 |

**`map + sleep` 在 sleep 0→2500 区间恒定在 2668µs（波动 ±1.4%）。**

这只能有一种解释：

```
map_time = max(0, T_land − sleep)        T_land ≈ 2.67 ms
```

`T_land` 是 PBO 拷贝真正落地（主机内存可见）的时刻。
**map 不是一个"开销"，它是"等拷贝的余额"。** 到 SLEEP=3000 时拷贝早已落地，map 掉到 **1.6µs**（几乎为零）。

**2.67ms 对应 8.29 MB → 3.10 GB/s，与下面 §4 的独立拟合（3.15 GB/s）一致。**

## 4. 分辨率扫描：下限随字节数走，不是随"活"走

同一程序、LOAD=0、mode A，改分辨率（每次 5000 或时间封顶）：

| 分辨率 | Mpx | 帧字节 | map_min | map_p50 | 拟合预测 | 残差 |
|---|---|---|---|---|---|---|
| 640×360 | 0.230 | 0.92 MB | 0.4 | **403.2** | 383.2 | +5.0% |
| 960×540 | 0.518 | 2.07 MB | 624.0 | **749.8** | 748.6 | +0.2% |
| 1280×720 | 0.922 | 3.69 MB | 1104.2 | **1229.8** | 1263.4 | −2.7% |
| 1920×1080 | 2.074 | 8.29 MB | 2476.6 | **2737.5** | 2725.1 | +0.5% |

```
map_p50 = 91 µs + 317.8 µs/MB × bytes      R² = 0.9995
        = 91 µs + (3.15 GB/s 的传输时间)
```

**截距只有 91µs**——所谓"2ms 固定项"里，**91µs 才是真正的固定开销，其余 2.63ms 全是按字节收费的传输**。

一块 1080p 帧 8.29MB，在 Gen1 x16 上就是 2.6ms。这不是能"优化"的东西。

### 4.1 而且链路提不上去

```
pcie.link.gen.current = 1
pcie.link.gen.max     = 1     ← ★ 上限就是 1
pcie.link.width.current = 16 / max 16
```

**`gen.max = 1`**：不是"降速了所以是 Gen1"，而是**这张卡在这个槽位上最高只能 Gen1 x16**。
→ 3.15 GB/s 是硬天花板，`nvidia-smi -lgc` 之类的手段也改不了。

## 5. ★ 由此得到一把"物理尺"，顺手发现一处锚点风险

`map ≥ 317.8 µs/MB` 在本机是**物理约束**。任何低于它的 map 读数，都只可能有两种解释：
(a) 测的不是这么大的一帧；(b) **map 没有等传输完成就返回了**。

拿这把尺去量既有数据：

| 既有结论 | 换算 | 与物理尺比较 | 判断 |
|---|---|---|---|
| 报告 29：**515 的 map = 1070µs** | 若真是 1080p：8.29MB/1.07ms = **7.75 GB/s** | **超过 Gen1 x16 上限 2.4 倍** | ⚠️ **两者必有一错**：要么当时不是 1080p，要么 515 的 map 不等传输 |
| 报告 26：525 的 map = 2862µs | 8.29MB/2.86ms = 2.90 GB/s | 略低于上限 | ✅ 合理（还含排队） |
| 本次 525：2750µs | 3.01 GB/s | 接近上限 | ✅ |

**推导（重要）**：primus 的 autosleep 稳态是 `usleep = 9 × map`，故 `D = 10 × map`。
- 若 map 有 PCIe 下限 2.65ms → 在 1080p 下 **D ≥ 26.5ms → fps ≤ 37**。
- 而 515 实测 **108fps（帧 9.2ms）**。
- → **在 1080p 下，515 不可能每帧都真搬 8.29MB 并等它落地。**

**所以 515 与 525 的差别，不是"同样搬 8.29MB 但 515 搬得更快"（物理上不可能），
而是"515 没有在 map 里等这次传输"。**

这条把一个原本模糊的对比（1070 对 2750µs）变成了一个**必须二选一的判决**，
而且两条分支都指向具体下一步（见 §7）。

> ⚠️ 报告 29 的这个数必须按**同分辨率**重测才算锚点。按 README 的铁律，
> 跨版本对比必须同一探针、同一脚本、同一参数；分辨率没对齐的倍数不能进结论。

## 6. 对"解决 525"的直接含义

### 6.1 好消息：map 确实是最该动的杠杆

`D = 10 × map`（autosleep 9× 放大）。所以在 1080p：
- map 2.75ms → D 27.5ms → **36 fps**
- map 2.20ms → D 22.0ms → **45 fps**
- map 1.50ms → D 15.0ms → **67 fps**

**map 每降 0.5ms，帧率涨约 9fps。** 这是全链条里放大倍数最大的一个环节——
比报告 37/38 查的"等待机制"（只值 15%）有效得多。

### 6.2 坏消息：光电传输搬不动

下限 2.65ms 由 Gen1 x16 决定。要真正降 map，只有三类办法：

| 办法 | 可行性 | 说明 |
|---|---|---|
| **少搬字节**（降分辨率 / 只搬所需区域） | 高，但改变画面 | 报告 27 已量化：像素 1/9 → D 降 31%（非等比，因为下限抬着） |
| **让拷贝早落地**（不被后续渲染排在后头） | 中 | §2 的 LOAD 数据说明：并发 GPU 工作会把 map 从 2.75 抬到 5.09ms。**反过来，若能提高拷贝优先级，map 可以稳定贴到 2.65ms 下限** |
| **map 不等传输**（515 的做法，见 §5） | 待验证 | 若成立，这是唯一能突破 2.65ms 的路径；需要先做 §7 的对照 |

### 6.3 与既有结论的关系

- **与报告 38 相容**：38 说"一帧 = 1 次真等 20ms + 若干空转"。现在知道那 20ms 的真等，
  在 primus 里就是 `usleep = 9 × map`；map 越大，等的越久。**两者是同一件事的两端。**
- **与报告 37 相容**：37 说改等待策略只值 15%——因为等待策略不改 map，而 map 才是放大器输入端。
- **与报告 31 相容**：Heaven 下 GPU 48~68W ≈ 空转。因为大部分时间在做 PCIe 传输 + 睡，不是在算。

### 8.1 两个操作教训

1. **`iters=400` 会先于 `RL5_SEC` 封顶**：冒烟测试里 n=400、只跑了 1.1s，等于采样窗口没对齐。
   → 必须**迭代数给大（5000）+ 时间封顶**，各组窗口才一致。
2. **`/tmp` 在本机与另一台机器不是同一视图**：`cat > /tmp/x.sh` 后远端 `bash /tmp/x.sh` 报"没有那个文件"。
   → 脚本必须写到共享路径（`/data/...`），或直接 `bash -c` 传内容。

### 8.2 一个待解释的观察（本轮没结论）

`LOAD=100` 时**每轮迭代时间几乎等于 map 时间**（5.13ms 中 5.08 是 map，render+wait ≈ 0.05ms）。
即 100 个全屏 quad（≈103 Mpx 混合填充）在 `glWaitSync` 之后**没有表现为等待时间**。
两种可能：(a) 填充与拷贝并发，被 map 的等待期间吸收了；(b) `glWaitSync` 未按预期串行化。
**这需要单独验（加 `glFinish` 对照）**，但它不影响 §1–§5 的任何结论——
因为下限（min）在所有 LOAD 下都不动，那才是被解释的量。
