## 1. 先否证 pinned 假设

**假设**：我的 `wbtest.c` 用普通 `malloc`（pageable），H2D 会走驱动 bounce buffer，
上限恰好 0.7–0.8 GB/s —— 所以测到的 0.778 可能根本不是 PCIe 带宽。

**实测**（新工具 `bwtest2.c`，同时测 pageable 和 pinned）：

```
buffer=256 MB  iter=7        （Gen1 x4 基线）
  pageable   H2D med 0.777  max 0.779   D2H med 0.853  max 0.853  GB/s
  pinned     H2D med 0.779  max 0.780   D2H med 0.855  max 0.855  GB/s
```

**两者几乎完全一致 ⇒ 假设否证。**

在 Gen1 x4 这种低带宽链路上，瓶颈就是链路本身，pinned 帮不上忙。
（pinned 的意义在于高带宽链路，比如 Gen3 x16，pageable 会因为 bounce 掉到一半。）

**结论：0.778 GB/s 确实是真的 Gen1 x4 带宽，之前的测量是有效的。**
`bwtest2` 保留下来，因为它同时给出两种模式的对照，比单测一种更有说服力。

## 2. 参考项目的 Linux 版脚本：不完整，不能用来解决问题

`linux/p104-gen2-linux.sh` 的核心只有一行：

```bash
NEW=$(( (0x$CTL2 & ~0xF) | TARGET_SPEED ))    # LINKCTL2[3:0] = 2
wr_w 0x30 "$NEWHEX"
```

**它完全不碰 BAR0 的 `0x8C040`。** `oneclick.sh` 里搜 `8C040|BAR0|COMMIT|/dev/mem` —— **0 条命中**。

我们已经反复证明 `0x8C040.SPEED[19:18]` 才是真正的速率请求开关：
- `retrain-only.py`：声明 `LCAP2=0x06` + 两端 TLS=2 + 根端口重训 6 轮 → **升不到 Gen2**
- 一旦写 `0x8C040.SPEED=1` → **当场/一轮重训就上 Gen2**

⇒ **这个 Linux 脚本在不改 SPEED 的前提下不可能成功。** 它自己的 README 也写明
"⚠️ 尚未在 Linux 实机验证，属于社区测试版"。

它唯一有价值的提示在"待确认"一节：

> · NVIDIA 闭源驱动是否会在驱动重置后把目标速率写回 Gen1（需要实测）

**这正是我们反复观察到的现象。** 参考项目作者自己也没解决这个问题。

## 3. COMMIT 在 unbind 状态下也必死 —— 彻底否证

之前一直有个侥幸：所有写 COMMIT 的事故都发生在驱动绑着的时候，
也许 unbind 之后写就安全（因为 unbind 下写 SPEED 是安全的）。

**`commit-unbind.py` 实测：**

```
=== C1: unbind → 解锁声明 → 写 SPEED=1 + COMMIT ===
  unbind 成功
  bound = False
  解锁: 0x8841C=0xc0b4ad00 LCAP2=0x0006
  ★ 写 0x8C040: 0x20085800 → 0x20045801（SPEED=1 + COMMIT）
  !! 写完 COMMIT 端点死了 —— unbind 也救不了，COMMIT 确认是毒药
```

**COMMIT 的毒性跟驱动无关，跟状态无关。在任何情况下写都死。**

对比之下，同一个脚本里写 `SPEED=1` 而不带 COMMIT，在 unbind 状态下从未死过。

### 为什么参考项目写 COMMIT 却不死？

唯一合理解释：**Windows 的 `DICS_DISABLE` 让 GPU 真的断了电**，重新上电后 GPU 处于
完整的初始化流程中，此时写 COMMIT 是"在干净的状态机上推进"，而我们在**运行中的状态机**
里塞复位信号 → LTSSM 死锁。

⇒ **真断电是写 COMMIT 的前提，而我们做不到真断电。**

## 4. Linux 无法让 GPU 真断电（两条新路径也失败）

之前测过四个"复位"方法（reports/179），寄存器全部逐字节不变。本轮又补测两条
专门针对 D3cold 的路径：

### 路径 A：unbind → `power/control=auto` → 等运行时挂起

```
  unbind 后 bound=False
  [1s] runtime=suspended power=D0
  ...（10 秒都是 runtime=suspended，power=D0）
  唤醒：control=on
  [唤醒后] config=0xc0b4ad00 lnkcfg0=0x20085800     ← 逐字节不变
```

`runtime_status` 变成 `suspended` 了，但 **`power_state` 一直是 D0**，
**没有进 D3cold，寄存器一个都没变**。

⇒ `runtime suspended` ≠ 真断电。设备只是进了 D3hot 或更浅的状态。

### 路径 B：驱动绑着直接 `remove`（强制 D3cold）→ rescan → bind

```
  remove 返回值=0
  已离开总线
  rescan …
  枚举回来（0.5s）
  [rescan 后] power=D0                              ← 没有 D3cold
             config=0xc0b4ad00 lnkcfg0=0x20085800
  bind 返回值=1 err=echo: I/O error                  ← 已在 rescan 时自动绑上
  smi: GPU 0: NVIDIA P104-100                        ← 驱动正常
```

这次连 D3cold 都没出现（`power=D0`），寄存器基本不变（`0x8841C` 的 bit13 被驱动清掉了，
但 `0x8C040` 完全没动）。

⇒ **`remove` 不 unbind 也不会强制 D3cold。** 之前遇到 D3cold 是特定条件下的副产物，
不是稳定可控的手段。

### 汇总：六种方法全部不能真断电

| 方法 | 结果 |
|---|---|
| `enable=0/1` | `echo 0 > enable` 报 I/O error |
| `power/control` + runtime PM | `runtime=suspended` 但 `power=D0`，寄存器不变 |
| `setpci` PMCSR → D3hot | 写入成功但寄存器不变 |
| `remove/rescan` | 寄存器不变 |
| `remove` 不 unbind（强制 D3cold） | `power=D0`，寄存器不变 |
| `unbind → auto → 唤醒` | `power=D0`，寄存器不变 |

**Linux 上让 GPU 真断电的唯一方式是关机（冷启动）。**

## 5. 完整因果链（这条链现在每一环都有实测支撑）

```
① GPU 硬件默认只声明 Gen1
      冷启动 LCAP2 = 0x0002，LNKSTA = 0x1041              【实测，数十次】

② 要让它声明 Gen2，必须让 GPU 重新 POST
      Windows 靠 PnP disable（真断电）→ enable            【参考项目文档】
      Linux 六种方法全部失败，无法真断电                    【本轮+上轮实测】

③ 我们只能手写 0x8841C 去改"声明镜像"
      LCAP2 0x02 → 0x06 当场生效（安全）                  【实测，多次】

④ 但镜像 ≠ 硬件状态
      链路层能协商 5GT/s（两端 LNKSTA sp=2）              【实测】
      GPU 内部数据面（MPSS / VC credits / Replay buffer）
      仍按 Gen1 配置                                       【推断，但有强证据】

⑤ 结果：真实 TLP 一来就崩
      Xid 79 GPU has fallen off the bus                    【实测，dmesg】
      零 AER 错误（无 Correctable/Bad TLP/Bad DLLP）        【实测】
      ⇒ 不是信号质量问题，是协议层状态不一致

⑥ 唯一可能修复②的手段是 COMMIT 位（让 GPU 自己重训并同步数据面）
      任何状态下写入都必死                                  【本次实测，unbind 也死】
      因为前提是"GPU 处于干净初始化流程"，而我们做不到

⑦ 驱动的 probe 会 reset GPU，把手写的状态打回 Gen1
      bind 后 LNKSTA 回到 0x1041，0x8C040 回到 SPEED=2     【实测】
```

**⇒ 在"不能真断电"这个约束下，P104 在这台机器上无法达成可用的 Gen2。**

## 6. 但有一个值得再确认的疑点

参考项目声称在**同型号卡**上跑到 1.55 GB/s。他们的条件：
- Windows
- PnP 真断电复位
- 其后再也没停过按住循环（每 20 ms 重写全部寄存器，含 COMMIT）

他们能承受每 20 ms 写一次 COMMIT 而不死，说明**在真断电+重新初始化之后，
COMMIT 是安全的**。这反过来说明"真断电"确实是关键前提。

**下一步唯一有意义的验证**：找一个能让 GPU 断电的机会 —— 即**冷启动后的第一次操作**。
但我们已经做过无数次冷启动了，每次 `LCAP2` 都是 `0x02`、链路都是 Gen1。

除非…… 在冷启动的**极早期**（BIOS POST 阶段之后、驱动加载之前）就介入。
但这需要从 initramfs 阶段执行，工程复杂度高，而且驱动加载时仍会 reset。

**所以我的判断是：这条路在当前平台上走不通，建议转向。**

## 7. 建议的三条路

### A. 换插槽 / 换转接卡再试一次（成本最低，能区分责任）
参考项目在同一型号卡上成功，差异可能来自：
- 插槽电气（是否 x4 直连，是否经过桥片）
- 转接卡/延长线的信号质量（虽然我们无 AER，但仍可能影响训练稳定性）
- 主板 BIOS 对 PCIe 速率的处理

**如果换直插 x16 槽后 `LCAP2` 冷启动就是 `0x06`**，那说明问题在插槽/BIOS，
不是卡；那这条路立刻通了。

### B. 接受 Gen1 x4 封顶，把精力转回 P106 每批延迟课题
P106 那条线已经有确定成果（52.2 ms → 3.67 ms），且是**可交付的方案**。
P104 这条线的剩余价值不确定。

### C. 如果一定要 P104 高带宽，考虑放弃 PCIe 路线
P104 的瓶颈是 Gen1 x4 = 0.78 GB/s（H2D）。如果任务能改成"数据留在显存内计算"，
PCIe 带宽就不是瓶颈。
