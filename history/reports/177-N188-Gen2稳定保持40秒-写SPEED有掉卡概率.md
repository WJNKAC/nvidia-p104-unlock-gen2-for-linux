## 1. E 组：完整成功日志

```
[起点] CAP2=0x00000002  LNKSTA=0x1041  cfg=0xc0b40500  lnkcfg0=0x20085800
       根端口 LNKSTA=0x5041  TLS2=0x0043
[Gen1 基线] 带宽: H2D 0.774 GB/s | D2H 0.851 GB/s     ← 与参考项目 0.78/0.85 完全吻合

第1步：四个 XP3G + 0x8841C(置15/13/11) + 0x88610 + 0x8872C=6
      安全网：LINK_CAP2 = 0x0006 ✓        ← 声明当场解锁
      0x8C040 —— 跳过（latespeed）

第2步：unbind → remove → rescan → 0.5 s 回来，power=D0
第2.5步：LCAP2=0x06 已锁存 → 现在写 SPEED
      [late] 0x8C040 = 0x20085800 → 0x20045800  回读 0x20045800  CAP2=0x0006
              （第 1 次读到有效值）              ← 没掉卡！

第3步：端点 LNKCTL2 本来就是 0x10002（TLS=2）
      根端口 0x0043 → 0x0042
      第1轮: 端点 LNKSTA=0x1042 sp=2 | 根端口=0xd042    ← 一轮就上 Gen2

第4步：按住 60 s，每 20 ms
      n=100 … n=1700，全部 sp=2 | 根端口 sp=2 | 驱动回压=0
      结束: 端点 LNKSTA=0x1042 sp=2
```

### 1.1 三条被实测否定的参考项目结论

| 参考项目说 | 我们的实测 |
|---|---|
| "必须靠 COMMIT 才能提速" | ❌ **不需要**。只写 SPEED，硬件自己重训 |
| "复位后要等 25 秒声明才锁存" | ❌ **4 秒内就锁存**（第 1 步做完时就已经是 `0x06`） |
| "停止按住就掉回 Gen1，必须常驻" | ⚠️ **在 Linux 上不成立**：按住 60 s 期间驱动回压 **0 次**，`lnkcfg0` 一直是 `0x20045800`。580.178.04 根本不写这个寄存器 |

⇒ **Linux 上不需要"按住"这个机制。** 这是本次最有价值的收获之一：
省掉常驻进程、省掉看门狗、省掉开机自启。

### 1.2 与参考项目的判据完全对齐

- Gen1 x4 ≈ 0.78 GB/s → 我们测到 **0.774 / 0.851**（H2D/D2H）
- 参考项目 Gen2 x4 ≈ 1.55 GB/s（本轮没测到，因为驱动没起来）

## 2. F 组：同样的路径，写 SPEED 时掉卡

```
[起点] CAP2=0x00000002  LNKSTA=0x1041  cfg=0xc0b40500     ← 与 E 组完全相同
第1步后 CAP2=0x06  cfg=0xc0b4ad00                          ← 与 E 组完全相同
第2步 unbind/remove/rescan → 0.5 s 回来，D0                ← 与 E 组完全相同
[锁存后] CAP2=0x06 LNKSTA=0x1041 cfg=0xc0b4ad00            ← 与 E 组完全相同
第2.5步 [late] !! 写 SPEED 后 1 秒内 BAR0 一直 0xffffffff —— 端点已死
```

**每一个前置状态都逐字节相同，结果却相反。** 这只能是
`0x8C040` 写入 → 请求 5 GT/s → LTSSM 重训 这条硬件路径本身有**概率性失败**。

参考项目自己也记过这个风险（`04-硬件事实表.md:302`）：

> 对 `0x8C040` 逐位写走查 → **显卡掉下 PCIe 总线，只能重启**

他们能承受，是因为 Windows 的 disable/enable 会**真的给卡断电**，一次 PnP 就拉回来；
Linux 的 `remove`/`rescan` 只是软件重枚举，**不给卡断电**，所以掉了只能物理重启。

### 2.1 推测的改进方向（V3 要试）

掉卡的直接触发是"端点请求 5 GT/s，但链路训练没成功"。
而**写 SPEED 时根端口 TLS 还是 3（Gen3）**：

```
根端口 LNKCTL2 = 0x0043   → TLS=3（10 GT/s 目标）
端点请求        = 5 GT/s
```

两端目标不一致 → 训练过程要协商降速 → 协商失败就卡死。

**V3 改法：写 SPEED 之前，先把根端口 TLS 也设成 2**，让两端一开始就同目标。
参考源码的顺序是 `WriteSpeedGen2` 在前、`WriteTlsBoth` 在后 ——
那是因为 Windows 上 PnP 复位会清干净状态。Linux 上顺序应该反过来。

## 3. 驱动共存：Linux 特有的新错误码

E 组最后重载驱动失败：

```
NVRM: GPU 0000:01:00.0: RmInitAdapter failed! (0x25:0xf:1636)
NVRM: rm_init_adapter failed, device minor number 0
```

之后设备彻底掉线，链路回到 `0xd041`，再 `modprobe` 又变回老熟人：

```
NVRM: RmInitAdapter failed! (0x22:0x56:897)
```

### 3.1 这个错误的归属已经能确定了

| 现象 | 判断 |
|---|---|
| Windows 上 Gen2 + 驱动完全正常（带宽 1.55 GB/s） | Gen2 本身**不是**驱动不兼容的原因 |
| 我们 `rmmod` → `modprobe` 后失败 | **重载**这个动作有问题，不是 Gen2 有问题 |
| 失败后设备从总线消失 | RM 初始化失败 → 设备掉线，**RM 是"凶手"而非"受害者"** |
| 957/897 静态查不到 | 闭源 RM 内部数值，OKM 头文件只到 `0x10008` |

⇒ **897/1636 很可能不是"Gen2 校验失败"，而是"设备已经半死时 RM 初始化超时"的通用错误。**

### 3.2 本轮犯的错（必须纠正）

E 组第 4 步结束时，**驱动是绑定的、链路是 Gen2** —— 这是唯一一次"可能共存"的机会。
我却直接 `rmmod nvidia_drm nvidia_modeset nvidia_uvm nvidia` + `modprobe nvidia`，
把它重载了。于是：

- 从没测过 `nvidia-smi` 在 Gen2 下是否正常
- 从没测过 Gen2 的真带宽
- 反而引入了一个新的失败模式（重载时的 1636）

**脚本已改：结束时先测活着的那份驱动，`rmmod`/`modprobe` 改成 `--reload` 显式开关。**

## 6. V3 结果：根端口 TLS 不是原因

V3 在写 SPEED **之前**先把根端口 `LNKCTL2` 从 `0x0043`(TLS=3) 改成 `0x0042`(TLS=2)，
让两端一开始就同目标。结果：

```
根端口 TLS2 = 0x0043 → 0x0042  （先让两端同目标，再请求速率）
[late] !! 写 SPEED 后 1 秒内 BAR0 一直 0xffffffff —— 端点已死
```

⇒ **根端口 TLS 不是掉卡原因。** 假设否证。

## 7. 重新比对三组的起点，找到真正的差异

| 实验 | 起点 `cfg`(`0x8841C`) | 是否已含 bit15+bit11 | 写 SPEED 结果 |
|---|---|---|---|
| **E（成功）** | **`0xc0b48d00`** | **✅ 都有** | ✅ Gen2 |
| F（失败） | `0xc0b40500` | ❌ 都没有 | ☠ 掉卡 |
| V3（失败） | `0xc0b40500` | ❌ 都没有 | ☠ 掉卡 |

**E 组是唯一一次「脚本还没跑，驱动就已经把 bit15 和 bit11 置好了」的情况。**

这与源码注释完全对上（`P104Gen2x4.cs:434-448`）：

> bit15 决定复位后声明能否锁存；
> 旧代码只「读旧值再 OR」**碰巧保留**它 → 表现为**时好时坏**：
> 上一次成功过 → bit15 残留 1 → 这次也成功；
> 刚开机/驱动刚重置 → bit15 = 0 → 这次失败。

我们第 1 步**显式置了** bit15（`(1<<15)`），所以脚本跑完都是 `0xc0b4ad00`。
但 E 组起点就是 `0xc0b48d00` —— 说明**驱动在我们介入之前，已经完成了一轮
「按 RmForceEnableGen2 策略置位 + 链路协商」**。

**新假设 H3**：写 `SPEED=1` 是否掉卡，取决于端点 PCIe 核是否已经
**在 bit15/bit11 就位的前提下完成过一次链路协商**。
- E 组：驱动已协商过 → 写 SPEED 只是"改目标速率" → 安全
- F/V3：我们刚置位、设备还没重训过 → 写 SPEED 等于"在未初始化状态下强改速率" → LTSSM 死锁

**验证方法（零风险，纯观察）**：重启后不跑脚本，每 2 秒读一次 `0x8841C`，
看驱动是否/何时会把 bit15、bit11 置上。如果它会自己置，那就等它置完再操作。
