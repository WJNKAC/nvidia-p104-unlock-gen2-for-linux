# 200 / N211 — 部署特性：补丁能"保持"，但必须有人"建立"

日期：2026-10-29 10:15–10:30
设备：P104-100（10de:1b87），Debian 13 / kernel 6.12.113+deb13-amd64 / NVRM 580.178.04

---

## 0. 结论

**「直接安装打过补丁的驱动」不够用。**

补丁只做一件事：让 `_nv017105rm(mode=1)` 在入口 bail，**驱动不再把链路降回 Gen1**。
它**不负责**把链路升上去 —— 升上去需要另一套动作（解锁端点声明 + SPEED=1 + 重训），
而且必须在 `nv_pci_probe` 返回的窗口里做。

所以上电后必然经历：

```
开机 → probe（声明被重置为 Gen1）→ 链路 2.5GT/s
       ↑ 补丁让人在这里"不降"，但也没人"升"
     ~ 一直保持 Gen1，直到有人做推送 ~
       ↓
     gen2kr push → 声明 0x06 + SPEED=1 + Retrain → 5GT/s
       ↓
     补丁保证之后不再降级
```

**推论：gen2kr 的那次推送是不可省的。** 补丁 + gen2kr 是"保持"和"建立"两件事，缺一不可。

## 2. 为什么不能在开机前/开机后用用户态脚本补上

三条路都堵：

| 方案 | 为什么不行 |
|---|---|
| 驱动加载前用用户态脚本推 | probe 会把声明重置回 Gen1（reports/198 实测），推了白推 |
| 驱动加载后用用户态脚本推 | 需要抢 `nv_pci_probe` 返回的窗口；且**链路动态时用户态 mmap 写 BAR0 已 2/2 打挂设备**（reports/197） |
| 只改 registry / 只改声明 | 均无效（reports/198 §7：`RMPcieLinkSpeed` / `RMPcieStickyGenSpeed` 实测无效） |

⇒ 只能在**内核里**、在**probe 返回的那一刻**做。这就是 gen2kr 存在的理由。

## 3. 顺带查清：`unbind/bind` 不会重置声明

原本想用「摘掉 gen2kr + unbind/bind」来模拟"新鲜开机、只有补丁"，结果发现**测不出来**：

```
解绑后:  CAP2=0x0006 LNKSTA=2 TLS=2 SPEED=1 MAXSPD=2    ← 完全没变
绑定后:  CAP2=0x0006 LNKSTA=2 TLS=2 SPEED=1 MAXSPD=2    ← 还是没变
```

⇒ **声明解锁（`0x8841C` / `XP3G` / `LCAP2=0x06`）是跨 `unbind/bind` 保持的。**
只有**整机断电重启**或**重载 nvidia 模块**（`rmmod` + `modprobe`）才会重置回 Gen1。

这条很实用：
- 想快速回 Gen1 做测试，`rmmod nvidia && modprobe nvidia` 就够，不必重启
  （但注意：反复 reload 有进入"驱动侧锁死态"的风险，reports/198）
- 反之，`unbind/bind` 不能用来"复位到原厂状态"

## 4. 如果想要"开机全自动"（三个选项，按侵入性排序）

| 选项 | 做法 | 侵入性 | 说明 |
|---|---|---|---|
| **A. 手动**（当前状态） | 每次开机跑 `sudo bash bin/20-install.sh` | 无 | 幂等，约 6 秒。补丁已在 ko 里，只剩重载+推送 |
| **B. modprobe softdep + gen2kr 加 init 推送** | 给 gen2kr 加"init 时若设备已绑定就直接 push"；`/etc/modprobe.d/nvidia.conf` 写 `softdep nvidia post: gen2kr` | 低（一个配置文件，无 systemd 单元） | 需要改 gen2kr 代码，**未实现、未验证** |
| **C. systemd service** | 安装 `kmod/gen2kr.service` | 高 | 用户已明确不要 |

### 关于 B 的可行性（静态推理，未验证）
- nvidia 的 `pci_register_driver()` 在模块 init 里**同步**完成 probe
  ⇒ `modprobe nvidia` 返回时设备已绑定
- `softdep nvidia post: gen2kr` 会让 gen2kr 在 nvidia init 之后立即加载
  ⇒ 此时设备已绑定，init 里可以直接跑 `push_fn()`
- `push_fn` 用 `ioremap` + `msleep(50)`，在 process context（模块加载）里可以睡眠
  ⇒ 无需 workqueue，不会错过窗口

**但这是推理，不是实测。** 且 `push_fn` 目前只在 workqueue 里被调用过，
直接放进 `__init` 需要确认：① 加载时设备确实已绑定 ② 不会被 kretprobe 的
`triggered` 标志挡住 ③ 加载失败时不会留下半解锁状态。

## 5. 当前部署形态（明确记录）

| 项 | 现状 | 重启后 |
|---|---|---|
| 2 字节补丁 | 在 `/lib/modules/…/nvidia.ko` 里（`514de9d4…`），备份 `.orig_nogen1` | **保留** |
| `gen2kr.ko` | 手动 `insmod`，**未开机自启** | **丢失** |
| systemd service | **未安装**（`gen2kr.service` 只在 /data 里） | — |
| 链路 | Gen2 5GT/s，pinned 1.56/1.71 GB/s | **回到 Gen1 0.78** |

⇒ 每次重启后需要手动执行：

```bash
sudo bash /data/labs/nvidia/nvidia-p104-unlock-gen2-for-linux/bin/20-install.sh
```

（补丁已在，该命令会跳过 apply，只做重载 + 推送，约 6 秒。）

**这也是为什么"补丁会随驱动升级丢失"这句话只讲了一半** ——
补丁丢失的后果是"驱动会主动降级"；gen2kr 丢失的后果是"链路压根升不上去"。
后者更明显、更容易被发现（开机就是 0.78）。
