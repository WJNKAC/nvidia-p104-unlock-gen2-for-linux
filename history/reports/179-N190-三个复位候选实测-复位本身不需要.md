# N190 — 三个"复位候选"全部实测：没有一个能复位 PCIe 核，而复位本身根本不需要

**日期**：2026-10-29 00:4x
**对象**：P104-100（10de:1b87），root port `00:01.0`，580.178.04 / kernel 6.1.0-50-amd64
**背景**：用户提出三个候选替代 `remove/rescan`（因为 remove 会把设备留 D3cold）

---

## 0. 直接回答：三个候选的实际测试结果

| 候选 | 实测结果 | 能否替代 remove/rescan |
|---|---|---|
| **M1** `unbind → echo 0 > enable → echo 1 > enable → bind` | **`echo 0 > enable` 直接报"输入/输出错误"，内核拒绝** | ❌ 不可用 |
| **M2** `power/control` + runtime PM | `echo auto` 后 `runtime_status` 仍是 **`active`**（驱动不让挂起），寄存器无任何变化 | ❌ 无效 |
| **M3** `setpci` PMCSR → D3hot → D0 | **安全但零效果**：PMCSR 写入成功（`0x0008`→`0x000b`→`0x0008`），设备完好，但**所有寄存器逐字节不变** | ❌ 无效（不是复位） |
| **M4**（对照）`unbind → remove → rescan` | 设备离开/回来正常，**但寄存器也逐字节不变** | ✅ 可用，但它**也没有复位核** |

**核心发现：这四个方法没有一个真正复位了 PCIe 核。**

---

## 1. 判据：怎么知道"核有没有被复位"

用 BAR0 里两个**非默认值**当标记（`bar0peek.py`）：

```
硬件默认：0x8841C = 0xc0b40500      0x8C040 = 0x20085800   SPEED=2(Gen1)
我们改成：0x8841C = 0xc0b4ad00      0x8C040 = 0x20045800   SPEED=1(Gen2)
0x880A4 LINK_CAP2 默认 0x0002，解锁后 0x0006
```

如果某个操作真的让 PCIe 核重新初始化，这些运行期寄存器会回到默认值。

### M3（D3hot 循环）实测

```
[当前]    CONFIG=0xc0b48d00  VSEC=0x00000001  LTSSM=0x00000006
          LINKCFG0=0x20085800  LINKCAP2=0x00000006  WIDTH=0x00000404
[D3hot中] CONFIG=0xc0b48d00  VSEC=0x00000001  LTSSM=0x00000006
          LINKCFG0=0x20085800  LINKCAP2=0x00000006  WIDTH=0x00000404   ← 完全一样
[D0后]    CONFIG=0xc0b48d00  VSEC=0x00000001  LTSSM=0x00000006
          LINKCFG0=0x20085800  LINKCAP2=0x00000006  WIDTH=0x00000404   ← 完全一样
```

**D3hot 只是电源态标记，GPU 固件根本不把它当"重新初始化"信号。**
它甚至没让配置空间变得不可读（这一点和 Windows 的 `DICS_DISABLE` 不一样 ——
Windows 那个会让设备从 PnP 树里消失，是**总线级**的移除，不只是电源态）。

⇒ 用户的推测（D3hot ≈ DICS_DISABLE）**不成立**。两者不在一个层次上。

### M4（remove/rescan）实测

```
[remove后] MMIO 失效（0xffffffff）        ← 设备确实离开总线
[rescan后] CONFIG=0xc0b48d00  VSEC=0x00000001  LTSSM=0x00000006
           LINKCFG0=0x20085800  LINKCAP2=0x00000006  WIDTH=0x00000404
           power=D0  cfg=1b8710de
```

**寄存器回来了以后跟 remove 之前一模一样。** 所以 `remove/rescan` 也**没有**复位核 ——
它只是让 Linux 重新枚举一遍，把设备拉回 D0。

## 2. 由此推翻了参考项目最关键的一条论断

参考项目（P104-Gen2x4 v1.6）把"整卡复位（禁用→启用）"列为**决定成败的第 2 步**，
理由是"声明是 PCIe 核在设备初始化时算出来并锁存的，只有让设备真正离开总线再回来，
这个初始化才会重跑"。

**实测：不需要。** 只写 `0x8841C`(置15/13/11) + `0x88610`(清12,置0) + `0x8872C=6`，
`LINK_CAP2` **当场**从 `0x0002` 变成 `0x0006`，既不离开总线，也不等 25 秒。

原因：`LINK_CAP2` 只是 `0x8841C` 那几位配置的**镜像**，写进去就反映出来。
Windows 上他们必须做 PnP disable/enable，是因为 **Windows 驱动会把这几位压回去**，
必须抢在驱动卸载的窗口里写；而 Linux 580.178.04 不碰这些位。

⇒ **整个第 2 步在 Linux 上是多余的。**

## 3. 但 `0x8C040.SPEED` 是必需的（重要否证）

我曾设想：既然 PCIe 协商速率 = min(两端 LNKCAP 声明, 两端 TLS 目标)，
那只要声明是 Gen2 + 两端 TLS=2 + 从根端口发一次 Retrain，就该协商出 Gen2，
**完全绕开那个危险的 `0x8C040`**。

`retrain-only.py` 实测：

```
第1步 解锁声明：LCAP2 0x0002 → 0x0006 ✓
第2步 两端 TLS=2：端点 0x0002（本就 2），根端口 0x0043 → 0x0042 ✓
第3步 根端口 Retrain × 6 轮：
  [第1轮] 端点 sp=1 | 根端口 sp=1 | LCAP2=0x0006
  ...
  [第6轮] 端点 sp=1 | 根端口 sp=1 | LCAP2=0x0006
未能升到 Gen2
```

**纯标准 PCIe 手段做不到。`0x8C040.SPEED` 是必经之路，不是可选镜像。**

好消息：这一轮全程没有掉卡，设备完好 —— 说明"写 `0x8841C`/`0x88610`/`0x8872C` + 两端 TLS + 根端口重训"这四件事**都是安全的**。

## 4. 已确认可用的 Gen2 配方（历史上成功过两次）

### 4.1 `speed-once.py` + 手动根端口重训 —— 本次拿到 `lspci` 亲证

```
起点：CAP2=0x0006  0x8C040=0x20585800(SPEED=2)  端点TLS2=0x0002  根端口TLS2=0x0042  LNKSTA=0x1041
写入 0x8C040 = 0x20545800（SPEED=1，无 COMMIT）
  回读 0x8C040 = 0x20545800  CAP2 = 0x0006        ← 设备活着
结果: 端点 LNKSTA=0x1041 sp=1                     ← 但没重训，还是 Gen1
```

然后**单独一条命令**触发根端口重训：

```
setpci -s 00:01.0 CAP_EXP+0x10.w=0060   （bit5 Retrain Link）
端点: 1042     根端口: d042
lspci: LnkSta: Speed 5GT/s, Width x4      ← ★ 亲证 Gen2，驱动绑着、设备活着
```

**这是全程第一次在「驱动绑定 + 设备存活」的条件下用 `lspci` 亲自确认 `5GT/s x4`。**

### 4.2 两个致命操作（都必须避开）

| 操作 | 后果 |
|---|---|
| 写 `0x8C040.bit0`(**COMMIT**) | **必掉卡**，且会把已达成的 Gen2 打回 Gen1 |
| 写端点 `0x88088` 的 Retrain 位（`LNKCTL bit5`） | **打死端点**（`gen2-recipe.py` 的 step3、`hold.py` 都死在这） |
| **写完 SPEED 后毫秒级立刻重训** | **打死端点**（`hold.py` 事故） |
| 直接往 `0x8841C` 写绝对值 `0xC0B4AD00`（跳过 XP3G 前置） | **打死端点**（`test-reset-methods.py` v1 事故） |

### 4.3 时序要求（踩出来的）

- 写 SPEED 之后**至少等 0.8 秒**才重训；实测 0.8 s 不够，**十几秒的自然间隔才稳**
- 重训只从**根端口**发，绝不碰端点
- 每轮重训后 sleep ≥1 s 再读状态

## 5. 仍未解决的问题：Gen2 保持不住

`lspci` 确认 Gen2 之后，隔一条命令的时间（约 10–60 s）再读，链路已经回到 Gen1，
`0x8C040` 也回到 `0x20585800`(SPEED=2)。

**这是谁写的？** 目前证据指向驱动/GPU 固件在某个时机把 SPEED 重置回 2。
（不是每 20 ms 一次 —— 按住 60 s / 1700 次采样期间**一次回压都没抓到**，
所以它是**偶发**的，只在特定事件后发生。）

### 5.1 带宽对照（唯一可信判据）

| 链路 | H2D | D2H |
|---|---|---|
| Gen1 x4（实测多次） | **0.774 – 0.779 GB/s** | **0.851 – 0.854 GB/s** |
| Gen2 x4（参考项目） | ~1.55 GB/s | ~1.69 GB/s |
| **我们 Gen2 时测到的** | **0.779 GB/s** | **0.854 GB/s** |

⇒ **尽管 `lspci` 说 5GT/s，实际吞吐仍是 Gen1 水平。**
两种可能：
1. 测带宽时链路已经掉回 Gen1（时间差导致，最可能 —— 传输前采样就已经是 `1041`）
2. 链路名义 Gen2 但数据面没跟上

**必须在"确认 Gen2 的同一瞬间"开始传输**才能分辨。这是下一步的核心实验设计。

## 8. 一句话总结

> **复位这一步根本不需要，而且没有任何一种"复位"能真正复位 PCIe 核。**
> 真正需要的只有三条：声明位（安全）+ 根端口 TLS=2（安全）+ `0x8C040.SPEED=1`（唯一危险点）。
> 剩下的全部工作是「怎么在驱动重新把它写回 2 之前，把数据搬完」。
