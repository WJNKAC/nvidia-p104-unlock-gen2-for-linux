# N199 — 本轮定案：kprobe 方案证否、守卫两处缺陷修正、pinned 稳定 1.560

**日期**：2026-10-29 06:30–07:15
**起点**：上一轮遗留"守卫在 GPU 忙时跳过重训导致带宽掉一半"
**结果**：修了三处，pinned 稳定 **1.560 / 1.699 GB/s**；同时证否了一条看似优雅的路线。

## 0. 一句话总结

> **可用，但有一个必须知道的前提：链路需要约 10 秒才能从 Gen1 恢复到 Gen2。**
> 链路就绪时 pinned 稳定 **1.560 / 1.699 GB/s**；链路未就绪时是 0.78。
> 长任务会自动摊薄这个启动期，短任务（<10 s）可能全程都是 Gen1。

## 1. ★ 我犯的重大错误：kprobe 挂在 notrace 函数上

### 1.1 起因（看起来很有希望）

静态分析 + 重定位解析，精确定位了驱动的 BAR0 寄存器**写**封装：

```
.text+0x126c5d  call → _nv053907rm（.text+0x5ffda0）   读
.text+0x126cb0  call → _nv053912rm（.text+0x5ff6c0）   写
```

并用 kallsyms 核对地址完全吻合：

```
ffffffffc21896c0  _nv053912rm   ← .text 基址 0xffffffffc1b8a000 + 0x5ff6c0
ffffffffc2189da0  _nv053907rm   ← + 0x5ffda0
```

思路：kprobe 这个写函数，当 `offset==0x8C040` 且 `SPEED==2` 时改成 1。
一处拦截胜过 38 处补丁，看起来很优雅。

### 1.2 实际后果

```
gen2kp: 已卸载。总调用 926009787，拦截改写 925622205 次
```

模块存在约 10 分钟 ⇒ **≈154 万次/秒**，`load average` 从 ~1 涨到 **5.95**（4 核机）。

### 1.3 根因：`_nv053912rm` 是 `notrace` 函数

**bpftrace 一开始就拒绝挂载，并明确警告：**

```
WARNING: _nv053912rm is not traceable (either non-existing, inlined, or marked as "notrace")
cannot attach kprobe, Invalid argument
```

**而 `register_kprobe` 不检查这个属性** —— 它能返回 0（"成功"），
但在被标记 notrace 的函数上强制插桩会破坏其执行。

叠加第二个问题：该函数内部疑似"写 + 读回校验 + 重试"，
我把要写的值从 2 改成 1，它校验永远失败 ⇒ 无限重试。

**⇒ 这条路线不可行。`gen2kp.c` 已加醒目警告头，标注"已证否，勿用"。**

### 1.4 由此反证出的重要事实

用**完全不碰内核**的方式（mmap BAR0 高频采样）测驱动真实写频率：

```
空闲 2s:  采样 1,666,717 次,  0x8C040 变化 0 次
CUDA 8s:  采样 2,370,281 次,  0x8C040 变化 0 次
```

**⇒ 驱动在稳态下根本不写 `0x8C040`。** 那 9.26 亿次全是我造成的。

（注意：第二次"CUDA 8s 0 变化"是在链路已是 Gen1、SPEED 已是 2 的状态下测的，
所以"没变化"不等于"没写"——它写的是同样的值。这一点见 §2。）

## 2. 修正了两处守卫缺陷

### 2.1 缺陷一：GPU 忙时跳过重训 ⇒ 带宽掉一半

上一轮加了 `gpu_busy()` 门禁（因 reports/185 的"宕机"担心），
而那个"宕机"**已被证否**（是 S3 睡眠，reports/185 §5）。经实测：

| 设置 | pinned H2D |
|---|---|
| `allow_busy_retrain=0`（保守） | **0.777** |
| `allow_busy_retrain=1`（放开） | **1.564** |

⇒ 新增参数 `allow_busy_retrain`，**默认 1**。

### 2.2 缺陷二：重训缺了 `0x8872C = 6`

守卫原来只做"从根端口 Retrain"，实测重训 16 次，`LNKSTA` 始终 `1041`。

对照 `safe-gen2.py`（一次成功）才发现少了关键一步 —— 完整配方是**两步**：

```
第1步  写 0x8872C = 6     ← 触发 LTSSM 训练（异步）
第2步  等 ≥3s 后从根端口 Retrain
```

⇒ 守卫改成两阶段状态机（`retrain_stage` 0→1→0）。

### 2.3 缺陷三：按回 SPEED 后立即重训，时机太早

日志实证：

```
[3057] SPEED 按回 1（第 25 次）
[3058] 补 Retrain（LNKSTA=1041）   ← 不到 1 秒就重训，无效
```

这违反了我自己在 reports/186 写的铁律 #1（写完 SPEED 后必须等 ≥3 s 才能重训）。

⇒ 新增参数 `speed_settle_ms`（默认 3000），按回 SPEED 后强制等 3 s 才允许重训。

### 2.4 当前守卫参数

```
guard_period_ms     200     守卫周期
debounce_cnt        3       连续 3 次(0.6s)读到 Gen1 才动作
retrain_min_ms      2000    两次重训最小间隔
speed_settle_ms     3000    ★ 按回 SPEED 后等待
allow_busy_retrain  1       ★ GPU 忙时也重训
guard_enabled       1       总开关
guard_rounds        0       0=常驻
```

## 3. 最终实测结果

### 3.1 链路就绪时的长测试（512MB × 15）

```
测前链路: 1042（Gen2）
  pinned     H2D med 1.560  max 1.566    D2H med 1.699  max 1.709  GB/s
  pageable   H2D med 0.779  max 1.547    D2H med 1.696  max 1.705  GB/s
测后链路: 1041
Xid: 0
```

**pinned 稳定 1.560 / 1.699** —— 与 reports/184 的 1.565/1.709 一致，可复现。

### 3.2 但短测试（每轮新进程、间隔 5–6 s）全部是 0.78

```
[1] H2D=0.773  端点=1041
[2] H2D=0.773  端点=1041
...
[8] H2D=0.779  端点=1041
```

**这不是失败，是恢复周期问题**（见 §4）。

### 3.3 pageable 始终 0.78 是 CUDA 的固有行为

`pageable max 1.547` 说明链路中途确实到过 Gen2，但中位数被 bounce buffer 压在 0.78。
⇒ **真实应用必须用 pinned / `cudaMemcpyAsync`，否则吃不到这 2 倍。**

## 4. ★ 关键特性：恢复周期约 10 秒

### 4.1 因果链（本轮全部实测）

```
新的 CUDA 上下文初始化
    ↓ 驱动写 0x8C040.SPEED = 2（请求 Gen1）
链路立刻降速到 Gen1（LNKSTA 1042 → 1041）
    ↓
守卫发现（debounce 0.6s）
    ↓ 按回 SPEED = 1
    ↓ 等 speed_settle_ms = 3s
    ↓ 写 0x8872C = 6 触发训练
    ↓ 等 ≥2s（retrain_min_ms）
    ↓ 根端口 Retrain
链路恢复 Gen2
```

**整条链路约 6–10 秒。** 期间带宽是 Gen1，恢复后是 Gen2。

### 4.2 这解释了所有"时好时坏"的现象

| 场景 | 表现 |
|---|---|
| 链路已就绪 → 跑长任务 | 1.56（§3.1） |
| 每个进程都是新的、间隔 5–6 s | 0.78（§3.2，总赶上恢复中） |
| 长任务（reports/184 的 10 次迭代） | 1.56（后续迭代都在 Gen2） |

### 4.3 工程含义

**部署时必须在应用启动后等链路就绪，再开始计时/测量。**
或者：把首次 CUDA 初始化当作预热，之后的传输才是 Gen2。

这一步对短交互型负载不友好（每次新进程都要付 10 秒）。**需要如实告知。**

## 5. 一个反证成功的副产品

在错误拦截模块（gen2kp）生效期间：

```
pinned H2D 1.550  D2H 1.679  GB/s，测后端点 1042，Xid 0
```

**虽然实现方式错误，但它证明：只要 `SPEED` 持续为 1，链路在真实 DMA 期间也能保持 Gen2。**
这与 §3.1 结论一致，互相印证 "SPEED=1 是关键变量"。

## 6. 三条必须记住的教训

### 6.1 挂 kprobe 前必须验证可插桩性

```bash
bpftrace -e 'kprobe:<symbol> { }' -c true
```
报 `not traceable` 就**不要挂**。`register_kprobe` 返回 0 不代表安全。

### 6.2 插桩模块必须暴露计数，并设"异常即卸载"的红线

9.26 亿次 / 10 分钟 = 154 万次/秒。看到这种数字应当**先怀疑自己的探针**。
验证方法：卸载探针，用纯用户态方式（mmap 采样）测同样的量。

### 6.3 修改被拦截函数的参数，要先确认它内部有没有校验重试

有"写-读回-校验-重试"的函数，改参数会导致死循环。
这类只能靠"事后纠正"（post_handler / 外部按回），不能改参数。
