## 1. 静态对比：push 一次成功、guard 屡败，差在哪

`push_fn`（每次 probe 都成，104ms 内 `LNKSTA=1042`）vs 旧 `guard_fn`（连续 4 轮失败）：

| 步骤 | `push_fn` | 旧 `guard_fn` |
|---|---|---|
| 解锁声明 / 清 DIS_G2 | ✅ | ❌（首次已做） |
| SPEED=1 | ✅ | ✅ 每轮按回 |
| 写 `0x8872C=6` | ✅ | ✅ |
| **→ 根端口 Retrain 的间隔** | **`msleep(50)`** | **`retrain_min_ms=2000`** |
| 两端 TLS2=5GT | ✅ | ❌ |
| 根端口 Retrain | ✅ | ✅ |

**根因**：`retrain_min_ms` 的设计意图是"两次**完整尝试**之间的最小间隔"（防止疯狂重训），
却被同时用来卡 **stage0 → stage1** 的间隔。

### 顺带排除一个误判：TLS2 不是原因
降级后两端 TLS2 与 Gen2 时**完全一致**：

| | 端点 LNKCTL2 | 根端口 LNKCTL2 | LCAP2 | 0x8C040 |
|---|---|---|---|---|
| Gen2 | `0002` | `0042` | `0x0006` | SPEED=1 |
| 降级后 | `0002` | `0042` | `0x0006` | SPEED=1 |

⇒ 所有协商条件都满足却停在 Gen1，**必须显式重训**；guard 不重设 TLS 不是缺陷。

## 2. 代码改造（`gen2kr.c`）

1. 新增 `stage_gap_ms`（150），专管 stage0→stage1 间隔
2. 新增 `stage_start_jiffies` / `last_attempt_jiffies`
3. `retrain_stage == 1` 走独立分支：**跳过防抖与 `retrain_min_ms`**，只等 `stage_gap_ms`
4. 链路恢复（`!low`）时**同时重置 `retrain_stage = 0`**
   —— 否则下次掉速会直接跳到 stage1，跳过 stage0（旧代码隐患）
5. `speed_settle_ms` 3000 → 800（依据见 §3）

实测 stage 间隔 204ms（受 `guard_period_ms=200` 粒度限制）。

## 4. ★★★★★ 查明：用户态 mmap 写 `0x8C040` 会打死设备，内核 writel 不会

### 4.1 事故经过（同一脚本，两次）
`tools/probe-selfheal.sh` 两次把设备打成 **C. ZOMBIE**：

```
降级后: 0x8C040=0x20585800 SPEED=2  LNKSTA[3:0]=1     ← 读值完全正常
按回后: 0x8C040=0xffffffff SPEED=3                     ← 写完立刻失联
2.0s~12.0s: sp=15                                       ← 一直失联
```
`pci-state.sh` 判定 ZOMBIE；**`dmesg` 里没有任何 Xid**（硬件级静默失联）。
两次都需要整机重启（`reset_subordinate` 已证无效，reports/194）。

**注意：写入前读值是合法的 `0x20585800`（不是 ffffffff、bit0=0），校验通过，
说明"从垃圾值派生 COMMIT"（reports/196 的假设）**不是**这两次的原因** ——
写入值本身合法，仍然掉卡。

### 4.2 决定性对照
| 路径 | 场景 | 结果 |
|---|---|---|
| **用户态 mmap `/dev/mem`** 写 `0x8C040` | 链路刚降级（0.5s 内） | **2/2 掉卡** |
| **用户态 mmap** 写（驱动未加载，链路静止） | `early-gen2.py` | 多次成功 |
| **用户态 mmap** 写（`safe-gen2.py` 完整配方，等 ≥5s） | 链路稳定 | 多次成功 |
| **内核 `writel`**（gen2kr 守卫，ioremap） | 链路刚降级（≤200ms） | **几十次按回、几十分钟运行，0 掉卡** |

⇒ **不是"写 0x8C040 危险"，而是"在链路动态时用用户态 mmap 写"危险。**

### 4.3 可能机制（未验证，但工程结论已足够）
1. `writel()` 带写屏障（sfence），mmap 写没有
2. 用户态进程可能**在写入与后续动作之间被调度打断**，内核路径不会被抢占，
   写入序列连续
3. `/dev/mem` 映射属性（UC-）与 `ioremap`（UC）语义不完全相同

无论哪一条，**纪律是明确的**：

> **改 BAR0 链路控制寄存器（会触发 LTSSM 动作的那些）必须走内核路径。**
> 用户态 mmap 只在"驱动未加载 / 链路静止"时用于读与一次性推送。
> 特别地，**不要用用户态脚本做"链路降级后立即按回"这类操作** —— 这是实测两次打挂设备的路。

### 4.4 这条结论的代价与价值
- 代价：**两次整机重启**
- 价值：解释了长期困惑——
  - 为什么 `safe-gen2.py` 有时成、有时不成（成的时候链路已静止）
  - 为什么"手动推 Gen2 后跑 DMA 带宽还是 0.78"（reports/195）不是偶然
  - 为什么 gen2kr 必须做成内核模块而不是脚本

## 5. 顺带修掉的致命缺陷（reports/196 遗留，本轮已完成）

三处写 `0x8C040` 都用了"读-改-写"但只判 `!= 0xffffffff`：

```c
lk = readl(bar + OFF_LINKCFG0);
writel((lk & ~0x000C0000u) | (1u << 18), bar + OFF_LINKCFG0);
//     若 lk = 0xFFFFFFFF → 0xFFF3FFFF | 0x40000 = 0xFFF7FFFF → bit0=1 = COMMIT
```

**已修 5 处**（`gen2kr.c` 的 guard / push / ret_handler fast path，`safe-gen2.py` ⑤，
`tools/probe-selfheal.sh`）。修法：写回前双校验
① `!= 0xffffffff` ② **`(lk & 1) == 0`**（COMMIT 必须为 0）。

虽然 §4 表明它不是那两次事故的原因，但它是一个**独立的、真实的**掉卡通道，必须堵。
