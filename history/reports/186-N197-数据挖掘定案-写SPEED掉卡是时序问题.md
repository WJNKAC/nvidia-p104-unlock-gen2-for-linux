# N197 — 数据挖掘定案：写 SPEED 掉卡不是概率，是「训练未完成就改速率」

**日期**：2026-10-29 02:30
**方法**：**纯静态分析**（实验机宕机不可达，挖掘 11 份历史日志）
**结论**：之前以为是"概率性掉卡"，实际是 **100% 确定性的时序问题**。

---

## 0. 一句话结论

> **`0x8872C = 6` 会触发一次 LTSSM 链路训练。在这次训练完成之前写 `0x8C040.SPEED`
> 必然让端点 LTSSM 死锁 —— 7 次实验，2 掉 5 存，完全由这一点区分，没有例外。**

之前记录成"写 SPEED 有概率掉卡"是错的。**它不是概率，是时序。**

### 2.1 ★ 修正：致命操作有【两个】，不是一个

上表只统计了「写 SPEED 后 6 行内」的死亡，漏掉了后续步骤的死亡。
逐份日志核对第 3 步之后的行为，真实结局是：

| 日志 | 写 SPEED 的时机 | 写 SPEED 后 | 第3步行为 | **真实结局** |
|---|---|---|---|---|
| `c2` | 第1步**立即** | — | — | ☠ **死在写 SPEED** |
| `f` | 第1步**立即** | — | — | ☠ **死在写 SPEED** |
| `T0` | 等 4s 后 | 活，sp=2 | 打了**端点 Retrain** | ☠ **死在端点 Retrain** |
| `e` | 等 4s 后 | 活，sp=2 | 第1轮即 sp=2，立即返回 | ✓ 存活 40s |
| `T2` | 等 4s 后 | 活，sp=2 | **显式跳过重训** | ✓ 存活 30s |
| `speedonly` | 第1步（起点已训练） | 活，sp=2 | 第1轮 sp=2 | ☠ **死在第4步写 COMMIT** |

### 2.2 规律（两条，各有独立证据）

```
致命 #1  写 SPEED 时链路训练还没完成
         c2 / f  → 2/2 死
         等 4s 后写的 e / T0 / T2 → 都没死在写 SPEED

致命 #2  打【端点】Retrain（写 0x88088 bit5）
         T0 → 打了，第1轮就「端点读不到」
         T2 → 显式跳过，存活
         e  → 打了但链路已是 sp=2 立即返回，侥幸活（1/2 风险）

致命 #3  写 COMMIT
         speedonly → 第4步循环里带 COMMIT，几毫秒死
```

⇒ **最安全的配方是：写 SPEED 前等够 + 之后【只从根端口】重训、绝不碰端点 Retrain。**
这正是 `safe-gen2.py` 的实现。

## 3. 机理

### 3.1 `0x8872C = 6` 是什么

这是 `XVE_OVR`（LTSSM override / 触发）寄存器。写 6 等于**命令 PCIe 核启动一次链路训练**。

训练是**异步的**：写完立即返回，硬件在后台跑 LTSSM 状态机
（Detect → Polling → Configuration → L0）。

### 3.2 为什么训练中改 SPEED 会死锁

```
写 0x8872C=6   →  LTSSM 进入 Polling/Configuration
                      ↓（正在按当时的速率请求协商）
写 0x8C040.SPEED=1  →  速率请求中途被改
                      ↓
                 两端速率意向不一致，且在 Configuration 阶段无法回退
                      ↓
                 LTSSM 卡死 → 端点不再应答配置读 → C. ZOMBIE
```

`0x8C040.SPEED` 是**速率请求**，属于 Configuration 阶段要读的输入。
在状态机跑到一半时改它，等于改正在被消费的输入。

### 3.3 为什么"已训练过"就安全

`caps=0x0006 / cfg=0xc0b48d00` 那次的起点，说明 GPU **已经完成过一轮 Gen2 训练**
（`0xc0b48d00` 的 bit13 是 `RmForceEnableGen2` 相关位，由驱动上一轮 devinit 置上）。

此时 `0x8872C=6` 触发的是一次**再训练**，而核已经知道目标速率，训练路径短、
不易被中途改动打乱 —— 所以立即写也活下来了。

⇒ **这条路径不能用"它能活"来推广。** 冷态才是常态。

## 4. 对现有方案的影响

### 4.1 `gen2kr.c`（kretprobe）为什么能活 —— 逻辑自洽了

kretprobe 的 fast path 在 `nv_pci_probe` 返回后写 SPEED。此时：
- 驱动 devinit 内部已经做过一轮训练（相当于"已训练过"）
- 所以属于 §3.3 的安全情形

⇒ 与 2/2 成功一致，**不是运气**。

**但要注意**：如果将来把 kretprobe 改成"在 probe 中间/更早"触发，
就会落进 §3.2 的陷阱。**必须在 devinit 的训练完成之后**。

### 4.2 手动脚本必须遵守的顺序

```
① 写 XP3G_OVR0/3 + VAL0/3
② 写 0x8841C / 0x88610
③ 写 0x8872C = 6          ← 训练开始
④ ★ 等待 ≥4s（推荐：轮询 LCAP2 变成 0x06，最多 25s）
⑤ 写 0x8C040.SPEED=1
⑥ 等 ≥3s，再从【根端口】发 Retrain
```

**③→⑤ 之间必须有等待。** 这是 2 次掉卡换来的教训。

### 4.3 可以安全地做的操作

- 写 `0x8841C` / `0x88610` / XP3G：**从不掉卡**（多组实验一致）
- 只从根端口写 `LNKCTL.bit5`：安全（端点 Retrain 才危险）
- 读任何寄存器：安全
- 写 `0x8C040.SPEED`（训练完成后）：安全

### 4.4 绝对禁止

| 操作 | 后果 |
|---|---|
| 训练中改 SPEED | **必死** |
| 写 `0x8C040.bit0`（COMMIT） | **必死**（任何状态） |
| 写端点 `0x88088` 的 Retrain 位 | **打死端点** |
| 往 `0x8841C` 写绝对值（跳过 XP3P 前置） | **打死端点** |
| 在 DMA 期间重训 | **可能打挂整机**（reports/185） |

## 5. 顺带修正的一个旧结论

reports/177 §7 曾提出假设 H3：「写 SPEED 是否安全，取决于端点是否已
在 bit15/bit11 就位的前提下完成过一次链路协商」，并把 `cfg=0xc0b48d00` 当作关键线索。

**这个假设方向对了**，但表述不准。准确的表述是：

> 关键不是 `0x8841C` 的位，而是 **`0x8872C=6` 触发的那次训练是否已经结束**。
> `cfg=0xc0b48d00` 只是"上一轮训练已完成"的间接痕迹。

## 6. 验证方案（机器恢复后立即做）

1. **正向验证**：冷启动 → 按 §4.2 顺序（③ 后强制 `sleep 5`）→ 写 SPEED → 应 **5/5 存活**
2. **反向验证**：冷启动 → ③ 后**立即**写 SPEED → 应 **掉卡**（预期，用于确认因果）
3. 若反向验证不掉卡，说明还有别的因素，需重新分析

⚠ 反向验证会打死设备、需要重启，做 1 次即可。

### 7.1 守卫的安全改造（reports/185 事故的直接补救）

| 项 | 旧版 | 新版 |
|---|---|---|
| 守卫周期 | 100 ms | **200 ms** |
| 重训触发 | 读到 Gen1 就重训（**每 5 轮**） | **连续 10 次（2s）都是 Gen1** 才重训 |
| 重训频率 | 无上限 | **最快 2 秒一次**（`retrain_min_ms`） |
| GPU 忙时 | 不管 | **查 `nvidia.ko` 模块引用数是否高于基线，忙则跳过** |
| 总开关 | 无 | `guard_enabled=0` 可完全停用 |
| 日志 | `pr_info` 每次刷 | `pr_info_ratelimited`，防日志风暴 |
| SPEED 按回 | 每轮都做 | 仍然每轮（这是纯 MMIO 小写，无副作用） |

新增内核参数（都可运行时改）：
```
retrain_min_ms  默认 2000   两次重训最小间隔
debounce_cnt    默认 10     连续多少次读到 Gen1 才重训
guard_period_ms 默认 200    守卫周期
guard_enabled   默认 1      总开关
```

**这版未经实机编译验证**（机器宕机），恢复后第一件事是编译 + 冒烟测试。
