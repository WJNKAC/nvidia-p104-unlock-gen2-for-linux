# N203 — 机制完全查清：这不是"用户态下发"，是内核的链路异常恢复逻辑

**日期**：2026-10-29 07:50–08:20
**问题**（用户）：这个 SPEED 锁定环是不是也是用户态发起的（类比 P106 的每批延迟）
**答案**：**不是用户态直接下发命令，但你的直觉指向了正确的层次。**
它是**内核模块的"PCIe 链路异常恢复"函数**，由**链路状态变差**触发。

---

## 0. 结论先行

| 项 | 结论 |
|---|---|
| 代码位置 | `nv-kernel.o_binary` `.text+0x105cc0` 区域；在 `nvidia.ko` 里同构于 `.text+0x126c4e` |
| 所属函数 | **`_nv017281rm`**（`nvidia.ko` `.text+0x1269f0`），约 0x760 字节 |
| 调用链 | `_nv005948rm` → `_nv017282rm` → `_nv017281rm` |
| 函数性质 | **链路异常处理/降级**，不是常规初始化 |
| 触发条件 | `[r12+0xa38] & 3` 等**状态码**非 0，且各分支都在打 RM 错误日志 |
| 锁定环 | `sp==1` 时写 `SPEED=2`（Pascal = 2.5GT/s）→ 与当前速率保持一致 → 永久 Gen1 |

**所以：不是用户态在"下发"这条命令。是内核在"发现链路是 Gen1"之后，
主动把速率请求也对齐成 Gen1。**

---

## 1. 关键证据：各分支都是错误日志

```asm
127070: mov esi,0xb80000        ; ← NV_STATUS 错误码
127075: mov edi,0xe59ecb0       ; ← 格式字符串地址
12707a: xor eax,eax
12707c: mov ebx,0x1
127081: call <NV_PRINTF>        ; 打日志

127096: mov esi,0xc50000        ; 另一个错误码
12709b: mov edi,0xe59ecb0
...

1270c8: mov esi,0xbe0000        ; 第三个
1270cd: mov edi,0xe59ecb0
```

`0xb10000 / 0xb80000 / 0xbe0000 / 0xc50000` 是 RM 的 NV_STATUS 分级码，
`0xe59ecb0` 反复出现说明是同一个格式串。

**⇒ 这些分支是错误/降级路径，只有异常时才走。**

---

## 2. 完整策略解析（位域解码）

```asm
; ---- 入口：先读 VSEC_HIERARCHY 0x88610 ----
126a6c: mov  ecx,0x88610
126a74: call <read>
126a7e: shr  ebx,0xc           ; bit12
126a81: and  r15d,0x1          ; bit0
126a85: and  ebx,0x1
; ← 正是 pcie-gen2.patch 里"清 bit12、置 bit0"的那个寄存器

; ---- 再看 [r12+0xa38] 的状态码 ----
126a91: je   0x126d30          ; [r12+0xa34]==0 → 跳过
126a97: mov  edx,[r12+0xa38]
126aa1: and  eax,0x3           ; bits[1:0]
126aa4: cmp  eax,0x1  → 0x1270f0   （打 0xb10000）
126aad: cmp  eax,0x2  → 0x127040   ★ 走 SPEED=2
126ab6: mov  eax,edx
126ab8: shr  eax,0x2
126abb: and  eax,0x3           ; bits[3:2]
126abe: cmp  eax,0x1  → 0x127070   （打 0xb80000）
126ac7: cmp  eax,0x2  → 0x1270c8   （打 0xbe0000）
126ad0: test edx,edx
126ad2: js   0x127096          ; 最高位 → 打 0xc50000

; ---- 再读 PL_LINK_RATE 0x8C1C0 ----
126b09: mov  ecx,0x8c1c0
126b22: call <read>
126b27: shr  eax,0x14          ; bits[23:20]
126b2a: and  eax,0xf
126b2d: cmp  eax,0x1  → 0x126ff0
126b36: cmp  eax,0x2  → 0x126b76
126b3d: test eax,eax  → je 0x126de8
```

**`[r12+0xa38]` 不是"配置"而是"状态/结果码"**，不同取值对应不同处理分支，
且每个非 0 分支都打错误码。这是典型的"错误分派"结构。

---

## 3. 锁定环本身（`.text+0x127040`，即我们要 patch 的点）

```asm
; ---- 读当前速率 ----
126c51: mov  ecx,0x8c040       ; LINK_CONFIG_0
126c5d: call <read>
126c67: mov  ecx,0x88088       ; LINK_CTRL_STATUS
126c73: call <read>
126c78: shr  eax,0x10          ; LNKSTA
126c7f: and  edx,0xf           ; edx = 当前 sp
126c82: and  eax,0xfff3ffff    ; 清 SPEED[19:18]

; ---- 按当前 sp 决定写什么 ----
126c87: cmp  edx,0x1
126c8a: je   0x127040          ; sp==1 → 下面
126c93: or   r8d,0x40000       ; sp!=1：SPEED=1
126c9a: cmp  edx,0x2
126c9d: cmovne r8d,eax         ; sp!=2：SPEED=0
126cb0: call <write>           ; 写回

; ★ sp==1 分支
127040: or   eax,0x80000       ; SPEED=2 → Pascal 2.5GT/s → 继续 Gen1
127045: mov  r8d,eax
127048: jmp  0x126ca1          ; 回去写
```

**这就是那个自我强化锁定环**：发现当前是 Gen1 → 请求也设成 Gen1 → 永远 Gen1。

---

## 4. 为什么之前所有动态手段都抓不到它

| 手段 | 结果 | 原因 |
|---|---|---|
| kprobe `_nv053912rm` | 9 亿次异常 | 那是**寄存器访问器**（CX 全在 0x160~0x10a4cc），不是这个函数 |
| perf 断点 `_nv053912rm` | CX 无 0x8C040 | 同上 |
| perf 断点 `_nv049698rm` | samples = 0 | 根本没被调用 |
| 20ms 采样 | 看到 SPEED 变 2 | 只能证明"值变了"，不能证明"谁写的" |

**真正原因**：`_nv017281rm` 是**异常恢复路径**，只在"检测到 PCIe 异常"时才执行。
正常 CUDA 运行（链路健康）时它不跑，所以动态抓不到。

而我们的场景恰恰有异常：**Gen2 链路在 DMA 压力下重训失败 → 触发这个恢复函数
→ 它把 SPEED 对齐成 Gen1 → 锁死。**

## 5. 补丁是否成立

### 5.1 方向是对的

把 `127040` 的 `or eax,0x80000` 改成 `or eax,0x40000`：
当恢复逻辑发现"当前是 Gen1"时，**改为请求 Gen2**，配合已解锁的声明（`LCAP2=0x06`），
链路有机会自己爬回 Gen2，而不是被钉死在 Gen1。

### 5.2 唯一签名已验证

| 签名 | `nvidia.ko` 命中数 |
|---|---|
| `0d 00 00 08 00`（5 字节） | **421,598** ❌ |
| `0d 00 00 08 00 41 89 c0 e9 94 fc ff ff`（14 字节） | **421,598** ❌ 仍然不唯一 |
| **`83 fa 01 0f 84 70 03 00 00`**（`cmp edx,1; je +0x370`，9 字节） | **1** ✅ |

```
anchor 0x126cc7 → 推断 sp==1 分支 = 0x126cc7 + 3 + 6 + 0x370 = 0x127040
该处字节: 0d 00 00 08 00 41 89 c0 e9 94 fc ff ff   ✓ 与预期一致
待改: 偏移 0x127043, 0x08 → 0x04
```

**工具**：`tools/patch_speed_lock.py`（check / apply / revert，含唯一性校验和目标字节校验）

**这解释了我上一轮 1 字节补丁为什么失败**：当时用的短模式在文件里有 42 万处，
改的那一处很可能根本不是这段代码。

## 6. 对用户类推的修正

你的类推（"是不是用户态发的，像 P106 每批延迟那样"）**方向对，但层次差一层**：

| | P106 的每批延迟 | 现在的 SPEED 锁定环 |
|---|---|---|
| 决策逻辑在哪 | **内核**（设备白名单） | **内核**（`_nv017281rm`） |
| 实际发送命令的是谁 | **用户态** glcore 发 method 0x3998 | **内核** 直接 writel BAR0 |
| 用户态能否绕过 | 否，但可 patch 内核白名单 | 否，但可 patch 这段代码 |
| patch 效果 | 52ms → 3.4ms | 待验证 |

**关键差别**：P106 那个是"内核告诉用户态去做"，所以用户态能改；
这个 SPEED 锁定环是内核自己直接写寄存器，**用户态没参与**。

**但共同点非常重要**：两者都是**内核里的一个策略判断**决定了降级行为。
P106 是设备 ID 白名单，这里是 PCIe 链路状态码。**都可以用 1 字节补丁绕过。**

## 7. 设备恢复后的验证方案（按优先级）

### 7.1 先确认这个函数确实被调用

```bash
ADDR=$(sudo grep -w _nv017281rm /proc/kallsyms | cut -d' ' -f1 | head -1)
sudo perf record -e mem:0x$ADDR:x -a --intr-regs=cx,r8,si,dx -o /tmp/f.data \
  -- sh -c 'for i in 1 2 3; do bwtest2 64 3; sleep 1; done'
sudo perf script -i /tmp/f.data -F comm,ip,iregs | head -20
```

- **有命中** ⇒ 确认它被触发，patch 有意义
- **无命中** ⇒ 说明触发条件还没满足（可能需要先让它真的经历一次 Gen2→Gen1 掉速）

### 7.2 再验证 patch 效果

```bash
sudo python3 tools/patch_speed_lock.py check   # 确认唯一命中 + 目标字节
sudo python3 tools/patch_speed_lock.py apply
# 重载驱动
modprobe -r nvidia_drm nvidia_modeset nvidia_uvm nvidia; modprobe nvidia
# 推到 Gen2 后测带宽
```

**判据**：如果 patch 生效，掉速后链路应**自己能回到 Gen2**，不再需要 `gen2kr` 守卫。

## 9. 一句话

> **不是用户态发起的 —— 是内核的「PCIe 链路异常恢复」函数
> `_nv017281rm` 在发现链路是 Gen1 后，主动把速率请求也对齐成 Gen1。**
