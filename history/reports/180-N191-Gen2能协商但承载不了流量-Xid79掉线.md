# N191 — Gen2 能协商但承载不了流量：Xid 79 掉线；897/1636 的归属定案

**日期**：2026-10-29 01:00
**对象**：P104-100（10de:1b87），root port `00:01.0`，580.178.04 / kernel 6.1.0-50-amd64
**脚本**：`gen2-bw.py`

---

## 0. 这一条改变了整个课题的性质

前面所有轮次都在问"**怎么把链路弄到 Gen2**"。
本轮答案出来了：**Gen2 能弄到，但一跑真实 DMA 流量，GPU 立刻从总线上消失。**

```
=== 5. 根端口 Retrain（不碰端点）===
  [第1轮] 端点 sp=2 | 根端口 sp=2 | 0x8C040=0x20045800      ← Gen2 达成，一轮

=== 6. ★ 立刻测带宽（紧接上一步，无间隔）===
  测前 sp=2  测后 sp=None  耗时 60.1s
  cuInit=101
```

dmesg 的死因：

```
[  203.860305] NVRM: GPU at PCI:0000:01:00: GPU-41c5b064-...
[  203.860311] NVRM: Xid (PCI:0000:01:00): 79, GPU has fallen off the bus.
[  203.860317] NVRM: GPU 0000:01:00.0: GPU has fallen off the bus.
[  203.864758] NVRM: GPU 0000:01:00.0: RmInitAdapter failed! (0x25:0xf:1636)
[  203.865102] NVRM: GPU 0000:01:00.0: RmInitAdapter failed! (0x22:0x56:897)
```

**`Xid 79 — GPU has fallen off the bus`。** 时间戳 203.86 正对应 bwtest 开始的那几秒。

## 1. 顺带把 897 / 1636 的归属彻底定了

之前（报告 177 §3.1）只是**推断** 897 是"设备半死时 RM 初始化超时"的通用错误。
现在有前因了：

```
Xid 79（GPU 掉下总线）  →  1636 (0x25:0xf)  →  897 (0x22:0x56)
```

**897 和 1636 都是"设备已经掉线之后"的善后错误，与 PCIe 速率、与 0x8C040 完全无关。**
查了无数遍闭源头文件找不到它们，因为它根本不是一个"PCIe 相关错误码"。

⇒ 以后看到 897，第一件事是查 dmesg 有没有 **Xid 79**，而不是怀疑速率配置。

---

## 2. 没有 AER 错误 —— 不是典型信号完整性问题

```
AER : 1        ← 只是 "[0.176] acpi PNP0A08:00: _OSC: OS now controls [AER PCIeCapability LTR]"
Correctable : 1  ← 只是 "[0.572] RAS: Correctable Errors collector initialized."
Uncorrectable : 0
Receiver Error : 0
Bad TLP : 0
Bad DLLP : 0
link is down : 1  ← 只是 "[7.695] r8169 网卡"（跟显卡无关）
```

**零条 PCIe 物理层错误。** 如果真是信号质量差（走线/金手指/转接卡），
通常先出现大量 Correctable Errors（Receiver Error / Bad TLP / Bad DLLP），
然后才降到 Gen1 或掉线。我们没有这个过程。

⇒ 更像是**协议层状态不一致**，而不是模拟信号撑不住。见 §3。

## 3. 最可能的原因：链路层到了 Gen2，GPU 内部数据通路还在 Gen1

我们的操作序列：

| 做了什么 | 谁在动 |
|---|---|
| 写 `0x8C040.SPEED = 1` | GPU 侧厂商寄存器（告诉 GPU 核"用 5GT"） |
| 从**根端口**写 `LNKCTL bit5` Retrain | **主机侧**发起重训 |
| 链路协商成功 → 两端 LNKSTA 都是 sp=2 | 链路层（LTSSM） |

问题在于：**这次重训是主机侧单方面发起的。**

参考项目在 Windows 上是写 `0x8C040` **并带 `bit0`(COMMIT)** ——
那个位大概率是让 **GPU 自己的 PCIe 核**去发起重训并同步内部数据通路。
我们因为 COMMIT 必掉卡而绕开了它，改用主机侧重训，
结果：**链路层谈成了 Gen2，但 GPU 内部数据面没跟着切**。

一旦有真实 TLP 流量，两边速率/状态不匹配 → GPU 掉线（Xid 79），且因为没有
物理层误码，AER 一个都不报。

这个解释与所有观测一致：
- 空闲时 `lspci` 老老实实显示 `5GT/s x4`
- 一旦 DMA 就死
- 没有 AER
- 带宽永远 0.78（因为每次要么已掉回 Gen1，要么刚跑就死）

## 4. 三个"复位候选"的最终裁决（对应用户的提问）

| 候选 | 结论 | 证据 |
|---|---|---|
| **M1** `unbind → enable=0 → enable=1 → bind` | **不可用** | `echo 0 > enable` 报"输入/输出错误"，内核直接拒绝 |
| **M2** `power/control` runtime PM | **无效** | `auto` 后 `runtime_status` 恒为 `active`，驱动不让挂起 |
| **M3** `setpci` PMCSR → D3hot → D0 | **安全但零效果** | PMCSR `0x0008→0x000b→0x0008` 写入成功、设备完好；但 6 个 BAR0 寄存器**逐字节不变** |
| **M4**（对照）`remove/rescan` | 可用，但**也没复位核** | 同上，寄存器逐字节不变 |

**推论：没有任何一种方法能复位 PCIe 核，而且复位本身根本不需要。**
`LINK_CAP2` 从 `0x02` 变 `0x06` 只是 `0x8841C` 那几位的**镜像**，写进去立刻反映，
和"设备初始化"无关。参考项目把它列为"决定成败的第 2 步"，
是因为 **Windows 驱动会把这几位压回去**，必须抢在驱动卸载窗口里写；
Linux 580.178.04 不碰这些位。

⇒ **用户的推测「D3hot ≈ DICS_DISABLE」不成立。** Windows 的 `DICS_DISABLE` 是
**总线级移除**（设备从 PnP 树消失、配置空间读不到），D3hot 只是**电源态标记**，
设备留在总线上、配置空间照读。两者不在一个层次。

## 5. 现在真正的配方（去掉所有不必要的步骤）

三个寄存器分工，已多组对照切干净：

```
① 声明解锁（安全）：0x8841C 置 bit15/13/11 清 bit12/14
                    0x88610 清 bit12 置 bit0
                    0x8872C = 6
                    ⇒ LINK_CAP2 0x02 → 0x06，当场生效，不需复位、不需等待

② 目标速率对齐（安全）：根端口 LNKCTL2[3:0] = 2
                        （端点本来就是 2）

③ 速率请求（唯一危险点）：0x8C040.SPEED[19:18] = 1，**绝不发 bit0 COMMIT**
                         ⇒ 有概率把端点写死；写完必须等 ≥3s 才能重训

④ 触发重训：只从根端口写 LNKCTL bit5
            ⇒ 链路层可达 Gen2，但 GPU 数据面可能没跟上（§3）
```

**不需要 `remove`、不需要 `rescan`、不需要 `unbind/bind`、不需要 D3hot、
不需要 COMMIT、不需要常驻按住（60 s / 1700 次采样回压 0 次）。**

## 6. 三条血泪级操作禁忌（都真实打死过设备）

| 操作 | 后果 |
|---|---|
| 写 `0x8C040.bit0`（**COMMIT**） | 必掉卡 |
| 写**端点** `0x88088` 的 Retrain 位 | 打死端点 |
| 写完 SPEED 后**毫秒级**立刻重训 | 打死端点（须等 ≥3 s，实测十几秒最稳） |
| 往 `0x8841C` 写**绝对值** `0xC0B4AD00`（跳过 XP3G 前置） | 打死端点（必须读当前值再 OR） |
| 在 Gen2 下跑真实 DMA | **Xid 79，GPU 掉下总线** |

## 7. 下一步的岔路

现在问题不再是"能不能解锁"，而是"**5GT/s 到底能不能承载数据**"。三条路：

### 路线 A：让 GPU 自己发起重训（最有可能成功）
既然主机侧重训会导致数据面不同步，那就想办法让 GPU 侧同步切换内部通路，
但**不写 COMMIT**。候选：
- `0x8C040` 的 bit22（实测被驱动置过，`0x20585800` vs `0x20085800`）—— 也许那才是"GPU 侧提交"
- 逐位走查 `0x8C040` 的其他位（**风险高**：参考项目记录过逐位走查会掉卡）
- 查 `0x8C080 WIDTH`（实测 `0x404` = x4）附近是否有速率相关字段

### 路线 B：接受"Gen2 只能协商不能跑"，工程上放弃
如果确认数据面无法同步，那这张卡在这台机器上就是 Gen1 x4 = 0.78 GB/s 封顶。
把结论写清楚，把精力转回 P106 的每批延迟课题。

### 路线 C：换硬件验证
参考项目在同一型号卡上跑到 1.55 GB/s，说明**卡本身支持**。
差异可能在：插槽（是否 x4 电气直连）、转接卡/延长线、主板。换直插 x16 槽再试一次，
可以区分"卡不行"还是"这台机器的链路不行"。
