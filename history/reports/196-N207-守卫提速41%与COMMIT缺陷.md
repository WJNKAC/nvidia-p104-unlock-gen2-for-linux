## 1. 先做静态对比：push 一次成功、guard 屡屡失败，差在哪

`push_fn`（每次 probe 都成功，104ms 内 `LNKSTA=1042`）与 `guard_fn`（连续 4 轮失败）的差异：

| 步骤 | `push_fn` | 旧 `guard_fn` |
|---|---|---|
| 解锁声明 | ✅ | ❌（首次已做，本可跳过） |
| SPEED=1 | ✅ | ✅ 每轮按回 |
| 写 `0x8872C=6` | ✅ | ✅ |
| **→ 根端口 Retrain 的间隔** | **`msleep(50)`** | **`retrain_min_ms=2000`** |
| 两端 TLS2=5GT | ✅ | ❌ **缺失** |
| 根端口 Retrain | ✅ | ✅ |

**核心问题**：`retrain_min_ms` 本意是"两次**完整尝试**之间的最小间隔"（防止疯狂重训），
却被同时用来卡 **stage0 → stage1** 的间隔，导致两步之间被强制隔 2 秒。

### 补充验证：TLS2 不是原因
降级后实测两端 TLS2 与 Gen2 时**完全一样**：

| | 端点 LNKCTL2 | 根端口 LNKCTL2 | LCAP2 | 0x8C040 |
|---|---|---|---|---|
| Gen2 时 | `0002` | `0042` | `0x0006` | SPEED=1 |
| 降级后 | `0002` | `0042` | `0x0006` | SPEED=1 |

⇒ 所有协商条件都满足，链路却停在 Gen1。**必须显式重训**，guard 不重设 TLS 也不是问题。

## 2. 改造：stage 间隔解耦

### 参数变化
| 参数 | 旧 | 新 | 说明 |
|---|---|---|---|
| `stage_gap_ms` | 不存在 | **150** | 新增。stage0→stage1 专用，模仿 push 的 50ms + 余量 |
| `debounce_cnt` | 10 | **3** | 3×200ms=600ms |
| `retrain_min_ms` | 2000 | 2000 | 语义收窄为"两次完整尝试之间" |
| `speed_settle_ms` | 3000 | 3000 | **未动**（reports/186 铁律） |

### 逻辑变化（`gen2kr.c`）
1. 新增 `stage_start_jiffies` / `last_attempt_jiffies` 两个时间戳
2. `retrain_stage == 1` 时**走独立分支**：跳过防抖与 `retrain_min_ms`，只等 `stage_gap_ms`
3. 链路恢复（`!low`）时**同时重置 `retrain_stage = 0`**
   —— 否则下次掉速会直接跳到 stage1，跳过 stage0（旧代码的隐患）

### 实测
```
[1008.184] SPEED 按回 1（第 1 次，原 20585800）
[1011.244] 触发训练 0x8872C=6（总第 1 次，LNKSTA=1041）   ← +3.06s  speed_settle
[1011.448] 根端口 Retrain（LNKSTA=1041，stage 间隔 150ms）← +0.204s ★ 原 2000ms
[1013.284] 触发训练（总第 2 次）                          ← +1.84s  retrain_min
[1013.488] 根端口 Retrain
→ 5.65s 恢复 Gen2
```
stage 间隔实测 204ms（受 `guard_period_ms=200` 粒度限制），符合预期。

### 剩余 5.65s 的构成
| 环节 | 耗时 | 能否压 |
|---|---|---|
| `speed_settle_ms` | **3.06s** | 是最大项，但受 reports/186 铁律约束，本轮未动 |
| stage 间隔 | 0.20s | 已压到极限 |
| Retrain 生效 | ~1.8s | 物理限制 |
| 第 2 轮 `retrain_min_ms` | 1.84s | 只因第 1 轮失败才付 |

**注**：`[1011.448]` 那条日志里的 `LNKSTA=1041` 是 **Retrain 之前**读的，
不代表 Retrain 失败。实测 Retrain 后约 1.8 秒链路才变 —— 这也是"日志全 1041 但最后成功了"的原因。

## 3. ★★★★★ 挖出的严重缺陷：写 `0x8C040` 未挡 COMMIT

### 现象
跑 `probe-selfheal.sh`（只按回 SPEED、不重训，观察链路是否自愈）时，
写入后立刻读回 `0x8C040 = 0xffffffff`、`LNKSTA = 0xf`。
`pci-state.sh` 判定：**C. ZOMBIE**（`lspci` 在、`cfg=ffffffff`、`power=D0`、`CAP_EXP` 找不到）。
**`dmesg` 里没有任何 Xid** —— 说明是硬件级静默失联，不是驱动检测到掉卡。

### 根因（静态推导，逐位验算）
三处写 `0x8C040` 的代码都用了同一个模式：

```c
lk = readl(bar + OFF_LINKCFG0);
if (lk != 0xFFFFFFFFu) {                       /* ← push/fast 只有这一道 */
    writel((lk & ~0x000C0000u) | (1u << 18), bar + OFF_LINKCFG0);
}
```

`0x8C040.bit0` 是 **COMMIT**（写 1 必掉卡，reports/186 致命 #3）。
如果 `lk` 在链路重训瞬态读到 `0xffffffff`（**这是常态，不是异常**）：

```
0xFFFFFFFF & ~0x000C0000 = 0xFFF3FFFF
0xFFF3FFFF | (1 << 18)   = 0xFFF7FFFF
                             ↑
                           bit0 = 1  →  COMMIT → 必掉卡
```

**"写 SPEED 时只要不碰 bit0"这个理解是错的**：
危险不在"主动写 COMMIT"，而在**从一个含垃圾位的读值派生写回**。

### 旧 guard 的漏洞更严重
```c
v = readl(bar + OFF_CAP2);
if (v == 0xFFFFFFFFu) goto unmap;      /* 只校验了 CAP2 */
lk = readl(bar + OFF_LINKCFG0);        /* ← lk 完全没校验 */
```
CAP2 可读但 LINKCFG0 瞬时失读 —— 完全可能（两者不同的读周期）。

### 修复（三处 + 一个 Python 脚本 + 一个 shell 脚本）

**① `guard_fn`**
```c
if (lk == 0xFFFFFFFFu) { 告警一次; goto unmap; }
if ((lk & 1u) != 0) {    /* COMMIT 已置位，绝不在此基础上写回 */
    pr_warn_ratelimited("... bit0(COMMIT)=1，拒绝写回（lk=%08x）\n", lk);
    goto unmap;
}
if (((lk >> 18) & 0x3) != 1) { writel(...); }
```

**② `push_fn`**：`if (v == 0xFFFFFFFFu || (v & 1u) != 0) 跳过写入并报错;`

**③ `ret_handler` fast path**：`if (lk != 0xFFFFFFFFu && (lk & 1u) == 0) {...} else 告警;`

**④ `safe-gen2.py` ⑤**：同样加了 `cur == 0xFFFFFFFF or (cur & 1)` 拒绝分支

**⑤ `probe-selfheal.sh`**：写 SPEED 前校验 `$V != 4294967295 && (V & 1)==0`

### 另一个语义错误（顺手修）
`probe-selfheal.sh` 原本用 `echo 0 > guard_enabled` 来"停守卫"。
但代码里 **按回 SPEED 在 `guard_enabled` 检查之前**（① 在 ③ 之前），
所以 `guard_enabled=0` 根本停不掉按回 —— 会造成两个 MMIO 写入者并发。
已改为 `rmmod gen2kr`，并在结束时重新 `insmod`。
