# N189 — "掉卡"和"D3cold 卡死"的区别：其实是三种状态，不是两种

**日期**：2026-10-29 00:20
**对象**：P104-100（10de:1b87），root port `00:01.0`
**工具**：`/data/labs/nvidia/pcie-gen2/pci-state.sh`

---

## 0. 先回答提问里那个困惑

> "掉卡和卡 D3cold 读都是 `0xffffffff`、写 `enable=1` 也拉不回 D0，区别是什么？"

**区别在于成因和可恢复性，而 `0xffffffff` 和 `enable` 失败本身没有鉴别力。**

为什么 `enable=1` 没用？因为 **`enable` 是写 PCI 配置空间 Command 寄存器**。
设备不应答配置读时，配置写自然也写不进去。所以：

```
enable=1 失败  ←  配置空间不可访问  ←  可能有 3 种完全不同的原因
```

它是**后果**，不是**原因**。用它判断等于用"灯泡不亮"判断"是停电还是灯泡坏了"。

今晚三种状态**全都真实出现过**，可以逐条对上。

---

## 1. 三种状态

| | **A. D3COLD** | **B. GONE** | **C. ZOMBIE** |
|---|---|---|---|
| 一句话 | 电源态错，设备**没上电** | 链路断了，设备**不在总线** | 枚举还在，**配置空间不应答** |
| `lspci -Dn` | 在 | **不在** | 在 |
| `/sys/bus/pci/devices/<BDF>/` | 在 | **不在** | 在 |
| `power_state` | **`D3cold`** | 目录不存在 | **`D0`** ← 关键 |
| `setpci -s .. 0.l` | `ffffffff` | `No devices selected` | `ffffffff` |
| `setpci .. CAP_EXP+0x2c.l` | **能解析出值** | — | **`capability not found`** |
| dmesg 专属台词 | **`Unable to change power state from D3cold to D0`** | 无 | 无 |
| 上游根端口 | 正常 | 掉回 `0x1041`/`0x5041` | 正常或掉回 |
| **软件能救吗** | **✅ 能** | ❌ 基本不能 | ❌ 不能 |
| 恢复手段 | unbind → remove → rescan | 次级总线复位偶尔有效 → 否则重启 | 只能重启 |

## 2. 为什么 A 能救、B/C 不能

### A. D3cold —— 只是"没上电"

`remove` 时驱动还绑着，设备进入 D3cold（**物理上掉了电**）。
这之后再 `rescan`，内核知道设备地址，但设备没电 → 配置空间读 `0xffffffff`。

**设备本身完好**，只是没人给它上电。所以：

```bash
echo 0000:01:00.0 > /sys/bus/pci/drivers/nvidia/unbind   # ★ 先解绑，让驱动别把设备再放回 D3
echo 1 > /sys/bus/pci/devices/0000:01:00.0/remove
echo 1 > /sys/bus/pci/rescan
echo 1 > /sys/bus/pci/devices/0000:01:00.0/enable
echo on > /sys/bus/pci/devices/0000:01:00.0/power/control
```

实测（本会话早期）：不 unbind 直接 remove → D3cold，救不回；
加 unbind → remove+rescan 后 `power=D0`，驱动正常。

**核心**：D3cold 是"电源管理状态机"的问题，拔出/重插（hot-reset 序列）能重置它。

### B. GONE —— 链路训练失败，端点下线

端点自己从链路层消失了。根端口的 `LNKSTA` 会退化（今晚见到 `0x5041` → `0x1041`）。
host 侧再怎么 rescan 也没用，因为下游没有设备应答。

理论上"次级总线复位"（根端口 `BRIDGE_CONTROL` bit6）能让根端口重新发起链路训练，
如果端点只是 LTSSM 卡在某个中间态，这一下能救回来。
**实测今晚两次都无效** —— 说明端点不是"卡住"，是"死了"。

**只能断电重启**（真断电，不是 `systemctl reboot` 的软重启 —— 但软重启会让
BIOS 重新做 PCIe 枚举，实际也够用）。

### C. ZOMBIE —— 最阴的一种

今晚的主战场就是它：

```
1) lspci -Dn         : 在（0000:01:00.0 0302: 10de:1b87 (rev a1)）
2) sysfs             : 在
3) power_state       : D0              ← 不是 D3cold！
4) setpci 0.l        : ffffffff
5) CAP_EXP           : capability not found
6) 根端口 LNKSTA     : 5041 / d041     ← 有时还显示链路是通的
```

**设备在枚举表里、电源状态说 D0、但整条配置空间读不回来。**

成因（今晚的推断）：写 `0x8C040.SPEED=1` 请求 5 GT/s 后，端点 LTSSM 进入
Recovery → 重训失败 → 端点内部 PCIe 核死锁。它对外既不响应配置读，
也不报告错误（因为错误上报本身也要走配置空间）。

**为什么 `power_state` 还写 `D0`**：这是内核缓存的软件状态，
内核以为"我已经把它拉起来了"。**它不代表硬件真的上电了。**
这正是这个字段最坑的地方 —— 不能用它证明设备活着。

## 3. 快速判定流程（三步）

```bash
# 第 1 步：还在不在枚举表
lspci -Dn | grep -i 10de
#   不在 → B. GONE，重启

# 第 2 步：在的话，看是不是电源问题
cat /sys/bus/pci/devices/0000:01:00.0/power_state
#   D3cold → A. D3COLD，按 §2 的 unbind 流程救
#   D0     → 继续第 3 步

# 第 3 步：配置空间答不答
setpci -s 01:00.0 CAP_EXP+0x2c.l
#   ffffffff / capability not found → C. ZOMBIE，重启
#   正常数字                        → 设备健康
```

或者直接用探针：

```bash
sudo /data/labs/nvidia/pcie-gen2/pci-state.sh
```

实测健康设备上的输出：

```
1) lspci -Dn 枚举      : 在 ✓
2) sysfs 目录          : 在 ✓
3) power_state         : D0
4) 配置空间 0x00       : 1b8710de  ← 正常应答
5) PCIe 能力链         : 可解析  LNKCAP2=00000002
6) 上游根端口 0000:00:01.0 : LNKSTA=5041
7) dmesg               : 无 D3cold 专有关键字
★ OK —— 设备正常应答
```

## 4. 对我方脚本的影响（重要）

之前 `gen2-recipe.py` 用 `alive()` 判活：

```python
def alive():
    r = sh("lspci -Dn | grep -c '10de:1b87'")
    return r.stdout.strip() not in ("", "0")
```

**这个判据在 C 状态下会给出"活着"的错误答案** —— 今晚就是这样骗过了流程检查，
让它带着半死的设备继续走第 2 步，最终彻底掉线。

`gen2-v2.py` 已经改成读 BAR0 镜像 `0x880A4`（`LINK_CAP2`，稳定常量 `0x0002`/`0x0006`）：

```python
def mmio_alive(m):
    for i in range(GRACE):        # GRACE=20，参考源码纪律
        v = rd(m, R_CAP2)
        if v != 0xFFFFFFFF:
            return True, v
        time.sleep(0.02)
    return False, 0xFFFFFFFF
```

**这条是今晚最重要的工程教训**：

> PCIe 设备"活着"必须同时满足两件事：
> ① 配置空间能读（`setpci 0.l` 不是 `ffffffff`）
> ② MMIO 能读（BAR0 镜像常量寄存器能读回）
>
> 只查 `lspci` 是不够的 —— 它能在一个已经死掉的设备上返回"存在"。
