## 1. ★★★★★ 先纠正一个错误结论：SPEED=2 是软件写的

reports/195/197 曾断言：「SPEED 变 2 是链路降级时**端点内部（硬件/GSP）回写**，
CPU 不可见，软件拦不了」，并据此关闭了"再 patch 一个函数"这条路。

**这是错的。** 原因是那次 perf 断点没生效（`0x127e65`/`0x12803b` 报 0 次命中）。

本次四点断点，跑 **1 轮** `minictx`（1 个 CUDA 上下文）：

```
entry     0x127d60   1 次   DX=0x1                        ← mode = 1
or80000   0x127e65   1 次   AX 0x20505800                 ← 清掉 SPEED[19:18] 后的值
wr_shared 0x127edd   1 次   R8=0x20585800                 ← ★ SPEED=2 真的要写进去
bailret   0x1280c8   1 次
```

时间序（同一函数内，间隔 2~10µs）：
```
1103.125445  entry
1103.125453  or $0x80000        ← AX 从 0x20505800 变 0x20585800
1103.125455  wr_shared          ← R8=0x20585800
1103.125608  ret
```

⇒ **SPEED=2 完全由软件写入，CPU 可见。** 之前"拦不了"的判断作废。

## 2. mode=1 的完整静态路径（含一个容易误判的分支）

```
127d60  endbr64
127d64  push %r15
127d66  lea  -0x1(%rdx),%eax        ; eax = mode - 1
...
127d72  xor  %r12d,%r12d            ; ★ 返回值初值 = 0（SUCCESS）
127d7e  mov  %edx,0xc(%rbp)         ; 存 mode
127d81  cmp  $0x2,%eax
127d84  ja   1280c8                 ; (mode-1) > 2 → bail
127d8a  cmp  $0x2,%edx  ; je 1280d9  ; mode==2 → 能力门禁 obj[0x954]
127d93  cmpl $0x3,0xc(%rbp) ; je 128169 ; mode==3 → 能力门禁 obj[0x955]
127d9d  ← mode==1 顺序落入（不是跳转来的）

127ded  cmpb $0,0x4de5(%r13)
127df5  jne  1281a8                 ; ★ 这里只是**打一条警告日志**
                                      ;   1281a8: NV_PRINTF(id=0x137450) 然后 jmp 127dfb
                                      ;   不是 bail！很容易看错
127dfb  ...循环读 0x8C040，直到 (al & 0x1f)==0
127e4b  mov  0xc(%rbp),%ecx          ; ecx = mode
127e4e  and  $0xfff3ffff,%eax        ; 清 SPEED[19:18]
127e53  cmp  $0x2,%ecx ; je 12819b    → or $0x40000  (SPEED=1, Gen2)
127e5c  cmp  $0x3,%ecx ; je 12817f    → 保持 eax    (SPEED=0, Gen3)
127e65  or   $0x80000,%eax            → SPEED=2 (Gen1)   ★ mode==1 落在这里
127e6a  movl $0x1,0xc(%rbp)           ; 把存储的 mode 也改成 1
127e71  mov  %eax,0x20(%rbp)          ; 待写值
127edd  ...写 0x8c040
1280c8  ← 唯一 return：pop %rbx; mov %r12d,%eax; pop×4; add $0x40,%rbp; ret
```

## 3. 补丁：平移范围检查的边界（比 A/B/C 都干净）

### 方案对比
| 方案 | 改什么 | 评价 |
|---|---|---|
| A｜入口加 `cmp $1,%edx; je ret` | 需 code cave | 该函数没有空隙塞 5 字节；还要处理 `endbr64`/CET |
| B｜把 `je .mode1_case` 目标改成函数末尾 | —— | **不存在这条指令**：mode==1 是**顺序落入**，不是跳过来的 |
| C｜nop 掉 `or $0x80000` | 1 条指令 | 会继续落到 `movl $0x1,0xc(%rbp)`（改存储 mode），语义不清 |
| **本方案** | **2 个字节** | 边界平移，白名单收窄，零附带影响 |

### 改法
```asm
- 127d66: 8d 42 ff        lea  -0x1(%rdx),%eax     ; eax = mode - 1
- 127d81: 83 f8 02        cmp  $0x2,%eax
+ 127d66: 8d 42 fe        lea  -0x2(%rdx),%eax     ; eax = mode - 2
+ 127d81: 83 f8 01        cmp  $0x1,%eax
  127d84: 0f 87 ...       ja   1280c8              ; 不动
```

### 新 bail 条件（无符号比较）
| mode | mode-2 | > 1 ? | 结果 |
|---|---|---|---|
| 1 | `0xFFFFFFFF`（下溢） | 是 | **bail** ★ 唯一变化 |
| 2 | 0 | 否 | 继续 → Gen2 |
| 3 | 1 | 否 | 继续 → Gen3 |
| ≥4 | ≥2 | 是 | bail（**与原逻辑完全等价**，原本 mode>3 也 bail） |

⇒ **唯一的行为差异就是 mode==1 从"执行"变"bail"**，其余位、其余分支、其余 mode 全不变。

### 为什么 bail 是安全的
- `1280c8` 是函数**唯一**的 return 点
- `%r12d` 在 entry 就被 `xor %r12d,%r12d` 置 0；mode=1 路径里对 `%r12` 的改写
  （`lea 0x1e08(%r13),%r12`）恰好在我们跳过的代码里
- ⇒ bail 返回 **0 = CUDA_SUCCESS**，驱动认为设置成功，不报错、不重试

### 定位与校验
- 签名用 entry 到 `ja` 的**完整 32 字节序列**，全文件**唯一命中 1 处**
  （`0x127da6` 文件偏移 = `.text` 节内 `0x127d66`）
- 待改字节先校验再写，未命中/不唯一则拒绝
- 备份 `nvidia.ko.orig_nogen1`

```
md5  7f6805ed15f1ae8122aa78e65a5d48a0  （原始）
  →  514de9d4fdd7c407a088f1baf4b62f04  （补丁后）
```

### 反汇编核对（副本上验证后才动线上文件）
```
改前:  127d66: 8d 42 ff     lea  -0x1(%rdx),%eax
       127d81: 83 f8 02     cmp  $0x2,%eax
改后:  127d66: 8d 42 fe     lea  -0x2(%rdx),%eax
       127d81: 83 f8 01     cmp  $0x1,%eax
       （ja 目标 1280c8 及其余指令一字未变）
```

## 4. ★★★★★ 决定性验证：摘掉守卫，只留补丁

这一步是关键 —— 带着守卫测是测不出补丁作用的（守卫会把链路拉回来）。
所以推上 Gen2 后**把 gen2kr 整个卸掉**，只留补丁：

```

第 1 轮后: CAP2=0x0006 LNKSTA=2 TLS=2 SPEED=1
第 2 轮后: CAP2=0x0006 LNKSTA=2 TLS=2 SPEED=1

再等 10s : CAP2=0x0006 LNKSTA=2 TLS=2 SPEED=1     ← 也不是延迟降级
Xid: 无（唯一的 XID 是网卡 r8169）
```

**一次都没掉。**

## 5. 这套方案改变了什么

| | 旧（gen2kr 守卫） | 新（补丁 + gen2kr 仅 push） |
|---|---|---|
| 机制 | 降级后 3.8s 内拉回 | **根本不降** |
| 链路状态 | 在 Gen1/Gen2 间反复跳 | **常驻 Gen2** |
| 对 DMA 的影响 | 恢复窗口内测到 Gen1 带宽（0.78） | 无窗口，带宽恒定 |
| 需要常驻模块 | 是（守卫要一直跑） | **否**（push 完即可卸载） |
| 测量方法敏感 | 强烈（短测必踩坑） | 不敏感（512MB/128MB 都一样） |

### 对 gen2kr 的影响
补丁后 gen2kr 只剩两件事必须做：
1. `nv_pci_probe` 返回瞬间：解锁声明 + 写 SPEED=1 + 触发训练 + 根端口 Retrain
2. 之后链路自己保持，**守卫可以完全不启用**

⇒ 可以把 gen2kr 退化成一个"跑一次就退出"的模块
（`guard_rounds=N` 小值，或加一个 `no_guard` 参数）。
**这是下一轮该做的简化。**

### 但建议**保留守卫**作为安全网

理由：补丁是二进制补丁，**驱动升级 / DKMS 重编就会丢失**。
丢了以后：
- 没人告诉你补丁失效了
- 链路会在下次 `cuInit` 静默降回 Gen1，带宽腰斩，且无任何报错

守卫正好补这个缺口：它只看 `LNKSTA`，补丁在时零动作（链路不掉），
补丁丢时才会动手。所以「补丁 + 守卫」是双保险，不是冗余。

**代价**：守卫常驻要每 200ms 读一次 BAR0（极轻），可以接受。

### 遗留注意
- 补丁是**内核模块二进制补丁**，驱动升级/重编会丢失，需要重新 apply
  （`python3 patch_no_gen1.py check` 可随时自查）
- 仍需要声明解锁（`LCAP2=0x06`）——硬件只有声明支持 5GT 才会协商上去
- 补丁只针对 Pascal（`P104/P106`）；Ampere 的 SPEED 编码不同（2=5GT），**不能照搬**
- **`mode=2` / `mode=3` 路径未实测**：本卡驱动只以 mode=1 调用，
  无法自然触发 2/3。静态分析显示这两条路径的判据与分支一字未改，
  但"没跑过"就是"没跑过"，不能声称已验证。
  若将来要在此补丁下使用 Gen3 卡，必须先单独验证 mode=3。
