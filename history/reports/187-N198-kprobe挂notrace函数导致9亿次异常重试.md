# N198 — 重大失误与反证：kprobe 挂 notrace 函数导致 9.26 亿次异常重试

**日期**：2026-10-29 06:30–07:00
**起因**：继续验证"拦截驱动写 SPEED"这条路（静态分析得出写函数是 `_nv053912rm`）
**结果**：**方案不可行，且我的实现造成严重性能事故。但反证出一个有价值的事实。**

---

## 0. 必须先说的错误

| 项 | 我做的 | 实际 |
|---|---|---|
| 认为 `_nv053912rm` 可 kprobe | 静态分析出符号 + kallsyms 地址吻合 ⇒ 写了模块挂上去 | **该函数是 `notrace`**，`register_kprobe` 不检查这个属性，强行挂上去会破坏其执行 |
| 认为"驱动每秒写 154 万次 0x8C040" | 看到 `hit_patched = 925,622,205` 就下结论 | **那些全是我的 kprobe 造成的异常重试**，不是驱动的正常行为 |
| 因此 load 5.95 | 以为是驱动忙等 | **是我自己烧的** |

**正确做法**：挂之前先用 `bpftrace` 探测可挂性。它一开始就明确报了：

```
WARNING: _nv053912rm is not traceable (either non-existing, inlined, or marked as "notrace")
cannot attach kprobe, Invalid argument
```

我绕过了这个警告（用 `register_kprobe` 硬挂），才酿成事故。

## 1. 事故数据

```
gen2kp: 已卸载。总调用 926009787，拦截改写 925622205 次
```

模块存在约 10 分钟 ⇒ **约 154 万次/秒**。

同时 `load average` 从 ~1 升到 **5.95**（该机 4 核）。

卸载后：

```
load average: 5.95 → 5.04 → 3.69 → 2.08   （逐分钟回落）
1 秒内 0x8C040 只有 1 种值 0x20585800（稳定不变）
```

**⇒ 高频写完全由 kprobe 引起，与驱动无关。**

### 1.1 机理推测

`_nv053912rm` 是 RM 的寄存器写封装，内部很可能有"写 + 读回校验 + 重试"。
我在 `pre_handler` 里把 `r8`（要写的值）从 `SPEED=2` 改成 `SPEED=1`，
函数内部校验发现值不对 ⇒ 重试 ⇒ 我又改 ⇒ 无限循环。

外加它被标记 `notrace`，说明厂商不希望任何插桩进入，强行进桩本身就可能破坏其状态。

**两层问题叠加，导致灾难性后果。**

## 2. ★ 反证出的重要事实：驱动正常状态下**不写** `0x8C040`

用完全不碰内核的方式（mmap BAR0 高频采样，纯用户态读）测真实写频率：

```
空闲 2s:  采样 1,666,717 次,  0x8C040 变化 0 次, 末值 0x20585800
CUDA 8s:  采样 2,370,281 次,  0x8C040 变化 0 次
```

**两次都是 0 次变化。** 采样率约 30 万~80 万次/秒，足够捕捉任何写操作。

⇒ **驱动在空闲和稳态 CUDA 运算时，都不会主动写 `0x8C040`。**

### 2.1 这修正了之前的认知

之前（reports/184）看到守卫日志：
```
[184.889] [guard] SPEED 被改回 20585800，已按回 1（第 1 次）
[185.928] [guard] SPEED 被改回 20585800，已按回 1（第 2 次）
```
我据此认为"驱动在持续回压"。现在的数据说明：
**它不是持续写，而是偶发**（在特定事件后写一次）。

### 2.2 但 reports/187 的观测仍然有效

那次看到：
```
[ 3.08s] SPEED=2 LNKSTA=0x1041  ← CUDA 启动瞬间
```
这是**一次性的、与事件绑定**的写，不是持续行为。

**尚未确定触发条件**。候选：
- 新建 CUDA 上下文（`bwtest2` 是新进程）
- 驱动 devinit / 电源状态切换
- `nvidia-smi` 类查询

今天测的"CUDA 期间 0 变化"是**同一个上下文内的循环传输**，可能不触发。

⇒ **下一步必须用"新进程"重现**，而不是在已建上下文的进程内循环。

## 3. 一个有价值的副产品：带宽确实到过 1.550/1.679

在那个错误的拦截模块生效期间：

```
带宽：pinned H2D 1.550  D2H 1.679 GB/s
测后端点: 1042  （链路保持 Gen2）
Xid: 0
```

**虽然实现方式错误，但这证明了一个因果链**：

> 只要 `0x8C040.SPEED` 持续保持为 1，链路就能在真实 DMA 期间保持 Gen2，
> 带宽达到 1.55/1.68，且不产生 Xid 79。

这与 reports/184（kretprobe 方案）的结论互相印证：
**"SPEED 必须保持 1" 是关键，不是"偶尔按回"就够。**

## 5. 为什么 kretprobe 挂 `nv_pci_probe` 没出问题

`nv_pci_probe` 是驱动的 probe 函数，**正常可插桩**（bpftrace 能挂）。
而且它只在 probe 时调用一次，频率极低。

**区别**：
- 可插桩函数 + 低频调用 = 安全
- **notrace 函数 + 高频调用 = 灾难**

## 6. 教训（要写进纪律）

### 6.1 挂 kprobe 前必须验证可插桩性

```bash
bpftrace -e 'kprobe:<symbol> { }' -c true     # 报 not traceable 就不要挂
```

**`register_kprobe` 不检查 notrace 属性** —— 它能成功返回 0，但函数行为可能被破坏。
"挂上了"不等于"挂对了"。

### 6.2 用"总次数"做健康检查

任何插桩模块都应该暴露调用计数。**如果短时间内计数达到百万级，立即卸载。**

### 6.3 看到异常大的计数，先怀疑自己的插桩

9.26 亿次 / 600 秒 = 154 万次/秒。任何"驱动每秒写百万次寄存器"的结论，
在下结论前都该先想想：**是不是我的探针导致的？**

验证方法：**卸载探针，用纯用户态方式测同样的量**。
这次就是靠 mmap 高频采样（166 万次/2 秒，0 变化）一眼看穿的。

### 6.4 修改变量参数前先想清楚调用方是否有校验

拦截写操作并改值，如果被拦截的函数内部有"写-读回-校验-重试"，就会死循环。
**这类函数不能靠改参数拦截，只能靠"事后纠正"（post_handler / 外部按回）。**
