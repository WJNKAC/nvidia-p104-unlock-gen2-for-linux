# 与参考项目的一致性对比

**参考**：`github.com/skbskhud/p104-gen2-unlock`（P104-100，Windows，Gen1 x4 → Gen2 x4）
**本机**：P104-100 `10DE:1B87` rev A1，VBIOS `86.04.7A.00.19`，Linux 6.12.113 + 驱动 580.178.04
**日期**：2026-10-28

---

## 0. 结论

**一致性很高，而且高到可以互相验证的程度。**

我们在 PCIe **配置空间层**做的每一个阴性结果，都和参考项目记录的现象**逐条吻合**。
这说明：不是我们的环境特殊、也不是测量错了，而是**这一层本来就不是开关所在**。

参考项目走通了下一层（**BAR0 内的 GPU 私有寄存器**），并给出了确切的地址、位定义和实测矩阵。
**这一层我们还没试过。**

## 1. 逐项对照

| 项目 | 参考项目（他的卡） | 本机实测 | 判定 |
|---|---|---|---|
| PCI ID | `10DE:1B87` subsys `10DE:1237` rev A1 | `10DE:1B87` rev a1 | ✅ 同型号 |
| 上游根端口声明 | `00:01.0` Gen4 x16 | `00:01.0` LnkCap2=`0x0e`（Gen4） | ✅ 一致 |
| `LNK_CAP`(0x84) Gen1 态 | `0x00463C41` | **`0x00453C41`** | ✅ 仅差 bit17（SDERC） |
| `LNK_CAP` 的 SPEED 位 | 1（2.5GT/s） | 1（2.5GT/s） | ✅ |
| **链路宽度** | **x4**（他标注"这张卡就是 x4"） | **x16** | ⚠ **不同**，我们更宽 |
| `LNKSTA` Gen1 态 | `0x1041`（speed=1, width=4） | `0x1101`（speed=1, width=16） | ✅ 速率同、宽度不同 |
| `LNKCAP2`(0xA4) | `0x00000002`（只声明 Gen1） | `0x00000002` | ✅ **完全一致** |
| `LNKCTL2`(0xA8) Gen1 态 | `0x00000000` | `0x00000000` | ✅ 完全一致 |
| 写 `LNKCTL2` = 2 | **被硬件钳回**（"温度计，不是开关"） | 写 `0x0002` → 读回 `0x0000`，**被忽略** | ✅ **同一现象** |
| 写 `LNK_CAP` 改声明 | 配置空间侧不可写 | 写 `3c42` → 读回 `3c41` | ✅ 一致 |
| 写 `LNKCAP2` 改声明 | 需走 BAR0 层 | 写 `0x06` → 读回 `0x02` | ✅ 一致 |
| 能力结构版本 | 实测 `EXP_HEAD` 在 v1/v2 间**随状态变** | `lspci` 报 **v1** | ✅ 与"Gen1 态=v1 模式"一致 |

**⇒ 我们读到的每一个值，都能在他的表里找到对应行；我们遇到的每一次写失败，他都记录过。**

## 2. 我们少走的那一层：BAR0 私有寄存器

参考项目的关键结构（`docs/04-硬件事实表.md`）：

```
本卡 BAR0 前 64 KB 与配置空间是 1:1 影子：BAR0[0x88000 + N] ≡ 配置空间[N]
（他实测 19/19 一致）

所以 0x88084 = 配置空间 0x84 = LNK_CAP  ← 我们试过，只读
     0x880A8 = 配置空间 0xA8 = LNKCTL2 ← 我们试过，被钳回
```

**真正的开关在别处：**

| 地址 | 名字 | 作用 | 是否需复位 |
|---|---|---|---|
| **`0x2241C`** | `PUNITS.PCI` | bit0=PCIE_VERSION，**bit7=PCIE_SPEED**：写 1 → Gen2 | **不需要，立刻生效** |
| **`0x8C040`** | `LINK_CONFIG_0` | **SPEED[19:18]：2=2.5GT/s，1=5.0GT/s**（反直觉映射）；**bit0=COMMIT** | 不需要 |
| `0x8841C` | `CONFIG`（能力字段生成器输入） | `[14:13]==3` 强制降 Gen1；`[15]` 复位前置 1 → 复位后锁 Gen2 | `[15]` 需要 |
| `0x8872C` | LTSSM 触发 | 写 6 = 触发 | 不需要 |

**他的实测值对照**：

```
0x8C040:  Gen1 态 0x20585800   Gen2 态 0x20545800
          (>>18)&3 = 2（2.5GT/s）      = 1（5.0GT/s）
0x2241C:  Gen1 态 0x00000000   Gen2 态 0x00000081
0x8841C:  冷启动   0xC0B46500   Gen2 态 0xC0B5AD00 / 0xC0B58D00
```

**Gen2 成立的条件（他的 8 组矩阵里唯一成功的一组）**：

```
LTSSM(0x8872C) = 6   AND   0x8841C[14:13] = 0   AND   0x2241C[7] = 1
    → 声明 0x06（支持 Gen1+Gen2）
```

单独写 `0x2241C[7]=1` 但 LTSSM 没触发 → 仍只有 `0x02`。

## 3. 熔丝：为什么最多只能到 Gen2

参考项目读了三个只读熔丝（BAR0 地址 = community 地址 − 0x7FF000）：

| 熔丝 | BAR0 | 实测值 | 含义 |
|---|---|---|---|
| `GEN23_DIS` | `0x02157C` | **1** | Gen2/Gen3 被禁用 |
| `GEN3_DIS` | `0x021580` | **1** | Gen3 被禁用 |
| `LANE_DIS` | `0x021394` | 0 | 宽度未被熔丝关闭 |

外部交叉验证：同类卡（CMP 170HX / GA100）在同一组地址读到 **完全相同的三个值**，
且用完全不同的方法（安全协处理器级写入）**也只做到 Gen2**。

**⇒ 这解释了"为什么 Gen3 不可达"，而且和"Gen2 可达"不矛盾**——熔丝禁的是 Gen3，
Gen2 是被另一组 live 通路（0x2241C / 0x8C040）压在 Gen1 上的。

## 4. 我们此前的判断 vs 他的记录

| 我们说过 | 他的记录 | 关系 |
|---|---|---|
| "LnkCap 硬只读，setpci 写不进" | "全 4KB 配置空间只有 Command/CacheLine 可写"（后被自己修正为 `0x41C` 可写） | ✅ 一致（他的 `0x41C` 是 **BAR0 的 0x8841C**，不是 config space） |
| "Express v1，没有 LnkCap2 字段" | `EXP_HEAD` 版本位在 v1/v2 间随状态变，**Gen1 态就是 v1** | ✅ 一致，且解释了为什么 lspci 报 v1 |
| "Retrain 后仍 Gen1" | 单写 LNKCTL2 或单触发都不够，需要三者组合 | ✅ 我们的打法缺条件 |
| "P106 也试过，同样只读" | 未测 P106 | ⚠ 我们的独有数据 |

**⚠ 一处我们必须承认的偏差**：参考项目在 `03-走过的弯路.md` §3.3 记了同款教训——
"写通道用错一个数字，得到一整批'寄存器只读'的假结论"。
我们虽然每次都做了读回校验（写后读回≠期望值即判失败），但**只验了配置空间这一条通道**，
没有尝试从 BAR0 写同一个逻辑字段。这是方法上的漏项。

## 5. 危险清单（他的血泪，我们照单全收）

| 禁止 | 实测后果（他的原话） |
|---|---|
| **对 `0x8C040` 做逐位写走查** | **显卡掉下 PCIe 总线**，只能重启 |
| 对含 COMMIT / 使能 / 复位语义的寄存器逐位走查 | 每一位都可能触发硬件动作 |
| 一次会话内整卡复位超过 2–3 次 | 他做过 9 次，属超限 |
| 不做对照写入就下"只读"结论 | 写通道可能本身是坏的 |

**⇒ 如果我们要动 `0x8C040`，必须整字写（读改写），绝不逐位试。**

## 6. 下一步（Linux 上可行，且不需要 Windows 驱动）

参考项目用 `WinRing0x64.sys + ThrottleStop.sys` 两个内核驱动访问物理内存/MMIO。
**Linux 上不需要这些**——直接 mmap BAR0：

```
/sys/bus/pci/devices/0000:01:00.0/resource0   →  mmap，按字节偏移读改写
```

**建议实验顺序**（每步都读 `LNKSTA[3:0]` 判定，不采信声明值）：

| # | 动作 | 判据 | 风险 |
|---|---|---|---|
| 1 | 只读：dump `0x8C040` / `0x2241C` / `0x8841C` / `0x8872C` / `0x88088` | 与他的 Gen1 值对照 | 无 |
| 2 | 写 `0x2241C` bit7=1（整字 0x00000081）+ `0x8872C`=6 | `LNKSTA[3:0]==2` | 低 |
| 3 | 若 2 不够：`0x8C040` 的 SPEED[19:18]=1 + bit0=COMMIT（整字读改写） | 同上 | 中（他要掉过卡） |
| 4 | 若成功：实测带宽、跑一次 GL 测试确认稳定 | — | 低 |

**掉卡也不影响我们**：显示在 Intel 核显，SSH 走网卡，显卡掉线只需重启（寄存器改动不持久）。

## 7. 边界

- 本文的"他的数据"全部引自仓库文档，**未经我独立验证**（我没有 Windows 环境和他那张卡）。
- 本机的数值（`0x00453C41` / `0x1101` / `0x02` / `0x0000` / 三处写失败）**都是实测**。
- 我们与他的**宽度不同**（x16 vs x4），所以即使解锁成功，带宽目标的参照值不能直接照搬
  （他是 0.78→1.55 GB/s；我们理论是 Gen1 x16 ≈ 4 GB/s → Gen2 x16 ≈ 8 GB/s，需实测）。
- 熔丝 `GEN23_DIS=1` 意味着**最多 Gen2，不要指望 Gen3**。
