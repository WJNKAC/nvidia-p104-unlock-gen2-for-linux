# Issue #1 回复 —— 针对性短版

---

先说清楚：我们已经在 Linux 下做成了（上面那个仓库就是），
所以下面只针对你 issue 里给的那三步逐条对一下。

## 第一步：`lspci -vv` 看 `LnkCap2` bit1

我们的卡读出来是 `LnkCap2 = 0x00000002`，**bit1 = 0**，压根没声明 5.0GT/s。
（你报告 §1.2 也是这个值，应该知道）

所以「如果声明了 5GT/s 但停在 2.5GT/s」这个前提在我们这里不成立 ——
真正要做的是先把声明打开，这得写 NVIDIA 私有 BAR0，`setpci` 够不到。

## 第二步：`LnkCtl2` 低 4 位写 2

这一步单独做**没用**，会被硬件直接钳回。

依据是你自己 §4.1 的实验：声明 `0x06` 时写 `LnkCtl2=3` → 读回立刻是 2，4527 次全被钳。
⇒ 硬件把 `LnkCtl2` 钳到**声明的上限**。声明还是 `0x02` 时，写 2 会被钳回 1。

## 第三步：`remove + rescan`

有两个问题：

1. **对速率没用。** 声明没解锁，rescan 只是重新枚举，`LnkSta` 不会变。
2. **`remove` 前要先 `unbind` 驱动。** 我们实测驱动还绑着时 remove 容易落到 D3cold，rescan 后设备不回来；先 unbind 就 0.5 秒回来。

另外：就算前两步成功了，链路也保不住 —— **NVIDIA 驱动每次 `cuInit` 都会主动把速率降回 Gen1**
（`_nv017105rm(mode=1)`，perf 实测 4/4 次）。这条在你的「待确认」清单里，答案是「会」。

## 所以 Linux 上要加两步

- **解锁声明**：写 BAR0 `0x8E11x` / `0x8841C`（读值再 OR）/ `0x88610`，再 `0x8872C=6` 触发训练
  ⇒ `LnkCap2` 当场变成 `0x06`。**这一步不需要复位，也不需要 PnP**（你 Windows 那套
  PnP + 25 秒是为绕开驱动压回，不是硬件必需）
- **让驱动别降**：我们是给 `_nv017105rm` 打了 2 字节补丁，比"每 20ms 按住"省事得多

## 你 README 里那条「输出示例」

`LINKCAP2 = 0x00000006` —— 但脚本里 grep 不到任何写 `0x8841C` / BAR0 的地方。
既然脚本做不到解锁声明，这一步就不可能读到 `0x06`，那段应该是从 Windows 版输出粘过来的。
