# Issue #1 回复 —— 定稿（可直接粘贴）

先说清楚：我们已经在 Linux 下做成了（上面那个仓库），所以只针对你给的三步逐条对一下。

**第一步：`lspci -vv` 看 `LnkCap2` bit1**

这里有个小坑：**P104 这个寄存器的 `SLSV` 是从 bit1 起算的**，不是标准的从 bit0 起
（你 `04-硬件事实表` §2.5 里也是这么记的：`bit1=2.5、bit2=5.0、bit3=8.0`）。

所以按标准规范去看 bit1，会读到 1 而误以为"已支持 5.0GT/s"。实际：

```
LNKCAP2 = 0x00000002    SLSV = 0b001   只有 2.5GT/s
LNKCAP2 = 0x00000006    SLSV = 0b011   2.5 + 5.0GT/s   ← 解锁后
```

差别在 **bit2**。我们卡出厂就是 `0x02`，压根没声明 5.0GT/s（你报告 §1.2 也是这个值）。

所以「如果声明了 5GT/s 但停在 2.5GT/s」这个前提在我们这里不成立——真正要做的是先把声明打开，
这得写 NVIDIA 私有 BAR0，`setpci` 够不到。

**第二步：`LnkCtl2` 低 4 位写 2**

这一步单独做没用，会被硬件直接钳回。

依据是你自己 §4.1 的实验：声明 `0x06` 时写 `LnkCtl2=3` → 读回立刻是 2，4527 次全被钳。
⇒ 硬件把 `LnkCtl2` 钳到**声明的上限**。（← 这是我们的推断，基于你的数据；下一条可以实测验证）

**第三步：`remove + rescan`**

两点：

1. 对速率没用。声明没解锁，rescan 只是重新枚举，`LnkSta` 不会变。
2. `remove` 前要先 `unbind` 驱动。我们实测驱动还绑着时 remove 容易落到 D3cold、rescan 后设备不回来；
   先 unbind 就 0.5 秒回来。

另外，就算前两步成功，链路也保不住——**NVIDIA 驱动每次 `cuInit` 都会主动把速率降回 Gen1**
（`_nv017105rm(mode=1)`，perf 实测 4/4 次）。这条在你「待确认」清单里，答案是「会」。

**所以 Linux 上要加两步**

- **解锁声明**：写 BAR0 `0x8E11x` / `0x8841C`（读值再 OR）/ `0x88610`，再 `0x8872C=6` 触发训练
  ⇒ `LnkCap2` 当场变 `0x06`。**这步不需要复位，也不需要 PnP**——你 Windows 那套
  PnP + 25 秒是为绕开驱动压回，不是硬件必需。
- **让驱动别降**：我们是给 `_nv017105rm` 打了 2 字节补丁，比「每 20ms 按住」省事得多。

**顺便提一下你 README 的输出示例**

`LINKCAP2 = 0x00000006`——但脚本里 grep 不到任何写 `0x8841C` / BAR0 的地方。
既然脚本做不到解锁声明，就不可能读到 `0x06`，那段应该是从 Windows 版输出粘过来的。
