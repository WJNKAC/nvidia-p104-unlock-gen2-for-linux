## 为什么这样跑不通 —— 用你们自己的实测数据就能推出来

你们 `01-技术报告` §4.1 做过一个很干净的实验：

> 在 Gen2 稳态（声明 `0x06`）下，写 `LNKCTL2[3:0] = 3`（8.0 GT/s）→ **读回立刻是 2**。
> 六次采样全是 2；另一组持续 25 秒写 4527 次，**全部被钳回 2**。

⇒ **硬件把 `LnkCtl2` 钳到"声明的上限"**，这是你们自己测出来的。

而 P104 原厂 `LNKCAP2 = 0x0002`（你们 §1.2 也写了）。两条合起来：

> 声明上限 = Gen1 ⇒ 写 `LnkCtl2 = 2` 会被钳回 `1`。

这是**推断**，不是我实测的（要实测得把卡重启回原厂状态再跑你们脚本）。

## 顺便纠正我上一版的另一个错误

我上一条说「他的第 2 步依赖 Windows PnP，Linux 无等价物，所以少了第一根支柱」——**这句也不对**。

我们实测：**Linux 上声明解锁不需要复位，也不需要 PnP**。
写完 `0x8841C` 那组使能位 + `0x8872C`，`LNKCAP2` 当场从 `0x02` 变 `0x06`（我们的实验报告 187）。

所以你们 Windows 版那套「PnP 禁用/启用 + 等 25 秒」，
本质是**为了绕开 Windows 驱动把这些位压回去**，不是硬件的必要条件。
Linux 上直接写 BAR0 就行 —— 但**必须在驱动不来抢的窗口里写**，这点两边一样。

## 你们 README 的「待确认」第 2 条，我们有确切答案

> NVIDIA 闭源驱动是否会在驱动重置后把目标速率写回 Gen1（需要实测）

**会，而且比"驱动重置后"更频繁：每次 `cuInit` 都会。**

```
每次 cuInit
 └─ rm_init_adapter+0xcd
     └─ _nv017755rm        if (mode == 当前速率) return;
         └─ _nv017105rm(mode=1)  → 写 0x8C040.SPEED=2 (2.5GT/s)
```

`mode=1` 就是 Gen1。perf 硬件断点实测：**4/4 次都以 `DX=0x1` 进这个函数**。

所以即使你成功把链路推上 Gen2，**第一次建 CUDA 上下文就被打回去**。
这条我认为是 Linux 上最关键、也最容易被漏掉的一环 ——
它不在 PCIe 规范里，只在驱动内部。

## 我们的两个绕法（分别对应上面两个坑）

**坑一（声明没解锁）** → 写 BAR0 私有寄存器，不能只靠 `setpci`：

```
0x8E110/0x8E11C/0x8E120/0x8E12C  →  XP3G 槽
0x8841C  →  读值再 OR，置 bit11/13/15，清 bit12/14（bit15 是你们说的「复位前置值」）
0x88610  →  清 bit12，置 bit0
0x8872C = 6  →  触发训练，声明当场锁存成 0x06
```

**坑二（驱动降级）** → 2 字节补丁改 `_nv017105rm` 的 mode 白名单：

```asm
- lea -0x1(%rdx),%eax   ; eax = mode - 1
- cmp $0x2,%eax
+ lea -0x2(%rdx),%eax   ; eax = mode - 2
+ cmp $0x1,%eax
  0x127d84: ja 1280c8   ; 不动
```

`(mode-2) > 1` 无符号：`mode=1` 下溢成 `0xFFFFFFFF` → bail；`2/3` 照旧；`≥4` 与原逻辑等价。
bail 跳到函数唯一的 return，返回 `%r12d`（入口被 `xor` 清零）⇒ **0 = CUDA_SUCCESS**，驱动无感。

之后就不需要"每 20ms 按住"了 —— 因为没人再降它。

实测：353 轮 CUDA 上下文零降级、Xid 0、pinned H2D 1.56 / D2H 1.71 GB/s。

## 你们脚本里我看到两个额外风险，供参考

1. **`remove` 前没卸 nvidia 驱动。** `rescan_one()` 直接 `echo 1 > remove`。
   我们实测：驱动还绑着时 `remove` 容易落到 D3cold，rescan 后设备不回来
   （先 `unbind` 再 `remove` 就没事，0.5 秒回来）。

2. **`sleep 1` vs 你们 Windows 报告的 ≥25 秒。**
   如果 Linux 上确实不需要那么久（我们观察是不需要），那没问题；
   但如果 P106 上撞到同样的锁存延迟，这个值要能调。
