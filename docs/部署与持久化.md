# 部署与持久化

> 对应原始研究记录 reports/200（未随仓库发布）。
> 结论一句话：**补丁能"保持"，但必须有人"建立"。两者缺一不可。**

---

## 一、为什么重启会回到 Gen1

方案由两部分组成，作用完全不同：

| 组件 | 作用 | 存在形式 | 重启后 |
|---|---|---|---|
| **2 字节补丁** | 让驱动**不再**把链路降回 Gen1 | 改 `nvidia.ko` 二进制 | **保留** |
| **gen2kr.ko** | 在 `nv_pci_probe` 返回瞬间**解锁声明 + 推送** | 独立内核模块，手动 `insmod` | **丢失** |

上电流程：

```
开机
 └─ modprobe nvidia → probe
      · 端点声明被重置为 Gen1（LCAP2 = 0x02）
      · 补丁让人"不降"，但也没人"升"
 └─ 链路停在 2.5GT/s   ← 到这里就卡住了
```

必须有东西在 **probe 返回那一刻**（RM 内部初始化之前）做三件事：

1. 解锁端点声明：`XP3G` 四个寄存器 + `0x8841C` 读值再 OR + `0x88610` → `LCAP2` 变 `0x06`
2. 写 `0x8C040.SPEED=1`（5.0GT/s）
3. 两端 `LNKCTL2` TLS=2，从根端口 Retrain

这三件事只能在**内核里**做 —— 用户态脚本抢不到那个窗口，而且在链路动态时
用用户态 `mmap` 写 BAR0 **会打挂设备**（实测 2/2，C. ZOMBIE，`dmesg` 无 Xid）。

## 三、补齐只要两条命令（不用重载 nvidia）

**关键认识：`unbind/bind` 就足以触发一次 `nv_pci_probe`，让 gen2kr 的 kretprobe 命中。**

只有"改了 `nvidia.ko` 文件"时才必须重载 —— 不重载的话内核里跑的还是旧代码。
补丁早在 `.ko` 里时（重启后就是这种状态），完全不碰 nvidia 就能完成推送：

```bash
# 1. 挂 kretprobe（gen2kr 的 init 只挂 probe，本身不做推送）
sudo insmod build/gen2kr.ko

# 2. 让设备重新 probe 一次
echo 0000:01:00.0 | sudo tee /sys/bus/pci/drivers/nvidia/unbind
echo 0000:01:00.0 | sudo tee /sys/bus/pci/drivers/nvidia/bind

# 3. 验证
sudo python3 bin/peek-regs.py            # LNKSTA CurSpeed=2
sudo lspci -vv -s 01:00.0 | grep LnkSta  # Speed 5GT/s
build/bwtest2 512 15 | grep pinned       # ~1.56/1.71
```

或者一条命令：

```bash
sudo bash bin/push.sh
```

### 实测日志（reports/201）
```
[fast] 直接写 SPEED=1，原 20045800 → 20045800
[push] 起始 cap2=00000006 config=c0b48d00 lnkcfg0=20045800
[push] 写完 cap2=00000006 config=c0b4ad00 lnkcfg0=20045800
端点 TLS2 0002 -> 0002
根端口 TLS2 0042 -> 0042
根端口 LNKCTL 0040 -> 0060 (Retrain)
★ SUCCESS Gen2 LNKSTA=1042（第 1 次）
```
→ 链路 5GT/s，pinned **H2D 1.561 / D2H 1.708 GB/s**，**nvidia 全程未被卸装/重载**。

注意日志里 `config=c0b48d00`：`unbind` 确实把 `0x8841C` 的解锁位清掉了
（`ad00` → `8d00`），但 `push_fn` 会重新写一遍（→ `c0b4ad00`）。
所以每次 unbind/bind 后 push 都会重新做完整的解锁+推送，不依赖残留状态。

### 什么时候必须重载

| 场景 | 要重载吗 |
|---|---|
| 刚 `patch_no_gen1.py apply`（.ko 变了） | **要** |
| 重启后（补丁早在 .ko 里） | **不要** |
| 补丁丢失后重新 apply | **要** |

`bin/20-install.sh` 会自动判断（比对 apply 前后的 md5）：

```
✓ 补丁是新写入的 ⇒ 需要重载 nvidia 才生效
✓ 补丁本来就在（.ko 未变）⇒ 不需要重载
```

也可以强制不重载：`sudo bash bin/20-install.sh --no-reload`

## 四、三个自动化选项

### A. 手动（当前采用）

开机后（或任何需要重新推送时）：

```bash
sudo bash bin/push.sh        # 在仓库根目录执行
```

- 只做 `insmod` + `unbind/bind`，**不碰 nvidia**
- 约 3 秒
- 实测有效（见上）

补丁丢失时另需 `20-install.sh`（会 apply + 重载）。

### B. modprobe softdep + gen2kr 加 init 推送（未实现、未验证）

思路：
1. 给 `gen2kr` 加"`__init` 里若设备已绑定就直接调 `push_fn()`"
2. `/etc/modprobe.d/nvidia.conf` 加一行：`softdep nvidia post: gen2kr`

为什么可能可行（**静态推理，未实测**）：
- nvidia 的 `pci_register_driver()` 在模块 init 里**同步**完成 probe
  ⇒ `modprobe nvidia` 返回时设备已绑定
- `softdep ... post:` 让 gen2kr 紧接着加载 ⇒ 此时设备已绑定，可以直接 push
- `push_fn` 用 `ioremap` + `msleep(50)`，在模块加载的 process context 里可以睡眠

需要先确认的三点：
1. 加载时设备确实已 probed & bound
2. 不会被 kretprobe 的 `triggered` 标志挡住
3. 推送失败时不会留下"半解锁"状态

侵入性低（一个配置文件，无 systemd 单元），但仍属于"开机自动动硬件"。

### C. systemd service（不推荐）

```bash
sudo cp drivers/580.178.04/kernel/6.12.113/gen2kr.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now gen2kr.service
```

最简单直接，但会留一个 systemd 单元。当前用户明确要求不装。

## 五、`unbind/bind` 与 `rmmod/modprobe` 对声明的影响（实测）

| 操作 | `0x8841C` 解锁位 | `LCAP2` | 链路 |
|---|---|---|---|
| `unbind` + `bind` | **被清**（`c0b4ad00` → `c0b48d00`） | 保持 `0x0006` | 保持 Gen2 |
| `rmmod nvidia` + `modprobe nvidia` | **保持解锁** | 保持 `0x0006` | 保持 Gen2 |

**两个都要注意**：

1. **`unbind/bind` 会清 `0x8841C`，但不影响 push** —— `push_fn` 每次都会重写。
2. **`rmmod/modprobe` 不会复位到原厂** —— 别指望用它把设备"恢复原状"做测试。
   真正能复位的只有整机断电。

> ⚠ reports/198 曾记录"reload 会把声明重置回 Gen1"，那是当时做过总线复位的场景。
> 单纯 `rmmod` + `modprobe` 不会重置。这里修正。

想快速回"未解锁"状态做测试：
- `rmmod nvidia && modprobe nvidia` **不行**（声明保留）
- 整机重启 **可以**（但注意整机断电才彻底）

## 六、补丁会丢的情况

| 场景 | 补丁 | 该怎么办 |
|---|---|---|
| 重启 | 保留 | 跑一次 `20-install.sh` |
| `apt upgrade` 升级 nvidia 驱动 | **丢失** | 重新 `20-install.sh`（会重新 apply） |
| DKMS 重编（换内核等） | **丢失** | 同上 |
| 换内核但驱动没重编 | 保留 | 跑一次 `20-install.sh` |

随时自查：

```bash
sudo python3 bin/patch_no_gen1.py check
# [已打补丁] → 正常
# [未打补丁] → 跑 20-install.sh
```

**两种丢失的后果不同，别混淆**：

- 补丁丢了 → 驱动会主动降级，链路在 Gen1/Gen2 之间反复跳，带宽不稳
- gen2kr 丢了 → 链路压根升不上去，开机就是 0.78，一眼就能发现

后者更容易察觉，所以实际使用中"忘记跑 20-install"是最常见的故障。
