# 安全纪律（每条都是真实事故换来的）

---

## 铁律 1：判据只能用寄存器

`nvidia-smi` 的**任何** PCIe 字段都是驱动缓存。寄存器已是 Gen2 时它照样报 1。

已实测两次踩坑，其中一次是用户当场指出的：

```
nvidia-smi：Device Max = 1        ← 缓存，骗人
同一时刻寄存器：
  LnkCap  = 0x00454c42  MaxSpeed=2 (Gen2)
  LnkCap2 = 0x00000006  Gen1/Gen2
  LnkSta  = 0x1042      CurSpeed=2 (Gen2)
  LnkCtl2 = 0x0002      TLS=2 (Gen2)
```

**唯一可信**：`LNKSTA[3:0] == 2`（BAR0 `0x88088` bits[19:16]，或 `lspci` 的 `LnkSta`）。

### 附带的判定 bug
`grep 'Speed 5GT/s'` 会**误匹配 `Speed 2.5GT/s`**（子串）—— 已踩 3 次。
要么读寄存器，要么用 `grep -E 'Speed 5GT/s[^.]'`。

## 铁律 2：改 BAR0 链路控制寄存器必须走内核路径

实测 **2/2 打挂设备**（C. ZOMBIE，`dmesg` 里没有任何 Xid，只能整机重启）：

| 路径 | 场景 | 结果 |
|---|---|---|
| 用户态 `mmap("/dev/mem")` 写 | 链路刚降级（0.5s 内） | **2/2 掉卡** |
| 用户态 mmap 写 | 驱动未加载 / 链路静止 / 等 ≥5s | 多次成功 |
| **内核 `writel`（ioremap）** | 链路刚降级（≤200ms） | 几十次、几十分钟，0 掉卡 |

关键细节：那两次掉卡前**读值是合法的**（`0x20585800`，bit0=0），校验也通过了，
**仍然掉卡**。所以不是"派生值含致命位"，而是**路径本身不安全**。
而且 `dmesg` 里**一个 Xid 都没有** —— 别指望从日志找证据。

⇒ 用户态 mmap 只用于：**只读观察**、或"驱动未加载 / 链路静止"时的一次性推送。
⇒ **绝不用用户态脚本做"链路降级后立即按回"这类时序敏感操作。**

可能机制（未验证，但结论够用）：`writel` 带写屏障；内核路径不会被抢占、写入序列连续；
`/dev/mem` 的 UC- 与 `ioremap` 的 UC 语义不同。

## 铁律 3：读-改-写前必须双校验

```c
lk = readl(0x8C040);                        // 重训瞬态常读到 0xffffffff（常态，不是异常）
if (lk != 0xFFFFFFFFu) {                    // ← 只判这一道不够！
    writel((lk & ~0x000C0000u) | (1u << 18), 0x8C040);
}
//  0xFFFFFFFF & ~0x000C0000 = 0xFFF3FFFF
//  0xFFF3FFFF | (1u << 18)  = 0xFFF7FFFF
//                                 ↑ bit0 = 1 = COMMIT → 必掉卡
```

**写回前双校验**：
1. 读值 `!= 0xFFFFFFFF`
2. **目标寄存器里所有"写 1 致死"的位必须为 0**（`0x8C040` 就是 `(lk & 1) == 0`）

只做第 1 条会留一条真实的掉卡通道。

### 但 COMMIT 本身不是毒药

驱动自己在 `_nv017105rm+0x1ff` 就会写 COMMIT：
```asm
127f40: and $0xfffffff0,%r15d   ; 清 bits[3:0]
127f4e: or  $0x1,%r15d          ; ★ 置 bit0 = COMMIT
127f5a: call <写 0x8C040>
```
前面还有一段"读回轮询直到匹配（eax==0x65）"的前置序列。

⇒ 致命的是**缺前置步骤就写**（SPEED 未写好、训练未完成、来源值含垃圾位），
  不是 COMMIT 本身。
⇒ **但外部仍然不要写 COMMIT** —— 你没有驱动那套前置序列。

## 铁律 4：状态锁死只能整机重启，不要把连续失败当"方法不对"

反复 `rmmod`/`modprobe` 驱动、或改 registry 参数做实验之后，设备会进入：

```
LnkCap.MaxSpeed = 1     LnkCap2 = 0x02（仅 Gen1）     LnkCtl2.TLS = 1
但 0x8841C（声明位）和 0x8872C（触发训练）都写对了，LNKSTA 仍恒为 1
```

实测**所有**挽救手段都失败：

| 手段 | 次数 | 结果 |
|---|---|---|
| `unbind/bind` 触发 push | 6 | 全部 `未升速，LNKSTA=1041` |
| 守卫重训 | 13 | 全部失败 |
| 重写端点 TLS=2 | ~20 | 写 2 后下一轮读回 1 |
| 重新解锁声明 + 触发训练 | 9 | `CAP2` 恒 0x0002 |

**一次整机重启后，第一次 push 就成功。**

⇒ 纪律：
- 试验时**尽量少 reload 驱动**，要改参数就集中一次做完
- 出现「CAP2 恒 0x0002 + TLS 恒 1 + 连续 push 失败」⇒ **直接重启，不要再试**
- 别把它解释成"方法不对"或"概率问题"

## 铁律 5：perf 断点"0 次命中"不能当"没发生"

本项目在这上面栽了两次，两次都导出了**错误结论**：

| 假结论 | 真实原因 |
|---|---|
| 「`CX` 里没有 0x8C040」 | `perf script` **默认不输出寄存器**，必须 `-F comm,iregs` |
| 「`or $0x80000` 各 0 次 ⇒ SPEED=2 是端点内部回写，拦不了」 | 断点地址/时机问题。实际 1 次命中，SPEED 完全由软件写 |

第二条曾让我关闭"再 patch 一个函数"这条路，直接导致这个课题多绕了一天。

⇒ **"没抓到"要先怀疑工具，再怀疑事实。** 交叉验证清单：
- `perf script` 是否带了 `-F iregs` / `--intr-regs` 是否真的生效
- 断点地址算对了没有（**节内偏移 vs 文件偏移差 0x40**）
- 是不是 perf 只用了部分调试寄存器（**x86 只有 4 个**，超了会静默丢弃）
- **拿一个确定会命中的地址做阳性对照**，确认整套机制在工作

## 铁律 6：先问"谁在改"，能让它不改就别事后修

这是整个课题最后才想通、但应该最早想到的一条。

| 阶段 | 做法 | 代价 |
|---|---|---|
| 早期 | 手动推 Gen2，掉了再推 | 带宽永远 Gen1，白费 |
| 中期 | 内核模块 + 200ms 守卫 | 能用，但链路在 Gen1/Gen2 间反复跳，恢复 3.8s |
| **正解** | **让驱动在 `mode==1` 时不写** | **2 字节，链路常驻 Gen2** |

守卫方案看起来"能工作"，实际是**在跟驱动打一场它每次都会赢的仗**。

### 方法论
1. 用 perf 找到"最后那个写者"（不是第一个，是生效的那个）
2. **顺调用栈上溯到"决策点"**，不要停在"写点"（写点通常是通用封装）
3. **在决策点做最小的"不改"**
4. **验证时必须把辅助手段全部摘掉** —— 带守卫测是测不出补丁作用的

### 一个极好用的补丁技巧：平移范围检查的边界

很多函数入口是白名单检查：
```asm
lea  -0x1(%rdx),%eax
cmp  $0x2,%eax
ja   <bail>          ; (arg-1) > 2 → 非法（arg ∉ {1,2,3}）
```
想让 `arg==1` 也非法，**不必加指令**，把两边同时平移：
```asm
lea  -0x2(%rdx),%eax ; arg-2
cmp  $0x1,%eax
ja   <bail>          ; (arg-2) > 1 → 非法（arg=1 下溢成 0xFFFFFFFF）
```
`arg∈{2,3}` 照旧，`arg≥4` 照旧（原本也非法）。
**唯一的行为差异就是你想拦的那一个**，零附带影响、无需 code cave。

⚠ 前提：那个 bail 必须是**正常的 return**（栈平衡、返回值合理）。
本例返回 `%r12d`，而它在函数入口被 `xor` 清零 ⇒ 返回 0 = SUCCESS。**必须逐个确认，不能假设。**

## 铁律 7：远程 reboot 前必查 GRUB recordfail

```bash
grub-editenv - list        # 有 recordfail=1 就先 unset
grub-editenv - unset recordfail
```

`recordfail=1` 会让 Debian 的 `00_header` 把 `timeout` 设成 `-1`（无限等待），
远程重启后**永久卡在 GRUB 菜单**，必须有人到现场按键。

已踩过一次，让用户到现场按了 Enter。

## 铁律 8：NFS root_squash

`/data/labs` 在 NFS 上，属主是 `union`。`sudo make` 会因为 root_squash **无法写入**
（`.gen2kr.o.d: 权限不够`）。

⇒ **编译用普通用户身份，`insmod`/`rmmod` 才用 root。**
⇒ `make` 说"无事可做"时：`touch gen2kr.c && rm -f gen2kr.o gen2kr.ko && make`

## 铁律 9：不要挂 nvitop

`Xid 79` 打死过设备一次（`dmesg` 实证：`Xid 79, pid=13176, name=nvitop`），
而且它占着 `/dev/nvidia*` 使 `rmmod nvidia` 一直 `EBUSY`。

任何轮询 `nvidia-smi` 的监控都要谨慎。

## 铁律 10：批量操作前先想清楚"能不能回滚"

- 打补丁前有备份（`patch_no_gen1.py` 自动做）
- 改 registry / 反复 reload 之前想清楚：状态锁死要整机重启
- 远程操作涉及 GPU 全部卸载时，先把能救回来的手段准备好
  （`reset_subordinate` 实测**救不回** ZOMBIE，exit=0 但设备不回来）
