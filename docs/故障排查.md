# 故障排查

按症状查。

## 症状：重启后带宽又变成 0.78

**最常见的故障，不是 bug。** 详见 `部署与持久化.md`。

`gen2kr` 是手动 `insmod` 的，重启就没了。补丁虽然还在 `nvidia.ko` 里，
但它只负责"不再降级"，不负责"把链路升上去" —— 上电时声明是 Gen1，没人解锁就升不了。

```bash
# 一条命令补齐（补丁已在会跳过 apply）
sudo bash bin/20-install.sh        # 在仓库根目录执行
```

判断是不是这个原因：

```bash
sudo python3 bin/patch_no_gen1.py check   # 应该是 [已打补丁]
lsmod | grep gen2kr                        # 大概率是空（重启丢了）
```

## 症状：编译报 `.gen2kr.o.d: 权限不够`

```
fatal error: opening dependency file .../.gen2kr.o.d: 权限不够
```

**原因**：用 `sudo` 跑编译。若仓库在 NFS 上（`root_squash`），
root 被映射成 nobody，写不进 union 拥有的目录。

**现在的处理**：脚本会**自动降权**到 `SUDO_USER`（`sudo` 时的原用户）编译，
所以 `sudo ./02-gen2-push.sh start` 能直接跑通。

如果仍然失败，通常是拿不到 `SUDO_USER`（例如 `su -` 或 `sudo -i` 之后）：

```bash
# 办法 A：用普通用户单独编
bash bin/build.sh
# 或
bash drivers/580.178.04/02-gen2-push.sh build

# 办法 B：确认用 sudo（不是 su）重新跑
sudo ./02-gen2-push.sh start
```

**注意**：编译**永远不该用 root**，无论仓库在不在 NFS 上 ——
root 编出来的产物属主是 root，之后普通用户改不动。

**另**：若 `make` 说「无事可做」但产物是旧的，先强制清掉：

```bash
cd drivers/580.178.04/kernel/6.12.113
touch gen2kr.c && rm -f gen2kr.o gen2kr.ko && make -C /lib/modules/$(uname -r)/build M=$PWD modules
```

## 症状：`20-install.sh` 说"push 未成功"

先看 `dmesg | grep gen2kr | tail -10`，按日志判断。

### `gen2kr: 未升速，LNKSTA=1041`
push 发了但没升上去。**先看声明解锁了没有**：

```bash
python3 bin/peek-regs.py
# 0x880a4 LNKCAP2 应该是 0x00000006
```

- **CAP2 是 `0x02`** → 声明没解锁。检查 `0x8841C`（应为 `0xc0b4ad00`）。
  注意：写完 `0x8841C` 后 `CAP2` **不会立刻变**，必须触发一次训练（`0x8872C=6`）才锁存。
- **CAP2 已是 `0x06` 但就是不升** → 看下面"声明对但升不上去"。

### `insmod gen2kr.ko` 报 `File exists`
已经在加载了。先 `rmmod gen2kr`，或者直接跳过这步。

### `insmod` 报 `Unknown symbol` / `register_kretprobe failed`
`nv_pci_probe` 找不到 —— 通常是 **nvidia 驱动还没加载**就 insmod 了。
顺序必须是：`modprobe nvidia` → `insmod gen2kr.ko`。

## 症状：声明对（CAP2=0x06）但链路升不上去

### 检查 TLS
```bash
python3 bin/peek-regs.py | grep 0x880a8
# TLS=2 才对；TLS=1 说明端点目标速率还是 2.5GT/s
```

### 检查是不是进了锁死态
```bash
python3 bin/peek-regs.py
```

**判据不能只看「CAP2=0x0002 + TLS=1 + Gen1」** —— 那正是**原厂未解锁**的样子，
刚重启的干净机器必然长这样。真正的锁死态特征是「写过解锁位但没生效」：

```bash
# 0x8841C 的 bit15|bit13|bit11（掩码 0xA800）
#   原厂 0xc0b40500 → (v & 0xA800) == 0      ← 没解锁过，正常
#   解锁 0xc0b4ad00 → (v & 0xA800) == 0xA800 ← 写过解锁
```

如果 `0x8841C & 0xA800 != 0`、但 `CAP2` 仍是 `0x0002`、链路仍是 Gen1
⇒ 写过解锁却没锁存成功 ⇒ **锁死态**。

`bin/_common.sh` 里的 `is_stuck()` 就是按这个判据写的，
`20-install.sh` 前置检查会调用它（干净重启不会误报）。

实测这个状态下所有挽救手段都失败：
`unbind/bind` ×6、守卫重训 ×13、重写 TLS ×20（下轮读回 1）、重新解锁声明 ×9。

⇒ **出现锁死态直接整机重启，不要再试。**
重启后第一次 push 就成功。

### 如果刚重启就失败
那可能是别的问题：

```bash
# 1) 设备活着吗
lspci -Dn | grep 10de:1b87
setpci -s 01:00.0 0.l        # 应该是 1b8710de；ffffffff = ZOMBIE

# 2) 有没有 nvitop 之类的轮询监控
pgrep -a nvitop

# 3) 完整日志
dmesg | grep -iE 'gen2kr|nvidia|Xid' | tail -30
```

## 症状：链路是 Gen2，但带宽只有 0.78

### 最常见原因：测试参数不对
**必须 `512MB × 15`。** `128MB×3` 会落在恢复窗口内，只测到 Gen1 数值。

```bash
build/bwtest2 512 15    # ✓
build/bwtest2 128 3     # ✗ 会得到 0.78，别被误导
```

### 第二常见：用的是 pageable，不是 pinned
Gen1 链路上 pinned 和 pageable 没差别（都 0.78），所以这个坑很容易掩盖。
到了 Gen2 才看得出来：

```
pinned    H2D 1.56  D2H 1.71     ← 真实带宽
pageable  H2D 1.56  D2H 1.70     ← 512MB 时也能到（大块传输绕过了 bounce buffer）
```

真实应用里如果要拿满带宽，**必须用 pinned 内存**（`cudaHostAlloc` / `cudaMemcpyAsync`）。

### 第三：RM 内部还是 Gen1
如果链路能上 Gen2 但带宽不涨，说明**推送时机不对** ——
RM 已经按 Gen1 完成内部数据面初始化了。

⇒ 必须靠 gen2kr 在 `nv_pci_probe` 返回瞬间推。手动事后推只能改链路，改不了内部状态。

## 症状：补丁"自己丢了"

某天突然带宽腰斩，`patch_no_gen1.py check` 说未打补丁。

**原因**：驱动升级 / DKMS 重编 / 换内核 → `nvidia.ko` 被重新生成，
二进制补丁**静默丢失**（不会报错）。

**这是设计上的已知限制**，这也是为什么建议保留守卫常驻（它是唯一兜底）。

```bash
# 自查
sudo python3 bin/patch_no_gen1.py check

# 重新打（不需要重启，但要重载驱动）
sudo python3 bin/patch_no_gen1.py apply
sudo rmmod nvidia_uvm nvidia_modeset nvidia_drm nvidia
sudo modprobe nvidia && sudo modprobe nvidia_uvm
```

## 症状：看不出受限设备表里到底有哪些卡

`00-whitelist.sh check` 已经打过补丁时，5 个 dword 全是 `0x0007FFFF`：

```
0x05cfdfcc  当前=ffff   已打
0x05cfdfd0  当前=ffff   已打
...
```

**低 16 位被换成了哨兵 `0xffff`，原始 device ID 已经不在文件里了**，
光看这个文件无法回答"我这型号在不在表里"。

**办法**：读备份 `.orig`（apply 时自动生成，是打补丁前的原厂值）。

```bash
python3 - <<'PY'
import struct
base = 0x5cfdfcc
for name, p in [("orig","/usr/src/nvidia-580.178.04/nvidia/nv-kernel.o_binary.orig"),
                ("current","/usr/src/nvidia-580.178.04/nvidia/nv-kernel.o_binary")]:
    with open(p,"rb") as f:
        f.seek(base); v = struct.unpack("<5I", f.read(20))
    print(name, " ".join(f"0x{x:08x}" for x in v))
PY
```

本版本（580.178.04）原始值是这 5 张，**全都是受限矿卡**：

| device ID | 型号 |
|---|---|
| `0x1B07` | P102-100 |
| `0x1B87` | **P104-100**（本项目这张） |
| `0x1BC7` | P104-101 |
| `0x1C07` | P106-100 |
| `0x1C09` | P106-090 |

现在 `00-whitelist.sh check` 会直接把这张表连同 `.orig` 里的原始值打出来，
并在本机那张卡后面标 `★`。

⚠ 如果 `.orig` 也没了（比如手动删过），就只能按下表核对 —— 这张表是
**驱动版本绑定**的，换版本偏移和条目都可能变。

## 症状：`rmmod nvidia` 报 `EBUSY`

有进程占着 `/dev/nvidia*`：

```bash
sudo fuser -v /dev/nvidia* 2>/dev/null
```

常见占用者：
- **Xorg**（桌面会话）→ `sudo systemctl stop sddm`（注意：这不结束已登录的 KDE 会话，
  还需要 `loginctl terminate-session <seat0 会话>`）
- **nvitop** / 任何轮询 `nvidia-smi` 的监控
- 任何还在跑的 CUDA 程序

`loginctl` 的坑：`terminate-user` 会**把你自己的 SSH 一起杀掉**，用 `terminate-session`。

## 症状：设备 ZOMBIE（`cfg = ffffffff`）

```bash
setpci -s 01:00.0 0.l
# 1b8710de → 正常
# ffffffff → 看下面三态判定
```

| 状态 | 特征 | 能救吗 |
|---|---|---|
| **A. D3COLD** | 在 lspci、`power_state=D3cold`、`CAP_EXP` 能读 | 可能可以 |
| **B. GONE** | 不在 lspci | ❌ 重启 |
| **C. ZOMBIE** | 在 lspci、`power=D0`、`CAP_EXP` 找不到、`cfg=ffffffff` | ❌ **重启** |

**实测 `reset_subordinate` 救不回 C**（exit=0 但设备不回来，rescan 也扫不到）。

```bash
# 判定工具
python3 bin/linkcap-audit.py
```

## 症状：`build.sh` 报找不到 `cuda.h` / 链接失败

`bwtest2.c` 用 `dlopen("libcuda.so.1")` 手工取 driver API 入口，
理论上不需要 CUDA toolkit。如果链接失败，检查：

```bash
ls -l /usr/lib/x86_64-linux-gnu/libcuda.so*
# 只要 libcuda.so.1 存在，-ldl 就够了
```

`minictx` 只依赖 `-ldl`，一定能编过。

## 症状：重启后卡在 GRUB 菜单

Debian 的 `recordfail` 机制：上次启动没被标记成功 → `timeout=-1` → 永久等按键。

```bash
# 到现场按 Enter 进系统后
sudo grub-editenv - unset recordfail
sudo grub-editenv - list        # 确认为空
```

**以后远程 reboot 前先查**：
```bash
grub-editenv - list
# 有 recordfail=1 就先 unset
```

## 症状：`perf` 抓不到断点

```bash
# 拿一个确定会命中的地址做阳性对照
perf record -e mem:$(grep ' __x64_sys_read$' /proc/kallsyms | awk '{print "0x"$1}'):x -a -- sleep 2
```

如果阳性对照也没命中，说明 perf 环境有问题（权限 / `perf_event_paranoid`）。

如果阳性对照命中、但目标地址 0 次，检查：
1. **地址算对了没有** —— `.text` 节内偏移 vs 文件偏移差 **0x40**
2. **`perf script` 带了 `-F comm,iregs` 没有** —— 不带就看不到寄存器
3. **断点数量** —— x86 只有 4 个调试寄存器，超了静默丢弃

## 症状：判 Gen2 时被 `grep` 骗了

```bash
lspci -vv -s 01:00.0 | grep 'Speed 5GT/s'    # ✗ 会匹配 "Speed 2.5GT/s"
```

正确做法：

```bash
# 方案 1：读寄存器（最可靠）
python3 bin/peek-regs.py | grep 0x88088       # CurSpeed=2 才是 Gen2

# 方案 2：精确匹配
lspci -vv -s 01:00.0 | grep -oE 'Speed 5GT/s[^.]'
```

**永远不要用 `nvidia-smi`** —— 它读驱动缓存，寄存器已是 Gen2 也报 1。
